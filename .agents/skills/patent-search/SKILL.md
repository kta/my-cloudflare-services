# patent-search — 構成要件ごとに先行技術を探し、典拠を積む

あなたは弁理士の調査担当として働く。**似た文献を眺めるのではなく、構成要件ごとに
「それを開示する公報のどの段落か」を突き止める。**

## 動かす前提

```sh
# 1. コーパスサイドカーが起きていること
make corpus/serve            # 別のターミナル。INTERNAL_KEY を渡す

# 2. アプリが起きていること
make dev/patent_research     # :5177
```

以下では `BASE=http://localhost:5177`、`TOKEN` は `POST $BASE/api/auth/token` で得た値とする。

## 手順

### 1. 仕事を 1 つ拾う

`GET $BASE/api/jobs` から `status=queued` かつ `kind=search` のものを 1 つ選ぶ。
`instruction` に人間の指示があれば必ず読む。**複数を同時に進めない**（未出願の発明が動くので、
何をいつ触ったかが曖昧になってはいけない）。

### 2. 案件の中身を読む

- `GET $BASE/api/matters/:id/disclosure` — 課題・手段・効果・キーワード
- `GET $BASE/api/matters/:id/elements` — 構成要件（A・B・C…）と、既に付いている典拠の数
- `GET $BASE/api/matters/:id/searches` — 既に実行した検索式。**同じ式を繰り返さない**

### 3. 構成要件ごとに検索式を組む

要件 1 つにつき、**最低 3 通り**の言い換えで探す。特許の文章は同じ概念を違う語で書く。

- 上位概念 / 下位概念（「瞳孔中心」↔「瞳孔」「暗瞳孔法」「角膜反射」）
- 装置の呼び方の揺れ（「撮像部」「カメラ」「イメージセンサ」）
- 動作の言い方の揺れ（「検出する」「抽出する」「特定する」「算出する」）

分類コード（`ipcPrefix`）で絞ると精度が上がるが、**最初から絞りすぎない**。
広い式で当たりを見てから絞る。日付は、出願を予定している日より前に公開されたものを見る
（`pubDateTo`）。

```sh
curl -s -X POST "$BASE/api/matters/$MATTER/searches" \
  -H "authorization: Bearer $TOKEN" -H 'content-type: application/json' \
  -d '{"terms":["瞳孔","中心","検出"],"elementId":"<要件のid>","ipcPrefix":"G06F3","limit":50}'
```

**検索は必ずこの API を通す。** コーパスの CLI を直接叩いてはならない —
API を通したものだけが検索の記録として残り、調査報告書になる。

応答の `record` を必ず読む:
- `hitCount` が 0 でも、`matchExpression` が `null` なら**検索語が空だった**（探していない）
- `splitTerms` / `droppedTerms` に語があれば、その語は思ったとおりに効いていない
- `undatedCount` は公開日が不明な公報の数。日付で絞っても落とされていない

`503 corpus_unavailable` が返ったら **0 件ではない**。サイドカーを起こしてやり直す。

### 4. 典拠を積む

当たった段落を典拠として積む。**引用文は公報の原文をそのまま貼る。**

```sh
curl -s -X POST "$BASE/api/matters/$MATTER/evidence" \
  -H "authorization: Bearer $TOKEN" -H 'content-type: application/json' \
  -d '{"elementId":"...","pubNumber":"特開2018-134274","paraNo":"0032",
       "quotedText":"<段落の原文をそのまま>","relation":"discloses","note":"要件Bの瞳孔中心検出に対応"}'
```

`relation` は次から選ぶ:
- `discloses` — その構成要件を開示している
- `suggests` — 示唆している（そのものは書いていないが、当業者が読み取れる）
- `teaches_away` — **阻害要因**。進歩性の主張で最も価値がある
- `background` — 技術水準を示すだけ
- `unrelated` — 関係ない

### 5. 応答の `quoteCheck` を必ず確認する

これがこの仕事の一番大事なところである。**あなたが送った引用は、機械が公報の原文と
突き合わせて判定される。あなたの申告は通らない。**

| 返ってきた値 | 意味 | やること |
|---|---|---|
| `verified` | 引用が原文に実在した | そのまま。次へ |
| `quote_mismatch` | **その段落にその文は無い** | 積み直す。段落番号を間違えたか、要約してしまったか、作ってしまったかのどれかである |
| `quote_too_short` | 引用が 10 文字未満 | 前後を含めて引用し直す |
| `paragraph_missing` | その段落番号が無い | 段落番号を確認する |
| `publication_missing` | その公報がコーパスに無い | 公報番号を確認する。コーパスの範囲外かもしれない |
| `not_in_corpus_tier2` | その公報の全文（またはその部分）が未取り込み | **「無い」と結論してはならない**。取り込み範囲の問題である |
| `pending` | コーパスに届かなかった | サイドカーを起こして `POST /api/matters/:id/evidence/recheck` |

**`quote_mismatch` が出たら、必ず原因を突き止めてから積み直す。**
`quoteCheckDetail` に実際の段落の冒頭が入っているので、それと自分の引用を見比べる。
同じ間違いを繰り返さない。

### 6. 見つからなかったことも報告する

典拠が 1 件も見つからなかった構成要件は、**新規性の勝ち筋の候補**である。
ただし「探していない」と「探したが無かった」は違う。
実行した検索式を列挙し、**どの範囲を見て見つからなかったのか**を書く。

### 7. 仕事を閉じる

やったことを `instruction` に対する答えとして書き、人間が読めるようにまとめる。
まとめには必ず次を含める。

- 実行した検索式（全部）とヒット件数
- 構成要件ごとの典拠の数と、照合が通った数
- **照合が通らなかった引用があれば、その理由**
- 典拠が 0 件の構成要件と、そこを探すのに使った式

## やってはいけないこと

- コーパスの CLI で直接検索して、その結果を典拠にする（記録が残らない）
- 引用文を要約・意訳して積む（照合が通らない。通ったら、それは偶然であって危険）
- `quote_mismatch` を無視して次へ進む
- 見つからなかったことを「存在しない」と書く（「この検索式では見つからなかった」と書く）
- 未出願の発明の本文を外部の LLM へ送る

この文書の `IDX-<群>-NN` は**仕様の索引**であり、承認済みの受入基準は `features/<NNN>-*/spec.md` にある。
ここに書いた索引番号は、後続の feature spec が `UC-` / `AC-` を定義するときの割り当て表として使う。
UC/AC の**定義**は `spec.md` にだけ置き、この文書は参照だけを行う（traceability validator の分母には入らない）。
**接頭辞が違うので、この文書の番号と feature spec の番号は grep で必ず見分けられる**（§0.2）。

- 読む人: 実装者（Worker / React / 契約）とテスト作成者（integration / web unit / E2E）。
- 粒度の基準: 「誰が読んでも同じ実装になる」。曖昧語は使わず、数値と条件で書く。
- 出典: `docs/frontend/mockups/eyex/`（68画面の HTML / PNG）と `assets/eyex.css`、および決定ブリーフ。
  **モックに描かれていないことは、モック・決定ブリーフ・設計判断で決着させて本文に断定で書く。発注元（EYEX）の運用・法務・機材の実情を知らないと決められない論点だけを `[要確認: Q-NN — いまの前提で進める]` として残す。問いの本体と暫定案は `design/09-open-questions.md`（Q-01〜Q-12）にあり、この文書は Q 番号で参照するだけである（§12）。**
- 文言は画面に出ている日本語をそのまま引用する（鉤括弧つき）。

## 0.2 この文書と feature spec の関係（見出し番号は `IDX-` を使う）

- **この文書の見出し番号は `IDX-<群>-NN` であり、`features/*/spec.md` が定義する `UC-<群>-NN` とは接頭辞から別である。**
  番号が同じでも指す業務は違う（例: この文書の `IDX-CUST-04` は「新しいお客様を登録する」だが、
  `features/007-customer-records/spec.md` の `UC-CUST-04` は「お客様の詳細で度数の移り変わりを読める」である）。
  接頭辞を分けてあるので、`grep -rn 'UC-CUST-04' specs/glasses_management` が指すのは feature spec の 1 業務だけになる（この節の説明文と `design/08-traceability.md` の対応表を除く）。
  **実装とテストが従うのは feature spec の `UC-` / `AC-` だけ**であり、`@e2e-covers` に `IDX-` を書いてはならない。
  この文書の番号は、群と本数を見渡すための索引として読む。
- **各 IDX の「検証点」は AC の素材**であって AC ではない。AC の定義は `features/*/spec.md` にだけ置く。
  UC ↔ AC ↔ 画面 ↔ E2E の対応表は `design/08-traceability.md` にある（363 件。traceability validator の分母ではない）。
- **`[要確認]` の問いをこの文書に置かない。** 発注元に聞くことの正本は `design/09-open-questions.md`（Q-01〜Q-12）で、
  本文には `[要確認: Q-NN — いまの前提で進める]` の参照だけを残す（§12）。

## 1. FOUND — 基盤・認証・テナント分離

### IDX-FOUND-01 ヘルスを確かめる

| 項目 | 内容 |
|---|---|
| 主体 | 運用者・監視 Cron |
| 事前条件 | Worker がデプロイされている |
| トリガ | `GET /api/health` を呼ぶ |

**主フロー**

1. 呼び出し側が `GET /api/health` を認証なしで送る。
2. Worker は D1 に触れず `{ "status": "ok" }` を 200 で返す。

**代替フロー**

- なし。

**例外フロー**

- E1. Worker 自体が起動できない場合はプラットフォームが 5xx を返す。アプリ側の分岐は持たない。

**事後条件**

- 副作用なし。監査記録も残さない。

**対応する画面**: なし（API のみ）

**検証点**

- 認証ヘッダなしで 200 が返る。
- default-deny ゲートの例外パスに `/api/health` が含まれている。

### IDX-FOUND-02 admin から組織スナップショットを受け取る

| 項目 | 内容 |
|---|---|
| 主体 | admin Worker（service binding `GLASSES_MANAGEMENT`） |
| 事前条件 | `INTERNAL_KEY` が両サービスに設定されている |
| トリガ | admin が組織を作成・更新した、または日次照合 Cron が走った |

**主フロー**

1. admin が `POST /api/internal/organizations` を `x-internal-key` 付きで呼ぶ。
2. body は組織スナップショット（id / name / plan / is_disabled / revision）。
3. Worker は `revision` が既存行以上のときだけ `organizations` を upsert する。
4. 200 を返す。

**代替フロー**

- 3a. `revision` が既存行より小さい場合は書き込まず 200 を返す（到着順の逆転で古い状態へ戻さない）。

**例外フロー**

- E1. `x-internal-key` が無い・一致しない → 401 `{"error":"unauthorized"}`。テナント JWT では越えられない。
- E2. `INTERNAL_KEY` が未設定のときも同じ 401 を返して処理しない（fail close。`packages/shared` の `internalAuth()` の挙動をそのまま使い、自前で検証し直さない）。

**事後条件**

- `organizations` に最新 revision の 1 行がある。ドメイン行は変更しない。

**対応する画面**: なし（API のみ）

**検証点**

- 古い revision で上書きされない。
- テナント JWT では `/api/internal/*` に到達できない。

### IDX-FOUND-03 dev トークンで業務 API に入る

| 項目 | 内容 |
|---|---|
| 主体 | 開発者・E2E |
| 事前条件 | `AUTH_DEV_GRANT` が設定されている（dev のみ。本番では未設定） |
| トリガ | `POST /api/auth/token` を呼ぶ |

**主フロー**

1. 開発者が組織 id とロールを指定して `POST /api/auth/token` を呼ぶ。
2. Worker は access JWT を返す。
3. 以降の `/api/staff/**` はこの JWT で通る。

**代替フロー**

- なし。

**例外フロー**

- E1. `AUTH_DEV_GRANT` が `'true'` 以外（未設定を含む）→ 404 `{"error":"not_found"}` を返し、経路ごと存在しない扱いにする。本番でトークンを発行しない。

**事後条件**

- 認証済みセッションが確立する。DB は変わらない。

**対応する画面**: なし（API のみ）

**検証点**

- `AUTH_DEV_GRANT` 未設定の環境でトークンが発行されない。

### IDX-FOUND-04 認証されていない要求を止める

| 項目 | 内容 |
|---|---|
| 主体 | 任意の呼び出し元 |
| 事前条件 | なし |
| トリガ | `/api/staff/**` またはルート表に無いパスを叩く |

**主フロー**

1. 呼び出し元が JWT なしで `/api/staff/reservations` を叩く。
2. default-deny ゲートが 401 を返す。

**代替フロー**

- 1a. `/api/not-a-route` のような未知パスも同じく 401（ルートを足しただけで保護される証明）。

**例外フロー**

- E1. JWT が期限切れ → 401（再ログイン判定に使う）。
- E2. JWT は有効だが権限が足りない → 403。401 と取り違えない。
- E3. 別 secret で署名された JWT → 401。

**事後条件**

- ドメインデータに触れていない。

**対応する画面**: なし（API のみ）

**検証点**

- 未認証 / 期限切れ / 別 secret / 権限不足 / 未知パスの 5 行を表駆動で固定する。
- 業務ルートを 1 本足したら表に 1 行足す。

### IDX-FOUND-05 組織が未同期・無効化のときを切り分ける

| 項目 | 内容 |
|---|---|
| 主体 | 受付スタッフ（結果として画面に出る） |
| 事前条件 | 有効な JWT を持っている |
| トリガ | 業務 API を呼ぶ |

**主フロー**

1. `requireActiveOrg` が JWT の `org` で `organizations` を引く。
2. 行があり `is_disabled = '0'` なら通す。

**代替フロー**

- なし。

**例外フロー**

- E1. 行が無い（admin から未同期）→ 503 `not_synced`。リトライ可能として扱う。
- E2. `is_disabled = '1'` → 403 `org_disabled`。
- E3. 再同期後は同じ要求が 200 になる。

**事後条件**

- 503 / 403 のときドメインデータを読み書きしていない。

**対応する画面**: なし（API のみ）

**検証点**

- 未同期 503 → 同期 → 200 → 無効化 403 の遷移を 1 本で書く。

### IDX-FOUND-06 他テナントのデータに触れさせない

| 項目 | 内容 |
|---|---|
| 主体 | 悪意ある・誤った呼び出し元 |
| 事前条件 | 3 組織以上が同居している |
| トリガ | 他組織の予約 id・顧客 id を指定して読み書きする |

**主フロー**

1. 組織 A の JWT で組織 B の予約 id を指定して取得する。
2. 全クエリが `organization_id = JWT の org` でスコープされているため 0 件になり 404 を返す。

**代替フロー**

- 1a. 一覧取得では他組織の行が 1 件も混ざらない。

**例外フロー**

- E1. body に `organizationId` を混ぜて偽装しても、認可根拠は JWT の `org` のみで body を見ない。
- E2. 選択中 `store_id` が他組織の店舗を指していても、`organization_id` との積で 0 件になる。

**事後条件**

- 他組織の行が読めない・書き換わらない。

**対応する画面**: なし（API のみ）

**検証点**

- 3 テナント同時稼働で越境 read / write が 0 件。
- 入力偽装が効かないことを 1 本。

### IDX-FOUND-07 選択中店舗を切り替える

| 項目 | 内容 |
|---|---|
| 主体 | 受付スタッフ |
| 事前条件 | 組織に銀座店・丸の内店・新宿店の 3 店舗がある |
| トリガ | ヘッダーの店舗名（共有端末の業務開始画面では「別の店舗」）を押す |

**主フロー**

1. スタッフが店舗の一覧から 1 店舗を選ぶ。
2. 選択中店舗が切り替わる。
3. 台帳・検索・設定・空き枠のすべてが新しい `store_id` でスコープされる。

**代替フロー**

- 2a. 業務開始前（LOGIN-SHARED）に切り替えた場合は、そのまま置き場所の選択へ進む。

**例外フロー**

- E1. 他組織の店舗 slug を直接指定しても解決できず、選択中店舗は変わらない。

**事後条件**

- 以降の全画面が同じ選択中店舗を指す。

**対応する画面**: LOGIN-SHARED（「別の店舗」「丸の内店・新宿店」）、各画面の appbar 店舗名

**検証点**

- 切り替え後に台帳の行（担当・設備）が新しい店舗のものへ入れ替わる。
- 切り替えが選択中店舗以外の状態（絞り込み・日付）を壊さないこと。**表示中の日付・並べ方・表示のかたち・絞り込みはそのまま保ち、本日へは戻さない**。店舗を切り替えて変わるのは `store_id` だけである。

## 2. SET — 店舗設定

設定画面は共通の骨格を持つ。左に第2サイドバー（236px・分類）、右上に `setbar`（左「キャンセル」／中央に見出し／右に「未保存の変更 N件」＋「保存」）、その下に設定本体。
第2サイドバーの分類は 5 群（店舗の設定 / Web予約 / 顧客台帳 / 端末とスタッフ / 全般）で全画面同一。
このうちモックが描いているのは「店舗の情報」「営業日」「営業時間」「ご来店の目的」「スタッフと技能」「設備と点検」「公開」の 7 項目である。
残る 8 項目（「予約のきまり」「受付できる時間」「お知らせ文」「（顧客台帳）項目」「注意ごと」「端末の登録」「PINと自動ロック」「通知・印刷」）は**行ごと出さない**。モックが描いていない画面を、空いた場所を埋めるために起こさない（モック README の決め事）。第2サイドバーに並ぶのは上の 7 項目だけである。

### IDX-SET-01 店舗の情報を直して保存する

| 項目 | 内容 |
|---|---|
| 主体 | 店長 |
| 事前条件 | 選択中店舗 = 銀座店 |
| トリガ | サイドバー「設定」→ 第2サイドバー「店舗の情報」 |

**主フロー**

1. 画面が「お店の基本」（店名 / お客様に見せる店名 / 電話番号 / 住所）と「行き方のご案内」（最寄り駅 / 出口と所要時間 / 駐車場）を表示する。
2. 店長が値を直す。
3. `setbar` の状態札が「未保存の変更 2件」に変わる。
4. 「保存」を押すと `stores` を更新する。
5. 状態札が消える。

**代替フロー**

- 4a. 「キャンセル」を押すと編集前の値へ戻し、状態札を消す。

## 3. LEDGER — 空き枠と台帳

台帳は縦が担当者または設備・場所、横が時間。時間グリッドは背景として通し（30分ごとの薄い線・1時間ごとの濃い線）、予約の帯をまたいでも途切れさせない。
モックの表示範囲は **10:00–17:00（30分 × 14枠 = 420分）**で、列見出しは各枠の開始時刻 10:00–16:30 の 14 個である。左の見出し列は 170px、時間軸は残り幅を 14 等分する。
営業時間は 10:00–19:00 の 18 枠あるが、画面に出すのは**14 枠の表示窓**で、残りは横スクロールで読む（LEDGER-STAFF / LEDGER-RESOURCE / LEDGER-DETAIL の 3 面がいずれも 14 列で描かれている）。
現在時刻は台帳の中では線だけを引き、文字はツールバーの札（「現在 11:08」）に置く。

### IDX-LEDGER-01 担当者別で当日の台帳を読む

| 項目 | 内容 |
|---|---|
| 主体 | 受付スタッフ |
| 事前条件 | 業務開始済み・選択中店舗 = 銀座店 |
| トリガ | サイドバー「予約台帳」を押す |

**主フロー**

1. 既定でサイドバーをたたんだ状態（76px）で開く。
2. ツールバーの並べ方が「担当者」、表示のかたちが「タイムテーブル」で選ばれている。
3. 縦に担当（佐藤 美咲／高橋 健／中村 彩）と「担当が未定」の擬似行、最下段に「ご来店お待ち」の帯が並ぶ。
4. 各予約は帯として置かれ、お客様名・来店回数・ご用件を持つ。出どころは **4 語（お電話／店頭／Web予約／ウォークイン）**で持ち、色は 3 系統（お電話・店頭＝緑、Web予約＝青、ウォークイン＝茶）にまとめる。帯の中に出どころの語を書くのは Web予約（「Web予約」）とウォークイン（「ウォークイン 004」）だけで、緑の帯には語を添えない（緑は既定なので色に意味が乗らない）。「お電話」と「店頭」の別は予約リスト（EX-OFFLINE）と予約詳細（LEDGER-DETAIL）で文字にする。

## 4. BOOK — 予約受付（電話・店頭）

予約は会話の順で 1 工程 1 問。工程は 5 つ（1 日時 / 2 ご来店の目的 / 3 担当と場所 / 4 お客様 / 5 ご確認）。
下の帯に工程と録音を常に出し、右下または帯の右に録音の経過時間を出す。予約フローの画面にはサイドバーを出さない。
出口は 3 つ持つ — ①appbar の「やめる」＝受付を破棄する（IDX-REC-09）②appbar の「あとで続ける」＝`reception_sessions` を進行中（`outcome IS NULL`）のまま置き、
仮の押さえを解放して、トップに「受けかけのご予約 N件」を出す（続きから戻ったときに押さえを取り直す）③工程の帯の左の「‹」＝1 つ前の工程へ戻る。
台帳を見たいだけの割り込みには、予約フローの上に**読むだけの台帳シート**を重ねる（書き込みの導線を持たないので受付の状態を壊さない）。
「やめる」しか出口が無いと、電話の途中の保留・折り返しで伺った内容を毎回捨てることになる。

### IDX-BOOK-01 お日にちとお時間を伺う

| 項目 | 内容 |
|---|---|
| 主体 | 受付スタッフ |
| 事前条件 | 業務開始済み。選択中店舗が決まっている |
| トリガ | トップ「新しい予約を取る」またはサイドバー「＋ 予約を取る」 |

**主フロー**

1. 受付セッションを開始し、録音を始める（IDX-REC-01）。
2. 「お日にちはいつがよろしいですか？」の月カレンダーを出す。定休日（火）は押せず「定休」と文字を添える。
3. スタッフが日付を選ぶ（既定は本日 27 が選択状態）。
4. 「お時間は何時ごろがよろしいですか？」の時刻の札を 8 枠出す。各札に残り枠数（「あと3枠」「あと2枠」「あと1枠」）を添え、埋まっている枠は押せず「満席」と書く。枠は「受け付けられる時刻だけを出しています。」に従い、IDX-LEDGER-07 の結果をそのまま並べる（モックは 10:00 / 10:30 / 11:00 / 11:30満席 / 13:00 / 13:30 / 14:00 / 14:30満席 の 8 枠で、12:00 台が 1 枠も無い。**受付を止める帯（お昼）が 12:00–13:00 だからである**。IDX-WEB-05 の E3 と §13 を参照）。
5. スタッフが時刻を選ぶ。
6. 右のまとめに「ご来店日」「ご来店時刻」が入り、目的とお客様は「このあと伺います」のままにする。
7. 次へ（工程 2）へ進む。

**代替フロー**

- 4a. この時点の枠は目的が未確定のため暫定である（「目的を伺ったあとに、もう一度確かめます。」）。

**例外フロー**

- E1. 選んだ日の空き枠が 0 件のとき、時刻の札をすべて「満席」にする。

- 枠の二重確保は、刻み（`slot_minutes`）単位に展開した占有表 `reservation_slot_locks(organization_id, store_id, kind, target_id, slot_start)` の UNIQUE index で止める。
  確定・変更では `reservations` / `reservation_purposes` / `reservation_assignments` / `audit_events` と**同じ `db.batch()`** にこの INSERT を並べ、衝突したらバッチごと失敗させて 409 `slot_taken` を返す。
  取消・変更では同じバッチで DELETE する。「同じ `db.batch()` の中で重なりを読み直して判定する」形は D1 では書けない（バッチは全文を投げて結果をまとめて受け取るので、読んだ結果で分岐して書けない）ため、
  読みと書きの間に別端末の書き込みが入る窓が空く。1 予約 60 分・刻み 30 分・担当 1 + 設備 2 でも 6 行しか増えない。**この表を足すのは決定ブリーフ §3 の変更なので、実装の前に人間の承認を取る。**
- 予約番号が `EY-YYMM-NNNN` の形になる。
- 復唱文の各値が入力と一致する。

- 3a. すべて済みでなくても受け付けられる。必須のチェックは設けない（お客様を待たせないことを優先する）。ただし「確かめずに受けた」ことが後から分かるように、消し込みの結果を受付に残す。

**例外フロー**

- E1. 注意ごとが 0 件のときは 2 行になる。

**事後条件**

- 確認の記録が受付に残る。行ごとに済み・未済と、済みにした時刻・操作者を保存し、受付履歴の 1 件から読み返せるようにする。

**対応する画面**: RECEPTION-CHECKIN

**検証点**

- 注意ごとの行が顧客の注意ごと（`customer_notes` の `attention`）と一致する。

### IDX-RECEP-03 お待ちいただく

| 項目 | 内容 |

| 主体 | 受付スタッフ |
| 事前条件 | 来店受付の画面を開いている |
| トリガ | 「お待ちいただく」を押す |

**主フロー**

1. 来店の記録に「待ち」を残す。
2. 来店受付ボードで待ち時間の計測を始める。

**代替フロー**

- 3a. 対応が始まると「対応中」に変わる。

**例外フロー**

- E1. 目安を超えた待ちは分析（IDX-ANA-05）の母数に入る。

**事後条件**

### IDX-RECEP-04 来店受付ボードで工程を見る

| 項目 | 内容 |
|---|---|
| 主体 | フロアの全スタッフ |
| 事前条件 | 来店中のお客様がいる |
| トリガ | サイドバー「来店受付」を押す |

**主フロー**

1. ボードが縦にお客様、横に工程 6 つ（受付／ご相談／フレーム選び／視力測定／レンズ・お会計／お渡し）で出る。列と `visit_events.stage` の対応は下の表で固定する。
2. 各セルの状態は 4 語だけ（「済みました」「対応中」「次にやること」「お待たせ中」）。「済みました」は終了時刻、「対応中」は開始時刻＋「〜」、「次にやること」は使う設備名、「お待たせ中」は経過分数を添える。
3. 「対応中」は緑の縦線と開始時刻、「次にやること」は緑地、「お待たせ中」は赤地で示す。色だけに意味を持たせず、上の 4 語を必ず添える。
4. 空のセルは空のままにする。
5. 右上に日付と人数を出す（「2026年8月27日（木）　ご来店中 4名」）。行数はこの人数と一致する（モックは 田中 花子 様／ウォークイン 003／山口 真央 様／伊藤 健 様 の 4 行）。

**列と `visit_events.stage` の対応**

| 列（画面の文言） | `visit_events.stage` |
|---|---|
| 受付 | `received` |
| ご相談 | `consulting` |
| フレーム選び | `fitting` |
| 視力測定 | `measuring` |
| レンズ・お会計 | `checkout` |
| お渡し | `handover` |

`waiting` は列を持たず、セルの状態「お待たせ中」として表す（IDX-RECEP-03）。`left`（退店）も列を持たず、退店した人を「ご来店中」から外すための記録として使う（IDX-RECEP-05 の代替 1b。定義は `features/008-reception-and-walkin/spec.md` の UC-RECEP-14 にある）。
`visit_events.stage` は決定ブリーフ §3.3 の 7 値に **`handover`（お渡し）を足した 8 値**とする。「お渡し」に `left` を当てることはできない — RECEPTION-JOURNEY の 伊藤 健 様は「お渡し　対応中 11:04〜」でありながら右上の「ご来店中 4名」に数えられており、退店を当てると来店中から外れて人数が合わなくなるためである。

**代替フロー**

- 1a. 「ご来店中」と「本日すべて」を切り替える。

**例外フロー**

- E1. 来店中が 0 名のときは、列見出しを残したまま空の面の型で出す（「いまご来店中のお客様はいません」「受け付けると、ここに並びます。」＋「＋ ご来店を受け付ける」）。

**事後条件**

- 表示だけ。

**対応する画面**: RECEPTION-JOURNEY

**検証点**

- 待たせている行が最上部でなくても赤地で真っ先に目に入る。
- ウォークインの行は来店回数バッジを出さない。

### IDX-RECEP-05 工程を進める

| 項目 | 内容 |
|---|---|
| 主体 | 担当スタッフ |
| 事前条件 | 来店中のお客様がボードに載っている |
| トリガ | 工程のセルを押す |

**主フロー**

1. 押した工程を「対応中」にし、開始時刻を記録する。
2. 前の工程を「済みました」にして終了時刻を残す。
3. **次に着手する予定の工程**を「次にやること」として示し、使う設備名を添える。「対応中」の隣の列とは限らない（モックの 山口 真央 様は ご相談＝対応中 11:02〜 のまま、2 つ右の 視力測定 に「次にやること 視力測定機 B」が付いている）。
4. 「次にやること」はお客様 1 人につき 0 個または 1 個とする。

**代替フロー**

- 1a. 工程を飛ばして先へ進める（伊藤 健 様は 受付 10:42 → ご相談 10:52 のあと フレーム選び・視力測定 を空のまま飛ばし、レンズ・お会計 11:01 → お渡し 11:04〜 と進んでいる）。
- 1b. 「お渡し」を済みにしたあと「ご来店を終える」を押すと、`visit_events` に `left` を積み、その行を「ご来店中」から外す（ウォークインは `walk_ins.left_at` も入れる）。**これが 1 日の終点**であり、`customers.visit_count` の書き戻しもこの遷移に紐づく。閉店時に盤面へ人が残らないよう、この操作は担当以外も押せる。

**例外フロー**

- E1. 工程を進める入口は、その行の**「次にやること」のセルを押すこと**とする（押すと「対応中」に変わり、前の工程が「済みました」になる）。**担当以外のスタッフも進められる**（受付は手の空いた人がやるため）。誰が進めたかは `visit_events` と `audit_events` に残す。
- E2. 営業終了時刻を過ぎても `status='confirmed'` のまま残った予約（＝退店まで進めずに終わった予約）は、日次 Cron が洗い出して「対応が必要」のお知らせに 1 件立てる（件数と一覧つき）。**自動で `no_show` には倒さない**（レジが混んで押し忘れただけのお客様が無断キャンセルとして記録に残るため）。翌朝に人が片づける。`customers.visit_count` も分析の再来率も現場の押し忘れに従属するので、この 1 本が無いと数が静かに狂う。

**事後条件**

- `visit_events` に工程ごとの行が積まれる。

**対応する画面**: RECEPTION-JOURNEY

**検証点**

- 工程の並びが 受付／ご相談／フレーム選び／視力測定／レンズ・お会計／お渡し で固定される。
- 「対応中」は 1 人につき 1 工程だけ。

### IDX-RECEP-06 店頭のお客様を受け付ける（ウォークイン）

| 項目 | 内容 |
|---|---|
| 主体 | 受付スタッフ |
| 事前条件 | 台帳を開いている |
| トリガ | サイドバー「来店受付」または予約リストの「ご案内」 |

**主フロー**

1. 台帳を見たまま右から受付パネル（400px）が出る。
2. 上に待ち状況と整理番号を出す（「いまお待ち 2名」「目安 15分」「ウォークイン 005」）。「目安」は**空き枠エンジンの結果から出す**
   （選んだご用件を受けられる担当が次に空く時刻 − 現在時刻）。待ち人数だけの式（件数 × 平均接客分数）では、空いている担当が 3 人いても同じ数字になり、モックの「2名／15分」も再現できない
   （ご用件は最短でも 20 分である）。この数字はお客様への約束になるので、出せないときは「目安」を出さず「いまお待ち 2名」だけにする。
3. ご用件を 4 択から選ぶ（メガネを新しく作る 約60分／メガネを調整したい 約20分／できあがりを受け取る 約20分／視力測定だけ 約30分）。ここで選ばなかったご用件は自由記述（`walk_ins.purpose_note`）に残す（LEDGER-STAFF の「フレームの相談」がこれに当たる）。
4. お客様は電話番号で探すか、「あとで登録する」を選ぶ。
5. 台帳側では入る先の枠を「ここに入ります」と点線で示す。
6. 「受付して台帳に載せる」を押す。
7. `walk_ins` に 1 行作る。**入る先の枠が決まったときは、同じ操作で `source='walkin'` の予約を 1 件起こし、`reservation_assignments` に担当と時間帯を入れる**
   （`walk_ins.reservation_id` で結ぶ。顧客未特定でよいのは `reservations.customer_id` が nullable だからである）。
   これをしないと、空き枠エンジンから見て「ここに入ります 11:30–12:30」の渡辺 由紀は空いたままで、同じ瞬間に電話予約がその枠を取れてしまう。
   枠が決まらない待ちのウォークインは予約を起こさず、台帳の最下段と来店受付ボードにだけ載せる。

**代替フロー**

- 4a. 電話番号で既存顧客が見つかれば紐づける（下4桁でも探せる）。
- 6a. 「やめる」でパネルを閉じる。

**例外フロー**

- E1. 空いている枠が無い場合でも受付は成立し、待ちとして扱う。台帳側の「ここに入ります」の点線は出さず、パネルに理由を 1 文で出す（「いまお入れできる枠がありません。お待ちの列に入れます。」）。

**事後条件**

- ウォークインが顧客未特定のまま台帳に載る。

**対応する画面**: LEDGER-WALKIN

**検証点**

- 整理番号が店舗・当日で連番になる（004 の次が 005）。
- 顧客未特定のまま受付・接客が始められる。

### IDX-RECEP-07 ウォークインの待ち時間を見せる

### IDX-RECEP-08 受付履歴を読む

| 項目 | 内容 |
|---|---|
| 主体 | 店長・受付スタッフ |
| 事前条件 | 受付の記録がある |
| トリガ | サイドバー「受付履歴」を押す |

**主フロー**

1. 絞り込みが 3 つ並ぶ（期間 8月21日〜8月27日／担当 すべて／結果 すべて）。「担当」は**接客する担当**（`reservation_assignments.target_id`）を指す。
   受けた人（`reception_sessions.actor_id`）は共有モードで個人未確認だと NULL になるので、そちらで絞ると共有端末の受付が全部漏れる。

2. 左に日付ごとの一覧が出る（「2026年8月27日（木）　46件」）。この日付は**ご来店日**で束ねる。一覧の元は「その日にご来店予定だったすべての予約 ＋ ウォークイン」で、

3. 1 件を選ぶと右に詳細が出る（お客様・時間帯・「中村 彩 が 8月20日（木）14:32 に電話で受け付け」・状態の札「成立」）。
4. 「そのあとの変更」を時系列で並べる（いつ / 何が / 誰が）。
5. 「受付のときの録音」を再生できる（再生位置と長さ 03:24 / 06:12）。

**代替フロー**

- 3a. 「予約を開く」でその予約へ移る。
- 1a. 「⌕ お客様名で探す」で名前から絞る。

**例外フロー**

- E1. 録音が無い受付では再生欄を出さない。
- E2. 条件に合う履歴が 0 件 → IDX-RECEP-09。

**事後条件**

- 表示だけ。受付履歴・録音・他店で書かれた顧客の記録は、**閲覧も `audit_events` に残す**（度数と録音は要配慮情報であるため）。

**対応する画面**: HISTORY-LIST

**検証点**

- 変更の履歴が `audit_events` から時系列で組み立てられる。
- 破棄された受付（`outcome='discarded'`）も履歴に残る。

### IDX-CHANGE-03 日時を変える

| 項目 | 内容 |
|---|---|
| 主体 | 受付スタッフ |
| 事前条件 | 対象の予約が決まっている |
| トリガ | 「日時を変える」を押す |

**主フロー**

1. 左に「いまのご予約」を固定して置く（日時 / お客様 / ご用件と所要 / 担当と場所）。
2. 右に日付 7 日ぶんを並べる（定休日は押せない）。
3. 「60分の枠が取れる時刻だけを出しています。」に従い、所要時間で絞った時刻を並べる（受付できます／選択中／満席）。
4. 選ぶと結果を 1 文で返す（「14:00 から60分、佐藤 美咲／視力測定機 A を確保します。」）。
5. 「変更内容を確認する」で差分の確認へ進む。
6. ヘッダーに対象の予約番号を出し続ける（「予約の変更　EY-2608-0142」）。

**代替フロー**

- 2a. 「‹」で検索へ戻る。
- 4a. 担当・設備が現状のままでは取れない時刻も候補として出し、札に理由を添える（「担当を変えると取れます」）。押すと確保できる組み合わせ（担当・設備）を 1 つ提示し、選ぶと差分の確認へ進む。

**例外フロー**

- E1. 60分の枠が 1 件も無い日は時刻をすべて満席にする。
- E2. 変更中に他端末が同じ予約を保存した → IDX-CHANGE-08。

**事後条件**

- 新しい日時が仮に決まる。予約はまだ書き換えない。

**対応する画面**: CHANGE-DATETIME

**検証点**

- 元の予約が枠から外れた前提で空き枠を計算する（自分自身と競合しない）。
- 録音が動いている（変更の受付も録音する）。

### IDX-CHANGE-04 変更内容の差分を確認する

| 項目 | 内容 |
|---|---|
| 主体 | 受付スタッフ |
| 事前条件 | 新しい日時が決まっている |
| トリガ | 「変更内容を確認する」を押す |

**主フロー**

1. 「この内容に変更します」「変わる行だけ色を付けています」を出す。
2. 項目 / 変更前 / 変更後 の 3 列で並べる。
3. 変わる行だけ緑地にし、変更後に札「変更」を付ける（お日にちとお時間、場所）。
4. 変わらない行は薄字で「同じ」と示す（ご用件、担当）。
5. 右にお客様へ読み上げる文を置く。CHANGE-DIFF は確定**前**の画面なので完了形では書かず、BOOK-05-CONFIRM と同じ「読み返して同意を取る」形にする（「8月27日木曜日、午後2時へお時間を変更いたします。担当は佐藤 美咲、所要時間は約60分です。こちらでお間違いないでしょうか？」）。読み上げる文は「です・ます」で書き、丁重語（「でございます」）は使わない。モックの「変更いたしました」「でございます」は採らない（§13）。
6. 通知の有無を明示する（「お電話でのご予約のため、メールは送りません。」）。
7. 「変更を確定する」で確定する。

**代替フロー**

- 7a. 「戻って直す」で日時の選び直しへ戻る。

**例外フロー**

- E1. 確定の瞬間に枠が埋まっていた場合は BOOK-CONFLICT と同じ型で出す（①「まだ変更していません。伺った内容は残っています。」と先に言う ②何が埋まったかを差分で出す ③同じ担当で案内できる時刻を 3 つと、担当だけ入れ替える案を 1 つ並べる）。選び直すとその場で押さえ直す。
- E2. 他端末が先に保存していた → IDX-CHANGE-08。

**事後条件**

- 確定するまで予約は書き換わらない。

**対応する画面**: CHANGE-DIFF

**検証点**

- 差分の行が実際に変わる列と一致する。
- 出どころが Web 予約のときは、店頭で変更しても**お客様へメールを送る**（お客様の手元の控えと突き合わせられなくなるため）。通知の 1 行も「Webでのご予約のため、変更をメールでお知らせします。」に変わる。店内予約（お電話・店頭・ウォークイン）ではメールを送らない。

### IDX-CHANGE-05 変更を確定して伝えることを読む

| 項目 | 内容 |
|---|---|
| 主体 | 受付スタッフ |
| 事前条件 | 差分を確認した |
| トリガ | 「変更を確定する」を押す |

**主フロー**

1. `reservations` を更新し、`version` を 1 つ上げる。
2. 予約番号は変えない（「予約番号は変わりません」）。
3. 完了画面に変更後のご予約（日時・所要・変更前の時刻・お客様・担当と場所）を出す。
4. 右に「お客様にお伝えすること」を並べる。
5. 誰がどの端末で操作したかを残す（「この操作は受付履歴に残ります（銀座店 レジ横iPad・11:12　操作者 中村 彩）。」）。
6. 「台帳で見る」または「トップへ戻る」で終える。

**代替フロー**

- なし。

**例外フロー**

- E1. 通知の送信に失敗しても変更は成立させ、失敗はお知らせに残す（best-effort）。

**事後条件**

- 台帳・受付履歴・分析に変更が反映される。`audit_events` に前後の値が残る。

**対応する画面**: CHANGE-DONE

**検証点**

- 予約番号が変わらない。
- `version` が上がり、古い version での上書きが弾かれる。

### IDX-CHANGE-06 担当・場所を変える

| 項目 | 内容 |
|---|---|
| 主体 | 受付スタッフ |
| 事前条件 | 対象の予約が決まっている |
| トリガ | 「担当・場所を変える」を押す |

**主フロー**

1. 日時を保ったまま、担当軸・設備軸のタイムテーブルで置き直す（予約フロー工程 3 と同じ形）。
2. 重なりの警告と候補の出し方は IDX-BOOK-04 / IDX-BOOK-05 に合わせる。
3. 差分の確認（IDX-CHANGE-04）へ進む。

**代替フロー**

- 1a. 「担当はあとで決める」で未定に戻す。

**例外フロー**

- E1. 専用の画面は起こさず、**BOOK-03-SLOT-STAFF / BOOK-03b-SLOT-RESOURCE をそのまま再利用する**（選ぶものが同じで、覚え直しが要らない）。ツールバーの対象と見出しだけを「予約の変更　EY-2608-0142」に差し替える。

**事後条件**

- `reservation_assignments` が置き換わる。日時は変わらない。

**対応する画面**: 専用モックなし（CHANGE-SEARCH の出口／BOOK-03-SLOT-STAFF・BOOK-03b-SLOT-RESOURCE を流用する想定）

**検証点**

- 日時を変えずに担当だけを変えたとき、差分表の「担当」行だけが色付く。

### IDX-CHANGE-07 予約を取り消す

| 項目 | 内容 |
|---|---|
| 主体 | 受付スタッフ |
| 事前条件 | 対象の予約が決まっている |
| トリガ | 「取り消す」を押す |

**主フロー**

1. 見出しで、まだ取り消していないことを明示する（「この予約を取り消します」「まだ取り消していません」）。
2. 対象の予約を 1 枚のカードで出す（日時と所要 / お客様 / ご用件 / 担当と場所）。
3. 取り消したあとに何が起きるかを先に読ませる（「取り消すと、この枠はすぐほかのお客様にご案内できる状態になります。」）。
4. 理由を 4 択で選ばせる（お客様のご都合／店舗の都合／予約の重複／ご来店がなかった）。「受付履歴と分析に残ります」と添える。
5. 既定の操作（左端）は「取り消さずに戻る」。危険な操作（右端）が「この予約を取り消す」。
6. 取り消すと `status='cancelled'`、`cancelled_at` と `cancel_reason` を残す。

**代替フロー**

- 5a. 「取り消さずに戻る」で検索へ戻る。

**例外フロー**

- E1. 理由は**必須**である。4 択のどれも選んでいない状態から始め（既定で選択済みにしない）、選ぶまで「この予約を取り消す」を押せない。既定で「お客様のご都合」が入っていると、店舗都合の取消・重複の取消が押し間違いでお客様都合として残り、分析の内訳が狂うためである。
- E2. 取り消した予約は元に戻せない（「取り消した予約は元に戻せません。」）。

**事後条件**

- 枠が解放され、受付履歴と分析に取り消しとして残る。

**対応する画面**: CHANGE-CANCEL

**検証点**

- 既定のボタンが「取り消さずに戻る」で、危険操作と位置が入れ替わっている。
- 「ご来店がなかった」を選んだ取り消しだけが `status='no_show'` になり、残る 3 つ（お客様のご都合／店舗の都合／予約の重複）は `status='cancelled'` になる。理由そのものは `cancel_reason` に残し、分析の取消の内訳（IDX-ANA-06）はこの列で分ける。受付履歴の「結果」には「成立 / 取消 / ご来店なし」の 3 語を出す。

### IDX-CHANGE-08 ほかの端末で先に保存されていた

| 項目 | 内容 |
|---|---|
| 主体 | 受付スタッフ |
| 事前条件 | 予約を直している最中に、別端末が同じ予約を保存した |
| トリガ | 保存しようとした |

**主フロー**

1. 消えていないことを先に言う（「同じご予約を、ほかの端末でも直していました」「受付iPad の 中村 彩 が 11:06 に保存しました。選ぶまで、どちらの内容も書き換わりません。」）。
2. 左に相手の内容（保存済み）、右に自分の内容（未保存）を並べる。
3. 変わった項目だけ新旧を上下に出し、変わらない項目は薄字にする。
4. 「中村 彩 の内容を残す」または「あなたの内容で上書きする」を選ぶ。
5. 選んだ内容で保存し、`version` を上げる。

**代替フロー**

- 4a. 「1項目ずつ選ぶ」を押すと、同じ画面の差分の各行にラジオ（相手の内容／自分の内容）が出る。既定はどちらも選ばれておらず、全行を選ぶまで保存を押せない。画面を移らないので EX-CONFLICT の型（①失っていないものを先に言う ②差分 ③次の一手）を保ったまま解決できる。
- 4b. 「やめて台帳に戻る」で自分の編集を捨てる。

**例外フロー**

- E1. 選んでいる間にさらに 3 台目が保存した場合は、同じ画面を最新の内容で出し直す。

**事後条件**

- どちらか一方の内容だけが残り、両方の内容が失われない。

**対応する画面**: EX-CONFLICT

**検証点**

- 競合検知は `reservations.version` の条件付き更新で行う。
- 選ぶまで DB が書き換わらない。

## 8. REC — 受付録音とお知らせ

録音は受付の全工程で見せる。予約フローでは下の帯の右に、確認画面と受付・変更の画面では右下の常駐表示に置く。
録音の許可だけを説明する画面は作らない。

### IDX-REC-01 受付の開始で録音を始める

| 項目 | 内容 |
|---|---|
| 主体 | システム（受付スタッフの操作が起点） |
| 事前条件 | 端末にマイクがある（許可はこの UC の中で求める） |
| トリガ | 予約フロー・来店受付・変更フローを**始める操作を押した**とき（「新しい予約を取る」「ご来店を受け付ける」「変更する」） |

**主フロー**

1. 受付を始める操作を**押したその手のイベントの中で**マイクの許可を求める。ルート遷移の副作用として求めない（Safari はユーザーの操作を起点にしない要求をそのまま断る）。
2. 許可を尋ねている間、録音の表示を「マイクの許可を確かめています」にする。許可の理由を説明するだけの画面は作らないので、理由はこの録音の表示がその場で担う。
3. 受付セッション（`reception_sessions`）を作る。端末 id と操作者 id を残す。
4. 録音を始め、`recordings` を `state='recording'` で作る。
5. 画面に録音中の表示と経過時間を出す（帯では「録音中 01:08」、常駐表示では「録音しています 00:42」）。

**代替フロー**

- 3a. 共有端末では操作者 id が置き場所（端末）になる。

**例外フロー**

- E1. マイクが使えない → IDX-REC-03。
- E2. 許可を尋ねたまま応答が無く閉じられた場合も、断られたのと同じ扱いで IDX-REC-03 へ移る。受付の工程はそのまま進める。

**事後条件**

- 受付セッションと録音の行が 1 件ずつできる。

**対応する画面**: BOOK-01-DATETIME / RECEPTION-CHECKIN / CHANGE-DATETIME

**検証点**

- 受付セッションが端末と操作者を必ず持つ。
- 録音中の表示が色だけでなく文字でも分かる。
- マイクの許可の要求が、ボタンの押下を処理する中から出る（画面の遷移そのものでは出ない）。
- 許可を尋ねている間の「マイクの許可を確かめています」が読み上げにも届く。

### IDX-REC-02 録音したまま工程を進める

| 項目 | 内容 |
|---|---|
| 主体 | 受付スタッフ |
| 事前条件 | 録音中 |
| トリガ | 工程を進める |

**主フロー**

1. 工程が変わっても録音は続く。
2. 経過時間は工程をまたいで単調に増える。
3. 確認の工程では帯から右下の常駐表示へ置き換える。

**代替フロー**

- 3a. 変更フローでは工程の帯（日時を変える）と常駐表示（差分の確認）で同じ扱いにする。

**例外フロー**

- E1. 途中でマイクが切られた場合は IDX-REC-03 の状態へ移り、受付は続けられる。

**事後条件**

- 1 受付につき録音が 1 本になる。

**対応する画面**: BOOK-01〜05 / CHANGE-DATETIME / CHANGE-DIFF

**検証点**

- 工程を戻っても録音が分割されない。
- 経過時間の表示が実時刻ではなく録音開始からの差で出る（時刻は注入する）。

### IDX-REC-03 マイクが使えない

| 項目 | 内容 |
|---|---|
| 主体 | 受付スタッフ |
| 事前条件 | マイクの許可が下りていない（端末またはブラウザの設定で切られている、あるいはこの端末で断られた） |
| トリガ | 録音を始めようとした |

**主フロー**

1. できないのは録音だけだと言い切る（「マイクが使えないため、録音できません」「ご予約の受付は、このまま最後まで続けられます。お客様をお待たせせずに、そのまま伺ってください。」）。
2. いまも使えることを 3 行で出す（予約を取る・変える・取り消す／ここまで伺った内容／手書きメモ）。
3. 右に直し方を 3 手順で出す（設定を開く → EYEX予約 を選ぶ → マイクをオンにする）。**この 3 手順が成り立つのは、業務画面を「ホーム画面に追加」した Web アプリとして配った場合だけ**である（iPadOS 17+ はそのとき「設定 > アプリ」に「EYEX予約」が並ぶ）。Safari のタブのまま開くと iPadOS の「設定」に「EYEX予約」の項目は無く、許可はアドレスバーの「ぁあ」→ Web サイトの設定 → マイク、または 設定 > Safari > マイク にある。したがって**この 3 行の文言は配り方に従属する**。①（ホーム画面に追加した Web アプリとして配る）として作り、モックの 3 手順の文言をそのまま使う。 `[要確認: Q-05 — いまの前提で進める]`
4. 右下の録音表示を灰色にし「録音していません」「--:--」を出す。
5. 「録音せずに続ける」で受付を続ける。

**代替フロー**

- 5a. 「直したので、もう一度確かめる」で許可を取り直す。同じページ読み込みの中で一度断られた許可は、呼び直してもダイアログが出ないまま即座に断られるので、この操作は**画面を読み込み直してから判定し直す**経路にする。読み込み直しで工程の入力を失わないよう、**予約フローの下書きは `reception_sessions` に持たせる**。端末に残すのは受付セッション id と選んだ id だけで、お客様の名前・電話番号そのものは端末に残さない。読み込み直したら受付セッション id で引き直し、同じ工程から続ける（iPadOS の Safari は裏に回ったタブを捨てるので、端末のメモリだけでは伺った内容が丸ごと消える）。
- 5b. 「受付をやめる」で受付を破棄する（IDX-REC-09）。

**例外フロー**

- E1. 録音が無いことの結果を明示する（「できないのは録音だけです。この受付をあとから聞き直すことはできません。」）。

**事後条件**

- 受付は成立しうる。録音の行は作らない。

**対応する画面**: EX-MIC-DENIED

**検証点**

- 録音なしでも予約が確定できる。
- 録音の有無が受付履歴で区別できる。
- 「直したので、もう一度確かめる」が、同じページ読み込みのまま許可を呼び直すだけで終わらない。

### IDX-REC-04 録音を保管庫へ送る

| 項目 | 内容 |
|---|---|
| 主体 | システム |
| 事前条件 | 録音が終わった |
| トリガ | 予約の確定、または受付の終了 |

**主フロー**

1. 録音を `state='uploading'` にする。
2. R2（`RECORDINGS`）へ非公開で置く。ダウンロード URL は発行しない。
3. 成功したら `state='stored'` にし、`retain_until` を決める。
4. 予約が成立していれば録音完了から最低 30日、破棄された受付なら録音終了から最低 24時間を保持する。

**代替フロー**

- 3a. 破棄された受付でも録音は残す（`reception_sessions.outcome='discarded'`）。

**例外フロー**

- E1. 送信に失敗 → IDX-REC-05。
- E2. 最低保持期間を過ぎる前の削除要求は拒否する。
- E3. `legal_hold` が立っている録音は保持期限を過ぎても消さない。

**事後条件**

- 録音の実体が R2 に、状態が D1 にある。

**対応する画面**: なし（背景処理）

**検証点**

- 保持期限の境界（成立予約は 30日ちょうどは削除不可、+1秒で削除可）。
- 破棄受付の 24時間ちょうどと +1秒。
- ダウンロード URL を返す API が存在しない。

### IDX-REC-05 録音の保存に失敗した

| 項目 | 内容 |
|---|---|
| 主体 | 受付スタッフ（結果として画面に出る） |
| 事前条件 | 予約は確定している |
| トリガ | R2 への送信に失敗した |

**主フロー**

1. 成功を先に言う（「ご予約は確定しています」「予約番号 EY-2608-0187　台帳にも入っています」）。
2. 失敗したのは録音だけだと言う（「保存できなかったのは、この受付の録音だけです」「店内の通信が弱く、録音（03:24）をお店の保管庫へ送れませんでした。録音は、この iPad の中に残っています。」）。
3. 次の自動再送の時刻を出す（「11:20 に自動でもう一度送ります。操作は要りません。」）。
4. 右に確定したご予約の内容を出す。
5. 右下の表示を「録音は端末に保管中」にする。未送信の音声は端末の **IndexedDB** に置く（送信に成功したら即削除。**端末セッションが失効しても消さず**、次に同じ端末で有効なセッションが立ったときに自動で再送する。再生・書き出しの操作は出さない。24 時間送れないままなら端末から消す ＝ E2）。
   顧客の氏名・電話番号・メール・度数はここに書かない。EX-UPLOAD-FAILED の「11:20 に自動でもう一度送ります。操作は要りません。」は、
   端末のメモリだけに置くと staff が別のアプリを開いた瞬間（iPadOS の Safari が裏のタブを捨てる）に嘘になるため、永続領域が要る。
6. 「このまま続ける」で業務へ戻る。

**代替フロー**

- 6a. 「もう一度送る」で即時に再送する。

**例外フロー**

- E1. 端末は **5 分の固定間隔**で再送し、**3 回続けて失敗したら**「対応が必要」のお知らせに上げる（IDX-REC-06）。EX-UPLOAD-FAILED は 11:15 表示で「11:20 に自動でもう一度送ります。」（＝5 分）、ALERTS が「録音の保存に3回失敗しました」と書いている。通信の再接続（IDX-LEDGER-09）は 1 分間隔で、これとは別に持つ。
- E2. 端末に残した録音は、**端末セッションが失効しても消さない**（自動ロック 120秒 や交代のたびに消えると、「11:20 に自動でもう一度送ります。操作は要りません。」が守れない）。次に**同じ端末で**有効なセッションが立ったときに自動で再送し、その間は再生も書き出しもさせない。**24 時間送れないままなら**「対応が必要」のお知らせに上げ、端末側は `state='failed'` として IndexedDB から消す（共有 iPad に接客の音声を居残らせない）。サーバ側の最低保持期間（成立予約は 30日 ほか）は R2 に届いた録音の話で、端末に残る間は別に数える。

**事後条件**

- 予約は成立したまま。録音は `state='failed'` で `upload_attempts` が増える。

**対応する画面**: EX-UPLOAD-FAILED

**検証点**

- 録音の失敗が予約の成立を巻き戻さない。
- 失敗した事実（状態・試行回数）が残る。

### IDX-REC-06 お知らせから録音を送り直す

| 項目 | 内容 |
|---|---|
| 主体 | 受付スタッフ・店長 |
| 事前条件 | 録音の保存に繰り返し失敗している |
| トリガ | appbar 右の「お知らせ」ボタン（バッジ付き）。ALERTS を開いている間はサイドバーにも「お知らせ 3」の項目が出る |

**主フロー**

1. お知らせの一覧が種類別に並ぶ（すべて 3／アラート（対応が必要） 1／お知らせ 2／対応済み 12）。

   記事には**どの端末に残っているか**（`terminals.name`）を必ず入れる。音声の実体は端末側にあり、「もう一度送る」が成功するのはその録音を持っている端末だけで、
   別の端末（レジ横 iPad で失敗した録音を受付 iPad）から押しても直らない。サーバから再送する経路は無い。
4. 「もう一度送る」を押すと再送する。
5. 成功したら記事を対応済みにする。

**代替フロー**

- 1a. Web予約の確認待ち（「Web予約が2件、確認待ちです」「本日中に確認しないと自動で取り消されます。」）から「台帳で確認する」で台帳の確認待ちへ移る。

**例外フロー**

- E1. 共有端末では録音の保全に本人確認が要る（IDX-TERM-08）。

**事後条件**

- 成功時は録音が `stored` になり、記事が対応済みに移る。

**対応する画面**: ALERTS

**検証点**

- 種類ごとの件数が記事の数と一致する（アラート 1 + お知らせ 2 = すべて 3）。
- 同じ失敗で記事を増やさない（1 録音につき 1 記事）。

## 10. ANA — 分析

分析はタブで指標を切り替える。タブは 8 つ（トップ／予約数／予約の入口／取り消し／来店回数／担当者／ご来店の目的／お待ち時間）。

### IDX-TERM-07 共有端末がお客様の情報を隠す

| 事前条件 | 共有モードで業務中 |

**主フロー**

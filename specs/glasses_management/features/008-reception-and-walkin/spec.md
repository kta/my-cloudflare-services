# 008-reception-and-walkin: 来店受付とウォークイン

- サービス: `glasses_management`
- ステータス: Draft

## 1. WHAT / WHY

**概要**: お客様が店に着いてから帰るまでを扱う。ご予約のお客様を受け付け、予約なしのお客様を
お名前も伺わないうちから受け付け、店内のどの工程にいるかを 1 枚の盤面で共有し、その日の受付を
あとから時系列で追えるようにする。

**ユーザーストーリー**:

- US-RECEP-01: 受付スタッフとして、伝え忘れると後戻りできないことを取りこぼさないために、ご予約のお客様がお着きになったときに、名前と伝え忘れやすいことを 1 画面で確かめてから受け付けたい。
- US-RECEP-02: 受付スタッフとして、お客様を入口に立たせたままお待たせしないために、予約なしで来られたお客様を、お名前も電話番号も伺わないうちから受け付けて接客を始めたい。
- US-RECEP-03: 受付スタッフとして、そのご来店を来店回数と分析に正しく数えるために、あとからお客様が分かったときに、その来店を今までのお客様か新しく登録したお客様へ結びつけたい。
- US-RECEP-04: フロアのスタッフとして、手の空いた者がすぐ次の一手に入れるように、いま誰がどの工程にいて、誰をお待たせしているかを見渡したい。
- US-RECEP-05: 店長として、お客様からのお問い合わせにその場で答えられるように、その日の受付で誰が何をしたかを時系列で追い、絞り込みで 0 件になっても行き止まりにならないでほしい。
- US-RECEP-06: 店長として、取り消しとご来店がなかったものを分けて数えられるように、ご来店・取り消し・ご来店がなかった、のどれだったかを残したい。
- US-RECEP-07: フロアのスタッフとして、閉店のときに盤面へ誰も残らないように、接客を終えたお客様と、お待ちのまま帰られたお客様を、その日のうちに盤面から降ろしたい。

**ユースケース**:

- UC-RECEP-01: 受付スタッフは、ご予約のお客様を受け付け、予定時刻との差を確かめられる。
- UC-RECEP-02: 受付スタッフは、受け付ける前に確かめることを 1 行ずつ消し込める。
- UC-RECEP-03: 受付スタッフは、お客様にお待ちいただき、その待ちを盤面に載せられる。
- UC-RECEP-04: フロアのスタッフは、ご来店中のお客様がどの工程にいるかを 1 枚で見られる。
- UC-RECEP-05: 担当スタッフは、工程を進め、担当と設備と経過を書き換えられる。
- UC-RECEP-06: 受付スタッフは、予約なしのお客様を、お客様を特定しないまま受け付けられる。
- UC-RECEP-07: 受付スタッフは、いまお待ちの人数と 1 人ずつの経過時間を見られる。
- UC-RECEP-08: 受付スタッフは、受け付けたあとのウォークインを今までのお客様へ結びつけられる。
- UC-RECEP-09: 受付スタッフは、受け付けたあとのウォークインから新しいお客様を登録して結びつけられる。
- UC-RECEP-10: 受付スタッフは、お客様を特定しないまま退店した来店を、あとから受付履歴で探せる。
- UC-RECEP-11: 受付スタッフは、来店の結果（ご来店・取り消し・ご来店がなかった）を残せる。
- UC-RECEP-12: 店長は、1 件の受付について、受け付けた人とそのあとの変更を時系列で読める。
- UC-RECEP-13: 店長は、絞り込みが 0 件になったとき、条件を 1 つ緩めたときの件数を見て開き直せる。
- UC-RECEP-14: 担当スタッフは、接客を終えたお客様を退店として記録し、ご来店中から外せる。
- UC-RECEP-15: 受付スタッフは、お待ちのまま帰られたお客様を待ちの列から外し、その事実を記録に残せる。
- UC-RECEP-16: 店長は、受付履歴をお客様のお名前で絞り込み、選んだ 1 件からそのご予約を開ける。

**受け入れ基準**:

- AC-RECEP-03: Given 注意ごとが 1 件あるお客様の来店受付の画面を開いている, When 「受け付ける前に確かめること」を見る, Then その注意ごとの行に「要確認」の札が付き、確かめ済みの行と未確認の行が札と枠で見分けられる。

**スコープ外**:

- 受付中の録音・再生・保存の失敗（`010-recording`）。受付履歴の詳細に録音の欄が出るのはそちら。
- 予約の変更・取り消しの操作面と差分の確認（`009-change-and-cancel`）。
- お客様の登録・検索・統合・手書き（`007-customer-records`）。ここは結びつけるところだけ。
- 台帳そのものの描画・空き枠の計算・帯の移動（`005-availability-and-ledger`）。
- 待ち時間の日次集計と目安の線（`012-analytics`）。
- 共有端末・個人モード・PIN（`013-terminals-and-audit`）。受付の記録には端末を空のまま残す。
- お知らせ一覧への掲載（`alerts` の表は `010-recording` で作り、一覧（ALERTS）の画面は `013-terminals-and-audit`）。このフェーズの警告は画面の中だけに出す。

**決めたこと**（第2巡の検査で決着させた。根拠は承認済みモックと決定ブリーフ）:

- 「受け付ける前に確かめること」は全部消さなくても受け付けられる。必須の行は設けない（お客様をお待たせしないことを優先する）。消し込みの結果（確かめた行と確かめなかった行）は受付の記録に残し、「確かめずに受けた」ことがあとから分かるようにする。
- 工程を進める操作の入口は、その行の「次にやること」の欄そのものである。担当以外のスタッフも進められる（受付は手の空いた者が行う）。
- ウォークインからお客様を新しく登録する導線は受付パネルに置かない（受付を止めないため）。受け付けたあとに来店受付ボードのその行を開いて登録する。受付パネルが持つのは「電話番号で探す（下4桁でも探せます）」と「あとで登録する」の 2 つだけである。
- 担当が勤務に入っていない・設備が点検で止まっているときは、「次にやること」の欄の中に「本日はお休みです。担当を決め直してください。」「視力測定機 A は点検で止まっています。」を注意として出す。色だけに頼らず必ず文字を添える。
- 「ご来店がなかった」は来店受付ボードからも残せる（気づくのは受付の現場であるため）。予約の取り消しの画面にも同じ操作を置く。
- ご来店中が 0 名のとき・お待ちが 0 名のときは、HISTORY-EMPTY / EX-EMPTY-SEARCH と同じ型（見出し 1 行＋なぜ空かの 1 行＋次の一手 1 つ）で出す。行き止まりにしない。
- 受付履歴を読んだこと自体も監査に残す（度数と録音へ届く経路であるため）。
- 受付履歴の「結果」の語は「成立」「取消」「ご来店なし」の 3 つ。取り消しの理由は必須で、「ご来店がなかった」を選んだものだけが `no_show`、それ以外は `cancelled` になる。
- 「お待たせ中」に変わる閾値は 15 分（LEDGER-WALKIN の受付パネルの「目安 15分」と同じ値。モックの 6 分は通常、18 分はお待たせ中で、その間にある画面上の値は 15 分だけである）。受付パネルの「目安」は待ち人数の掛け算では出さず、空き枠エンジンが返す「選んだご用件を受けられる担当が次に空く時刻 − 現在時刻」を 5 分単位に丸めて出す。お客様に口で伝える約束になるため、担当の空きを見ない数字は出さない。
- 来店受付ボードは台帳と同じ `role="grid"`（矢印で枠を移れる格子）に揃える。工程を進める操作は欄の中に置き、キーボードだけでたどり着ける。台帳と別の型にすると覚え直しになる。
- 受付の途中で別のアプリへ切り替えて戻ったときは、`reception_sessions` に持たせた下書きから引き直す。端末にはお客様の名前・電話番号そのものを残さず、受付セッションの id と選んだ id だけを持ち帰る。

ここでは新設しない（同じ表を 2 つの migration が作ると、あとから走ったほうの `db:generate` が既存表の再作成を出す）。
`audit_events` と `idempotency_records` も `006-booking-flow` で作った表を読み書きする。
`visit_events` は追記だけで、訂正は打ち消しの行を足す。
`reservations.status` は既存のままで、`arrived` と `no_show` への遷移をこのフェーズで初めて書く。
端末の表は `013-terminals-and-audit` で作るので、受付の記録と監査の記録の端末欄は空のまま置く。
待ち時間・お待たせの判定は保存せず、受付時刻と応答に含めるサーバの現在時刻の差で毎回出す。
「いまお待ち N名」は `visit_date = 本日（JST）` かつ `status='waiting'` の件数で数え、index にも `visit_date` を入れる
（日付の条件を落とすと、昨日帰られたお客様が今朝の待ち行列に残り、待ち時間の目安まで狂う）。
`walk_ins.status` は「接客を終えて退店した」と「お待ちのまま帰られた」を別の値で持つ。前者を数え落とすと来店回数が、
後者を数え落とすとお待ち時間の中央値が、いずれも実態より良い側へずれる。
受付履歴の一覧は新しい順にカーソルで読み足す（`OFFSET` は使わない）。

ウォークインの受付は `reservations`（`source='walkin'`）/ `reservation_purposes` / `reservation_assignments` /
`reservation_slot_locks` / `walk_ins` を 1 つの `db.batch()` で書く（このうち `reservation_slot_locks` を含む予約側の 4 表は
`005-availability-and-ledger` が作る。ここでは書くだけで新設しない）。枠の占有は一意 index に頼らず、
**上限つきの条件付き INSERT** で取る:

```sql
INSERT INTO reservation_slot_locks (...)
SELECT ?1, ?2, ?3, ?4, ?5, ?6, ?7, ?8
WHERE (SELECT COUNT(*) FROM reservation_slot_locks
       WHERE organization_id=?2 AND store_id=?3 AND kind=?5 AND target_key=?6 AND slot_start=?7) < ?9
```

`?9` に入れる上限は、担当未定（`target_key='unassigned'`）なら `store_slot_rules.max_parallel`、
担当ありなら `staff.max_parallel_reservations`、設備なら `equipment.capacity` である。取れたかどうかは `meta.changes` で読む。
一意 index にすると「1 枠 1 件」しか表現できず、**担当を決めずに受け付ける 2 人目のウォークインが、
店に余裕があっても 409 で落ちる**（目の前のお客様を受け付けられない画面ができる）。
枠を取る文より後ろの文は、すべて `WHERE EXISTS (SELECT 1 FROM reservation_slot_locks WHERE reservation_id = ?)` で
ガードする（ガードしないと、枠が取れていないのに予約と受付だけが書かれる）。

D1 の UNIQUE 違反には構造化されたエラーコードが無く、判別できるのは
`D1_ERROR: UNIQUE constraint failed: <表>.<列>` というメッセージだけである。表名の取り出しは
`src/worker/db/constraint.ts` の `constraintTable(err)` 1 か所に閉じ（この関数だけが D1 のメッセージ書式に依存する）、
その unit テストを必須にする（書式が変わったら 409 が 500 に化けるため、壊れたことを検知できる場所を 1 つ持つ）。
受付の 1 バッチには整理番号（`walk_ins_org_store_date_ticket_idx`）・予約番号（`reservations_org_code_idx`）・
冪等キー（`idempotency_records` の PK）の 3 つの一意制約が同居し、どれで落ちたかで返すものが違う。
整理番号と予約番号の衝突は +1 して最大 5 回まで再試行し、そのあいだ `idempotency_records` の `in_progress` の行は消さない
（消すと再試行が同じキーで `done` を書けなくなる）。`in_progress` を消すのは、再試行で解けない失敗のときだけである。

**却下した代替案**:

- ウォークインを予約の 1 種として同じ表に持つ: お客様も時間帯も決まらないうちに枠を押さえることになるため却下。別の表に分ける。
- 待ち時間を列に持って定期的に書き換える: 書き込みが増え、画面ごとに食い違うため却下。差で毎回出す。
- 工程を「いまの工程」1 列の上書きで持つ: 経緯が消えて分析の元にならないため却下。追記だけの記録にする。
- 0 件のときの緩和候補を別の呼び出しで取りに行く: 往復が増えて 0 件の画面が遅れるため却下。0 件の応答に同梱する。
- 経過時間を端末の時計で描く: 端末ごとに待ち時間がずれるため却下。サーバの現在時刻を応答に含めて描く。
- 整理番号をクライアントから受け取る: 同時受付で重複するため却下。サーバが店舗・当日ごとに採番する。

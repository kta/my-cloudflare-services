# 010-recording: 受付の録音

- サービス: `glasses_management`
- ステータス: Draft

## 1. WHAT / WHY

**概要**: 受付中の音を iPad のマイクで録り、非公開の保管庫へ置き、予約詳細・予約検索・受付履歴から聞けるようにする。
録音が動いていることを受付の最初から復唱の終わりまで見せ、マイクが使えないときと保存に失敗したときは
「予約は成立している」ことと切り分けて知らせる。成立予約は最低30日、破棄受付は最低24時間残し、それより前には消せない。

**ユーザーストーリー**:

- US-REC-01: 受付スタッフとして、あとで言った言わないを確かめられるように、受付のあいだ録音が動いていることを常に見ていたい。
- US-REC-02: 受付スタッフとして、お客様をお待たせしないために、マイクが使えないときも受付を最後まで続けたい。
- US-REC-03: 受付スタッフとして、取れたのか取れていないのか迷わないために、録音の保存が失敗しても予約の成立とは切り分けて知らせてほしい。
- US-REC-04: 店長として、聞き直しの求めに応えるために、予約と受付履歴からその受付の録音をその場で聞きたい。
- US-REC-05: 運営者として、お客様の声を守るために、録音を持ち出せない場所に置き、決めた期間より前には消せないようにしたい。

**ユースケース**:

- UC-REC-01: 受付スタッフは、受付を始めると録音が始まり、経過時間つきの録音中の表示を見ることができる。
- UC-REC-02: 受付スタッフは、工程を進めても戻しても、1回の受付につき1本の録音を切らずに続けることができる。
- UC-REC-03: 受付スタッフは、マイクが使えないとき、録音できない理由と直し方を見たうえで、録音せずに受付を続けることができる。
- UC-REC-04: システムは、終わった録音を非公開の保管庫へ送り、成立予約か破棄受付かで最低保持期限を決めることができる。
- UC-REC-05: 受付スタッフは、録音の保存に失敗しても、予約が成立していることを先に知って業務へ戻ることができる。
- UC-REC-06: 受付スタッフは、保存に失敗した録音をその場で送り直すことができる。
- UC-REC-07: 店長は、予約詳細・予約検索・受付履歴から受付の録音を聞くことができる。
- UC-REC-08: システムは、最低保持期限を過ぎ、保全されていない録音の実体を定期の片づけで消すことができる。
- UC-REC-09: 受付スタッフは、受付をやめても、受付の記録と録音を残すことができる。

**受け入れ基準**:

- AC-REC-01: Given 予約フローの1工程目で録音が始まっている, When 復唱の工程まで進める, Then 下の帯の「録音中」が右下の常駐表示「録音中」に移り、経過時間は工程をまたいで減らずに増え続ける。
- AC-REC-02: Given 受付の途中で工程を1つ戻した, When そのまま予約を確定する, Then その受付の録音は1本だけで、受付履歴の「受付のときの録音」にも1件だけ出る。
- AC-REC-03: Given マイクが許可されていない, When 予約フローで受付を始める, Then 「マイクが使えないため、録音できません」「ご予約の受付は、このまま最後まで続けられます。」が出て、右に「直し方」として、この端末の配り方（`design/09-open-questions.md` の Q-05。いまの前提は「ホーム画面に追加した Web アプリ」）に合った手順が番号つきで並ぶ。
- AC-REC-04: Given マイクが使えない面が出ている, When 「録音せずに続ける」を押す, Then ここまで伺った日時とお客様を保ったまま同じ受付の続きへ戻り、許可を説明するだけの別画面は挟まらない。
- AC-REC-05: Given 復唱の工程まで来ていて録音が途中で止まった, When 確定を押す前の画面を見る, Then 右下の常駐表示が「録音していません」「--:--」に変わり、確定の操作はそのまま押せる。
- AC-REC-06: Given 復唱を終えて予約を確定したが録音の保存に失敗した, When 完了の面が出る, Then 先に「ご予約は確定しています」と予約番号が出て、そのあとに「保存できなかったのは、この受付の録音だけです」と次に自動で送り直す時刻が出る。
- AC-REC-07: Given 録音の保存に失敗した予約がある, When その日時で予約台帳を開いて予約詳細を出す, Then 予約は台帳に載っており、「録音を聞く」の導線は出ない。
- AC-REC-08: Given 録音の保存に失敗した面が出ている, When 「もう一度送る」を押して送信が成功する, Then 右下の「録音は端末に保管中」が消え、その予約の詳細に「録音を聞く」が出る。
- AC-REC-09: Given 保存済みの録音がある予約を台帳で開いている, When 「● 録音を聞く　03:12」を押す, Then その場で再生が始まり、画面にも操作の結果にも保管庫のURLとダウンロードの導線は出ない。
- AC-REC-10: Given 受付履歴で1件を選んでいる, When 「受付のときの録音」の「再生する」を押す, Then 再生位置のバーと「03:24 / 06:12」が進む。
- AC-REC-11: Given 成立した予約の録音が保存されてから30日ちょうど, When その録音を消そうとする, Then 消せないことといつから消せるかが返り、30日と1秒を過ぎると消せる。
- AC-REC-12: Given 破棄した受付の録音が保存されてから24時間ちょうど, When その録音を消そうとする, Then 消せないことが返り、24時間と1秒を過ぎると消せる。
- AC-REC-13: Given 最低保持期限を過ぎた録音に保全の印が付いている, When 定期の片づけを走らせる, Then その録音は残り、保全を外して同じ片づけを走らせると消える。
- AC-REC-14: Given 別の組織の資格情報で業務画面を開いている, When 他組織の録音の再生と保全を求める, Then どちらも通らず、その録音は一覧にも出ない。
- AC-REC-15: Given マイクの許可をまだ一度も求めていない, When 「新しい予約を取る」を押す, Then その押した操作のなかで許可が求められ、求めているあいだ録音の表示が「マイクの許可を確かめています」になり、読み上げにも同じことが届く。画面が切り替わっただけでは許可を求めない。
- AC-REC-16: Given マイクが使えない面で端末側の設定を直した, When 「直したので、もう一度確かめる」を押す, Then ここまで伺った日時・お客様・手書きメモを失わずに許可がもう一度判定され、まだ使えないときは同じ面に留まって理由が読める。
- AC-REC-17: Given 録音が動いている, When 録音が途中で止まる, Then 常駐の表示が「録音していません」「--:--」に変わったことが画面を見ていなくても読み上げで伝わり、受付の操作は止まらない。
- AC-REC-18: Given 録音の保存に失敗した面が出ている, When 「このまま続ける」を押す, Then 予約台帳へ戻り、右下に「録音は端末に保管中　03:24」が残って、次に自動で送る時刻（11:20）が読める。
- AC-REC-19: Given 同じ録音の送信が 3 回続けて失敗した, When お知らせを見る, Then 「録音の保存に3回失敗しました」と「対応が必要」の札、録音番号（EY-R-1482）とお客様名、「ご予約は成立しています。」、そしてその録音が残っている端末の名前が 1 件として立つ。
- AC-REC-20: Given 送れないまま端末に残っている録音があり、その端末の業務セッションが失効した, When 同じ端末でもう一度業務を始める, Then その録音は消えずに残っていて自動の再送が再開し、失効しているあいだは送信も再生も行われない。24 時間送れないままだと保守の経路で `failed` になり、そのときに端末からも消える。

**スコープ外**: お知らせの一覧（ALERTS）の画面は `013-terminals-and-audit`。お知らせを貯める `alerts` の表は
この feature で新設する（録音の失敗は Web 予約の確認待ちより先に必要になるため）。この feature は3回失敗した事実を
録音の側に残し、`alerts` に 1 行（録音番号・お客様名・残っている端末の名前）を立てるところまで。
個人モードの昇格と暗証番号（MODE-PERSONAL）は `013-terminals-and-audit`。
受付履歴と予約台帳の画面そのものは `008-reception-and-walkin` / `005-availability-and-ledger`、予約フローの工程は `006-booking-flow`。
録音の文字起こし・要約・お客様への提供は作らない。

**決めたこと**（第2巡の検査で決着させた。根拠は承認済みモックと決定ブリーフ）:

- 録音の形式は `audio/mp4`（AAC 32kbps モノラル）を既定にする。iPadOS の Safari の MediaRecorder が確実に出せる形式で、60 分でも約 14MB に収まる。`audio/webm` は取れない端末がある。
- 未送信の録音は端末の IndexedDB に置く。置いてよいのは音声そのものと受付セッションの id だけで、お名前・お電話番号・メール・度数は引き続き永続領域に書かない。メモリだけに置くと、iPadOS の Safari が裏に回ったタブを捨てた瞬間に消え、EX-UPLOAD-FAILED の「11:20 に自動でもう一度送ります。操作は要りません。」が嘘になる。
- **端末セッションが失効しても、未送信の録音は消さない。** 消すのは①送信に成功した時点②24 時間送れないまま保守の経路で `failed` に落ちた時点の 2 つだけである。自動ロック（2 分）や担当の交代のたびに消していては、上の「11:20 に自動でもう一度送ります」が守れない。失効しているあいだは送信も再生も行わず、次に**同じ端末で**有効なセッションが立った時点で自動の再送を再開する。端末に残っているあいだ、その音声を画面で再生する操作も書き出す操作も出さない（共有 iPad で次の利用者に聞かれないため。持ち出しの経路を作らないという `design/07-nfr.md` §5.8 の決めと同じ）。`design/07-nfr.md` §6.6 の「端末セッションが失効したら削除」は同じ文書の §5.8 の表と正反対で、両方は実装できない。§5.8 と本項に寄せる。
- 自動の再送は 5 分の固定間隔（EX-UPLOAD-FAILED の 11:15 表示に対する「11:20」）。3 回続けて失敗したら「対応が必要」のお知らせに上げる。通信が切れているときの再接続は 1 分間隔（EX-OFFLINE の 11:08 表示に対する「11:09」）。
- サーバ側からの再送経路は持たない。音声の実体は端末にあり、サーバが持つのは `recordings` の行だけである。再送は端末が生きているあいだの 5 分周期と、画面の「もう一度送る」だけ。お知らせの本文にはその録音が残っている端末の名前を入れる（別の端末から押しても直らないため）。
- 24 時間動かない `recording` / `uploading` の行は、保守の経路で `failed` に落とす（警告を出し続けないため）。
- 端末の遠隔破棄は作らない。`terminal_sessions.revoked_at` で以後の送信を拒否するところまでとする（未送信の録音は端末のローカルにあり、Web からは消せない）。
- 「やめる」で受付を破棄するときの確認は 2 択（「入力をやめる」／「続ける」）にする。録音は破棄せず `discarded` として残す（破棄した受付も記録に残す）。
- 「直したので、もう一度確かめる」は読み込み直しで許可を判定し直す。工程の入力は `reception_sessions` の下書きから引き直し、端末には受付セッションの id だけを持ち越す。
- 1 ファイルの上限 100MB は約 7 時間ぶんに当たり、最長 6 分・約 1.4MB の受付録音では届かない。「録音を分割して送る」経路は作らない（`recordings.r2_key` は 1 本で、そのキーを第 2 の冪等キーにしているため、分割すると 1 録音に複数キーが要って前提が崩れる）。万一 413 `payload_too_large` が返ったときは 1 回の送信失敗として数え、3 回で「対応が必要」のお知らせに上げる。
- 再生の短命チケットは 900 秒にする。300 秒のままではモックの録音（6分12秒＝372 秒）を 1 回聞き通せない。切れたときは「もう一度開く」で取り直す。
- 録音の操作の記録（再生・保全・解除・削除）を横断して読む画面は作らない。モックにも `design/05-screen-flow.md` の画面一覧にも無く、空いた場所を埋めるために面を足さない。記録は `audit_events` に残し、API と integration テストで確かめる。

**不明点**:

- `[要確認: Q-05 — いまの前提で進める]` 業務端末は「ホーム画面に追加」した Web アプリとして配る前提で、EX-MIC-DENIED の「直し方」3 手順（「設定」を開く →「EYEX予約」を選ぶ →「マイク」をオンにする）をそのまま使う。Safari のタブのまま使うなら iPadOS の「設定」に「EYEX予約」が並ばないので、この 3 手順は書き直しになる（`design/09-open-questions.md` の Q-05。`design/07-nfr.md` §1.1 の同じ問いと 1 か所で決める）。

**データモデル差分**: `recordings` と `alerts` の 2 表を新設する（既存表への列追加なし）。`recordings` の親は
`reception_sessions`、任意で `reservations` を指す。`alerts` はここで作り、`011-web-booking` と `013-terminals-and-audit` が
読み書きする（`011` の確認待ちより先に、録音の失敗が置き場所を必要とする）。
index は `recordings_org_code_idx`（一意）/ `recordings_org_state_retain_idx` / `recordings_org_session_idx` / `recordings_org_reservation_idx`。
実体は R2（binding `RECORDINGS`）に置き、D1 には状態だけを持つ。R2 のキーを API の応答に載せない。
同じバケットには `007-customer-records` の手書きメモ（SVG）も入るので、片づけは `recordings` の行が指すキーだけを消し、
プレフィクスを走査して消す処理は書かない（走査で消すと手書きメモを巻き込む）。

**却下した代替案**:

- R2 の署名付き URL を画面へ渡す: 持ち出せてしまい、聞いた事実も残らないため却下。Worker 経由の短命チケットにする。
- 録音の許可だけを説明する専用の画面を作る: 受付が止まるため却下。使えないと分かったその場で理由と直し方を出す。
- 保存に失敗したら予約もやり直させる: お客様を二度待たせるため却下。予約は残し、録音だけを送り直す。
- 保持期限を録音ごとに指定できるようにする: 消し忘れと消しすぎの両方を招くため却下。成立30日・破棄24時間の2つに固定し、例外は保全の印だけで表す。
- 失敗した録音の再送を Queues に載せる: 無料枠の設計判断（Queues を採用しない）に反するため却下。端末に残し、端末側の 5 分周期の再送と画面の「もう一度送る」で拾う。
- サーバの日次 Cron で失敗した録音を再送する: 音声の実体は端末にあり、サーバは `recordings` の行しか持たないため実行できず却下。日次の保守は「24 時間動かない録音を `failed` に落としてお知らせに上げる」だけを担う。
- 未送信の録音を端末のメモリだけに置く: iPadOS の Safari が裏に回ったタブを捨てた瞬間に消え、自動再送の約束が守れないため却下。IndexedDB に置き、条件を決めて消す。

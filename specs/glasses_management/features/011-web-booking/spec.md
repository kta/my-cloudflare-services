# 011-web-booking: お客様向け Web 予約

- サービス: `glasses_management`
- ステータス: Approved

## 1. WHAT / WHY

**概要**: お客様が自分のスマートフォンから予約を取れるようにする。お店側は店舗ごとに
「出す・出さない」「何を出すか」「いつまで受けるか」「確かめてから確定するか」を決める。
お客様側は店舗・ご用件・日時・ご本人の情報・ご確認・完了の 6 歩を 1 問ずつ進み、
ご予約番号と確認番号で後から自分の予約を確かめ・変え・取り消せる。

**ユーザーストーリー**:

- US-WEB-01: 店長として、お店の受け入れ余力に合わせるために、Web からの予約を店舗ごとにいつでも止められるようにしたい。
- US-WEB-02: 店長として、社内の言葉をお客様に見せないために、目的ごとに「お客様に見せる呼び方」と「Web に出すかどうか」を業務の呼び方とは別に持ちたい。
- US-WEB-03: 店長として、駆け込みと遠すぎる先を避けるために、受け付ける時間の幅を自分で決めたい。
- US-WEB-04: お客様として、お店に電話をかけずに済むように、スマートフォンで 1 問ずつ答えるだけで予約を取りたい。
- US-WEB-05: お客様として、予定が変わったときに、ご予約番号と確認番号だけで自分の予約を確かめ・変え・取り消したい。
- US-WEB-06: 受付スタッフとして、確認のメールが出せなかった日でも、お客様の予約そのものは失いたくない。

**ユースケース**:

- UC-WEB-01: 店長は、店舗ごとに Web 予約を公開するかどうかと、お客様へのお知らせ文を決められる。
- UC-WEB-02: 店長は、保存する前に「お客様の画面の見え方」で、社内の言葉が漏れていないかを確かめられる。
- UC-WEB-03: お客様は、公開している店舗の中から 1 つを選べる。
- UC-WEB-04: お客様は、公開しているご用件を、お客様向けの呼び方と目安の分数から選べる。
- UC-WEB-05: お客様は、一週間ぶんの空き具合を見てから日と時刻を選べる。
- UC-WEB-06: お客様は、お名前・ふりがな・お電話番号・メールアドレスを入れ、送る前に読み返せる。
- UC-WEB-07: お客様は、予約を送ってご予約番号と確認番号を受け取れる。
- UC-WEB-08: お客様は、ご予約番号と確認番号で自分の予約を確かめ、日時を変え、取り消せる。
- UC-WEB-09: 受付スタッフは、確認待ちで届いた Web 予約を確かめて確定できる。
- UC-WEB-10: 店長は、受付を開始する何時間先からと、何日先まで受けるかを決められる。
- UC-WEB-11: サービスは、同じ送信を二度受け取っても予約を 1 件だけにできる。
- UC-WEB-12: サービスは、確認のメールを送れなかったときも予約を残し、送れなかった事実をお店に伝えられる。
- UC-WEB-13: お客様は、いま Web から受けられないとき・読み込みに失敗したとき・回線が切れたときに、行き止まりにならずに次の一手を受け取れる。

**受け入れ基準**:

- AC-WEB-01: Given 店長が設定の「Web予約の公開」を開いている, When 「Web予約を公開する」を切って「保存」を押す, Then 値が「公開していません」に変わり、その店舗のご予約ページを開いても予約の手順に入れない。
- AC-WEB-02: Given 「公開する目的」が「5件」の状態で公開の設定を開いている, When 「公開する目的」から「できあがりの受け取り」を外して保存する, Then 「公開する目的」は「4件」になり、右の「お客様の画面の見え方」からも「できあがりの受け取り」が消えて 4 件が並ぶ。
- AC-WEB-03: Given 目的が業務の中での呼び方とお客様に見せる呼び方の両方を持っている, When お客様のご予約ページで「ご用件をお選びください」を開く, Then お客様に見せる呼び方だけが並び、業務の中での呼び方は 1 つも出ない。
- AC-WEB-04: Given 「受け付ける時間」を 10:30–18:00 にして保存した, When お客様が営業時間 10:00–19:00 の日の「お時間」を開く, Then 10:30 より前と 18:00 以降の時刻は候補に 1 つも出ない。
- AC-WEB-05: Given 「何日先まで受ける」を 30日先まで にして保存した, When お客様が週を「›」で送っていく, Then 30 日先ちょうどの日は選べ、31 日先を含む週へは送れない。
- AC-WEB-06: Given 受付を開始するのは 3 時間先からだと保存した, When お客様がいまから 3 時間より手前の時刻を見る, Then その時刻は候補に出ず、3 時間ちょうど先の時刻は選べる。
- AC-WEB-07: Given 「ご予約の確定」が「お店が確かめてから確定する」になっている, When お客様が予約を送る, Then その予約はお店側では確認待ちとして数えられ、スタッフが確かめるまで台帳の確定した予約にはならない。
- AC-WEB-08: Given 公開中の店舗のご予約ページを開いた, When 「銀座店で予約を進める」「日時を選ぶ」「お客様の情報を入力する」「入力内容を確認する」を順に押す, Then 見出しが「ご希望の店舗をお選びください」「ご用件をお選びください」「ご希望の日時をお選びください」「お客様のことを教えてください」「この内容でお間違いないですか」の順に 1 つずつ変わり、上の帯の読み上げが「全6ステップのうち1つ目です」から「全6ステップのうち5つ目です」まで進む。
- AC-WEB-09: Given ある日の 13:00 が埋まっていて、その週に定休日がある, When お客様がその日を選ぶ, Then 13:00 には「満」と出て押せず、定休日の日には「定休」と出て押せない。
- AC-WEB-10: Given ご確認の画面で「まだ確定していません。」が出ている, When 「この内容で予約する」を押す, Then 完了の画面に「ご予約番号」とその番号、続けて「確認番号」とその番号と「ご変更・お取り消しのときにお使いください。」が出て、前の画面へ戻る「‹」が消える。
- AC-WEB-11: Given 「この内容で予約する」を 1 回押した, When 回線が切れて同じ内容がもう一度送られる, Then 返る予約番号は同じままで、お店の台帳にその予約は 1 件しかできない。
- AC-WEB-12: Given 完了の画面で受け取ったご予約番号と確認番号がある, When 「予約を変更・取り消す」からその 2 つを入れる, Then 「ご予約をお調べしました」と、ご来店・店舗・ご用件・お名前・ご予約番号の 5 行が出る。
- AC-WEB-13: Given 自分の予約を開いている, When 「日時を変更する」で別の空いている時刻を選んで確かめる, Then 「ご来店」の日時がその時刻に変わり、お店の台帳でも同じ時刻に移る。
- AC-WEB-14: Given 自分の予約を開いている, When 「この予約を取り消す」を押して確かめる, Then 「ご予約を取り消しました」「またのご来店をお待ちしております。」が出て、その予約は取り消され、同じご予約番号ではもう一度取り消せない。
- AC-WEB-15: Given 来店日の前日の終わりを過ぎている, When 「日時を変更する」または「この予約を取り消す」を押す, Then 日時も状態も変わらず、お電話でのご連絡をお願いする案内が出る。
- AC-WEB-16: Given 予約が 1 件できている, When 誤った確認番号で照会する, Then 明細は 1 行も出ない。正しい確認番号でだけ明細が出て、確認番号の平文は予約を作ったときの 1 回しか返らない。
- AC-WEB-17: Given 確認のメールを送れない状態になっている, When お客様が予約を送る, Then 予約は成立してご予約番号と確認番号が出るが「確認のメールをお送りしました。」は出さず、代わりに「この画面のご予約番号と確認番号をお控えください。メールはお送りできませんでした。」が出て、お店側にはメールを送れなかったことが残る。
- AC-WEB-18: Given 「この内容で予約する」を押して送信している最中, When そのボタンを見る, Then ボタンの文字が送信中であることを表し、二度押しできず、焦点はボタンに残ったままで、送信中であることが読み上げでも分かる。
- AC-WEB-19: Given お客様の情報の画面を開いている, When お電話番号とメールアドレスの欄に触れる, Then お電話番号は数字のキーボード、メールアドレスはメール用のキーボードが出て、お名前・お電話番号・メールアドレスはお客様の端末が覚えている値から入れられる。
- AC-WEB-20: Given お名前に「山口 真央」を日本語入力で変換しながら入れている, When 変換を確定する, Then ふりがなに「やまぐち まお」が一度だけ入り、変換の途中の文字は入らず、お客様が自分でふりがなを直したあとはその値が上書きされない。
- AC-WEB-21: Given お電話番号の欄に焦点があってソフトキーボードが出ている, When 画面を見る, Then 「入力内容を確認する」も入力中の欄もキーボードに隠れない。
- AC-WEB-22: Given 確認待ちの Web 予約が 1 件ある, When 台帳の予約リストの絞り込み「確認待ち」からその 1 件を開いて確定する, Then その予約が台帳の確定した予約になり、「確認待ち」の件数が 0 件になって、お知らせの「Web予約が2件、確認待ちです」の件数も 1 件減る。
- AC-WEB-23: Given 完了の画面が出ている, When 「地図・道順を見る」を押す, Then その店舗の住所を持った外部の地図が開き、戻るとご予約番号と確認番号が読める完了の画面のままである。

**スコープ外**: 業務側の予約台帳・空き枠エンジン本体（`005-availability-and-ledger`）、店内での予約作成（`006-booking-flow`）、
店内からの予約変更・取消（`009-change-and-cancel`）、来店目的そのものの登録と所要時間の編集（`004-store-settings`）、
分析（`012-analytics`）、地図・道順の実体（外部地図への受け渡しのみ）。

**決めたこと**（第2巡の検査で決着させた。根拠は承認済みモックと決定ブリーフ）:

- お客様が本人確認に使う番号は、画面でもメールでも「確認番号」と呼ぶ。`management_code_hash` / `ManagementCode` / `management-code.ts` は内部の名前として残し、画面には出さない。「管理コード」「お手元のメールの番号」は使わない。承認済みモックの WEB-06-DONE は「ご予約番号」しか描いていないが、実装は確認番号も画面に出す。メールだけを唯一の受け渡し経路にすると、メールを送れなかった日のお客様が自分の予約を二度と変更・取り消しできなくなる。
- 「ご予約の確定」に自動確定の選択肢は置かない。「お店が確かめてから確定する」の 1 値だけを持つ（モックが 1 値しか描いておらず、自動確定を足すと承認待ちの経路が二重になる）。
- 受付条件の初期値は「受け付ける時間 10:30–18:00 ／ 何日先まで 30日 ／ ご予約の確定 お店が確かめてから確定する ／ お知らせ文 120 文字まで」。受付を開始するのは既定で 2 時間先からとし、SETTINGS-WEB の「受け付ける内容」に「何時間先から受ける　2時間先から」の 1 行を足す。目的の最長 60 分＋片付け 10 分では、直前のご予約を受けると台帳の組み替えが間に合わない。
- 公開する目的が 0 件のときは Web 予約を公開できない（目的を選べない予約画面は成立しない）。
- お客様に見せるご予約番号は `web_bookings.public_code`（`EY-W-YYMM-NNNN`）として別に持ち、`reservations.code` は `EY-YYMM-NNNN` の 1 書式のままにする。モックの Web は `EY-W-2608-0031`、店内は `EY-2608-0142` / `EY-2608-0187` で、同じ連番なら 0031 と 0142 が同月に共存しないため、採番系統が別であることが読める。表示のときだけ `W` を足す案は採らない。
- 本人確認の入力画面は WEB-CANCEL の型、日時変更の候補画面は WEB-03-DATETIME の型を流用する。送信の瞬間に枠が埋まっていたときは BOOK-CONFLICT と同じ型（代わりの時刻を出す）に落とす。
- 店舗の並び順は登録順（`stores.sort_order`）。位置情報は使わない（お客様の予約の手前に許可の関門を増やさず、無料枠の構成にも入らない）。
- 公開面（`/api/public/**`）の空き枠計算では、業務面が置いた枠の仮の押さえ（KV）を読まない。KV の list は無料枠で 1,000 回/日しかなく、公開ページの閲覧数がそのまま list 数になる（1 日 400 人が 3 回ずつ日時を触れば 1,200 回で上限を越え、越えるとその種類の操作がエラーになって空き枠が丸ごと落ちる）。お客様に「他の端末が押さえ中」を見せる必要は無く、二重予約は確定時の `reservation_slot_locks` が止める。
- 確認待ちのまま残った予約は、**受け取った日**（`web_bookings.created_at` の JST 日付）の 24:00 到達時点で自動的に取り消す。**来店日ではない**（8/27 に届いた 9/17 のご予約は 8/27 の 24:00 に取り消す）。お知らせの「本日中に確認しないと自動で取り消されます。」の「本日」も受け取った日を指す。来店日起算にすると、確認待ちが 3 週間お知らせに居座り、お客様は席が取れたと思ったまま待つことになる。
- お客様向けの「読み込み中」「空」「エラー」「通信が切れた」は、業務画面の HISTORY-EMPTY / EX-EMPTY-SEARCH と同じ型（見出し 1 行＋なぜそうなったかの 1 行＋次の一手 1 つ）で作る。公開している店舗が 0 件のときはお電話の案内、その週に空きが 1 つも無いときは次に空きがある週へ送る操作、確認番号が違う／期限が切れたときは入力のやり直し、送信の途中で回線が切れたときは同じ内容の再送（冪等キーで 1 件に畳む）を次の一手にする。
- 予約を照会するための短命の鍵が切れたときは「お時間が経ちましたので、もう一度ご予約番号と確認番号をご入力ください。」と出し、WEB-CANCEL の入力画面へ戻す。黙って空にしない。
- 自動取消と、店頭からの変更・取消をお客様にメールでお伝えすることは、**いまの契約ではできない**。`packages/contracts/src/notification.ts` の `NotificationJob` は `reservation.confirmed` / `reservation.management_code_issued` / `reservation.management_code_reissued` の 3 型の `z.strictObject` で、取消・変更の型が無く、payload に別のキーも混ぜられない。型を足すのは別サービスの契約変更（人間の承認事項）なので、**承認が下りるまで取消のメールを送らない**（`009-change-and-cancel` の決めと 1 か所）。それまでは WEB-CANCEL の照会画面で「今回はお受けできませんでした」と理由を読める形にし、必要ならお電話でご連絡する運用にする。日時だけを変えたときは `reservation.confirmed` の送り直しで賄い、新しい型を足さない。`design/09-open-questions.md` の Q-01 の答えが何であっても、契約変更が済むまで送れないことは変わらない。

**不明点**:

- `[要確認: Q-01 — いまの前提で進める]` 承認制のとき確定までの間にお客様へ何と伝えるかは、完了の画面の見出しを「ご予約を承りました」にし「お店で確認のうえ、本日中にご連絡いたします。確定までお席の確保はできておりません。」を出す／確定後に「ご予約が確定しました」を送る／メールを送れなかったときは「この画面のご予約番号と確認番号をお控えください。」を出す、で進める（`design/09-open-questions.md` の Q-01）。自動取消のご連絡だけは、上の決めのとおり契約変更が済むまでメールで送らない。
- `[要確認: Q-09 — いまの前提で進める]` メールアドレスは必須（NOT NULL）にする。承認制である以上、連絡手段の無いお客様の予約が宙に浮くため（`design/09-open-questions.md` の Q-09）。

**データモデル差分**: `web_booking_settings`（店舗ごとに 1 行。公開の可否・受け付ける時間・何時間先から・何日先まで・承認要否・お知らせ文・`version`）と
`web_bookings`（予約本体への紐付け・お客様の連絡先・確認鍵と確認番号の**ハッシュのみ**・お客様に見せる `public_code`
（`EY-W-YYMM-NNNN`）・確認待ちかどうか）を新設する。確認待ちをお店に伝える `alerts` は `010-recording` が作った表へ
1 行足すだけで、ここでは新設しない。予約本体は `reservations`（`source='web'`）に作り、
ご用件は `reservation_purposes`、担当と設備は `reservation_assignments` に既存のとおり載せる。
公開する目的の判定は `visit_purposes.is_web_published` と `name_public`（`004-store-settings` で既に持っている列）を使い、新しい列を足さない。
公開設定の保存も `db.batch()` に入れるが、版の条件を 1 文目だけに付けない。D1 のバッチは 0 行しか当たらない `UPDATE` では
中断せず後続を commit するので、`version` の条件は全文（監査の追記を含む）に配り、`version` を進める文を最後に置く
（`009-change-and-cancel` の同じ決めと 1 か所）。409 `version_conflict` は最後の文の `meta.changes === 0` で判定する。

**却下した代替案**:

- 管理コードを平文で保存して照合する: 一度漏れると全予約が開くため却下。ハッシュだけを保存する。

- お客様に見せる呼び方を Web の画面側に別途持つ: 表記ゆれの元になるため却下。目的の 1 か所で持つ。

- 空き枠の絞り込みを Web 用に別の関数へ複製する: 店内と Web で答えがずれるため却下。同じエンジンに引数を足す。

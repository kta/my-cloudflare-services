# 013-terminals-and-audit: 端末の使い分けと監査

- サービス: `glasses_management`
- ステータス: Approved

## 1. WHAT / WHY

**概要**: 同じアプリを「スタッフが持ち歩く個人の iPad」と「レジ横に据え置く共有の iPad」の
どちらとしても使えるようにする。共有端末は個人ログイン無しで日常業務を回し、責任の残る操作の前だけ
本人の暗証番号で個人モードへ上げる。あわせて、重要な操作が消せない形で残ることと、
権限不足・通信断のときに打ちかけの入力を捨てないことを担う。

**ユーザーストーリー**:

- US-TERM-01: 店長として、iPad を配ったときに個人用か共用かを決め、置き場所を入れ替えたときに決め直したいので、使い方を選ぶ画面と、あとから開き直せる入口がほしい。
- US-TERM-02: 店舗スタッフとして、レジ横の共有 iPad では個人ログイン無しで日常業務を進めたいので、端末そのものを操作者として記録するしくみがほしい。
- US-TERM-03: 店舗スタッフとして、お客様の前で画面から離れても個人情報が出たままにならないでほしいので、一定時間で自動的に伏せるしくみがほしい。
- US-TERM-04: 店長として、責任の残る操作だけは誰がやったかを確実に残したいので、その前に本人の暗証番号を求めるしくみがほしい。
- US-TERM-05: 店長として、あとから経緯を追えるようにしたいので、重要な操作が消せない形で残るしくみがほしい。
- US-TERM-06: 店舗スタッフとして、権限が足りないときや通信が切れたときに打ちかけの入力を失いたくないので、何が足りないかと下書きの行き先を同じ画面に出してほしい。

**ユースケース**:

- UC-TERM-01: 店長は、この端末を個人の端末として使うか、みんなで使う端末として置くかを決め、あとから決め直せる。
- UC-TERM-02: スタッフは、個人の端末で業務を始める自分の名前を、技能と本日の勤務を見ながら選べる。
- UC-TERM-03: スタッフは、自分の 4〜6 桁の暗証番号で個人の端末の業務を始められる。
- UC-TERM-04: スタッフは、暗証番号を間違えたときに、残りの回数と続けて間違えたときに起きることと直し方を同じ画面で読める。
- UC-TERM-05: スタッフは、共有端末の置き場所を、いま誰が使っているか・つながっているかを見ながら選べる。
- UC-TERM-06: スタッフは、店舗共通の暗証番号で共有端末の業務を始められる。
- UC-TERM-07: スタッフは、共有モードのまま予約を受ける・台帳を見る・ご来店を受け付けるを個人ログイン無しで行える。
- UC-TERM-08: システムは、共有端末が一定時間さわられないとき、お客様のお名前と電話番号だけを伏せて画面を覆える。
- UC-TERM-09: スタッフは、録音の保全・注意ごとの公開と書き直しと取り下げ・設定の変更を始めるときに、本人の暗証番号で個人モードへ上げられる。
- UC-TERM-10: システムは、個人モードを一定時間さわられないときに共有モードへ戻せる。
- UC-TERM-11: スタッフは、権限が足りない操作に当たったときに、何が足りないか・設定が変わっていないこと・下書きの行き先を読める。
- UC-TERM-12: スタッフは、通信が切れているあいだ台帳をいつ時点の内容か分かる形で読み、打ちかけの入力を失わずに済む。
- UC-TERM-13: 店長は、1 件の予約について、いつ・誰が・どの端末で・何を・変更前後どうなったかを受付履歴から時系列で読み返せる。
- UC-TERM-14: スタッフは、お知らせを「対応が必要」と「お知らせ」に分けて読み、まとめて既読にできる。
- UC-TERM-15: スタッフは、お知らせに添えられた操作をやり終えたとき、その 1 件を対応済みとして一覧から外せる。
- UC-TERM-16: 店長は、端末の一覧を開き、使い方を決め直す・暗証番号を作り直す・自動で伏せるまでの時間を変えることができる。

- AC-TERM-12: Given 個人モードに上がっている, When 2 分間さわらない, Then 共有モードへ戻り、同じ操作をもう一度始めると再び「ご本人の確認が必要です」を求められる。

- AC-TERM-18: Given お知らせが 3 件ある, When 左の柱を読み上げでたどる, Then お知らせの入口が「お知らせ 3件」と読まれ、数字だけが単独で読まれることはない。柱がアイコンだけにたたまれていても同じように読まれる。
- AC-TERM-19: Given 暗証番号を 3 桁しか入れていない, When 「確定」を読み上げでたどる, Then まだ押せないことと、押せない理由が一緒に読まれる。

- AC-TERM-22: Given 「録音の保存に3回失敗しました」のお知らせが「対応が必要」に 1 件ある, When 「もう一度送る」を押して送信が成功する, Then その 1 件は自動的に対応済みになって一覧から外れ、「対応済み」の件数が 1 増え、「アラート（対応が必要）」が 0 になる。

**スコープ外**: 録音そのものの取得と保管（`010-recording`）。お知らせを立てる側の条件（`010-recording` / `011-web-booking`）。
分析（`012-analytics`）。店舗の切り替えそのもの（`003-service-foundation`）。本番のスタッフ認証（いまは dev トークングラントのまま）。
端末の登録・暗証番号の作り直し・自動で伏せるまでの時間の変更は、どのフェーズも引き受けていなかったため**この feature が持つ**
（`004-store-settings` へは持ち越さない）。

**決めたこと**（第2巡の検査で決着させた。根拠は承認済みモックと決定ブリーフ）:

- 端末の使い方は最初の 1 回で決めたあとも決め直せる。LOGIN-SHARED の「使い方を変える」と「設定 › 端末」の両方から入れる。端末の登録・暗証番号の作り直し・自動で伏せるまでの時間の変更も同じ面が持つ。
- 共有モードの完了画面に出す名前は、端末名ではなく受付のときに選んだ担当名にする。
- 暗証番号の連続失敗は `audit_events` に残す。残すのは端末の id と入力された担当の id までで、入力された値そのものは残さない。30 秒の待ちが明けたら失敗回数は 0 に戻す。
- すでに他のスタッフが業務中の置き場所を、別の端末から選ぶことは許す。前のセッションを失効させ、その事実を記録に残す。
- 情報を伏せているあいだは API を叩かない。表に戻ったときに読み直す。
- お知らせの未読は、左の赤い縦罫のほかに「未読」の札でも示す。色だけに意味を持たせない。
- お知らせは、「もう一度送る」「台帳で確認する」「影響する予約を見る」を押してその操作が成功した時点で自動的に対応済みにする。押しても直らなかったものは未対応のまま残す。手で対応済みにする操作は別に持たない。「対応済み」の件数は本日（JST）に `resolved_at` が入ったものを数える（ALERTS の右ペインの見出しが「本日 8月27日（木）」であるため）。
- 有効なスタッフが 0 人の店舗では、個人の端末として業務を始められない。「業務を始められるスタッフがいません」と、設定でスタッフを足す案内と「みんなで使う端末にする」を出して行き止まりにしない。ヘルプの画面は作らない（モック未描画。空いた場所を埋めるために面を足さない）。
- 打ちかけの下書きが無いまま権限が足りない画面（録音を聞く・分析・監査など）を開いたときは、EX-PERMISSION から「下書きは残っています」と「この下書きを店長に依頼する」を落とし、「この操作は店長だけができます」「設定はまだ何も変わっていません」と足りない権限の名前、そして「店長の暗証番号で続ける」だけを出す。
- いつ・誰が・どの端末で・何を・変更前後どうなったかを横断して読む監査の一覧画面は作らない（モックにも `design/05-screen-flow.md` の画面一覧にも無い）。読み返しは受付履歴の 1 件からたどる形に限り、それ以外は `audit_events` を API と integration テストで確かめる。
- 監査担当は独立した役割として持たない。役割は「店長」と「スタッフ（設定は見るだけ）」の 2 段で、監査の読み返しは店長の権限で行う（SETTINGS-STAFF の「できる役割」が 2 値しか出さない）。

**追加決定**:

- Q-07: `/start` と `/login/**` の最初のトークンは、admin に実在する `/api/internal/domain-auth/login` / `refresh` を `ADMIN` service binding 経由で呼んで得る。PIN はドメイン側で `AUTH_PEPPER` を使って照合し、平文を保存・記録しない（`design/09-open-questions.md` の Q-07）。
- Q-10: 依頼の受け取り先と承認フローが別featureで決まるまで、「この下書きを店長に依頼する」は画面に出さない。このfeatureでは下書きを残したまま店長PINで個人モードへ上げる経路だけを提供する（`design/09-open-questions.md` の Q-10）。
- Q-06: 自動ロック120秒と個人モードの寿命120秒は、WCAG 2.2.1（時間制限）の「必須（essential）」として扱う。伏せても打ちかけの入力は消さず、pointer・keyboard・focusによる読み上げ移動をすべて操作として数える（`design/09-open-questions.md` の Q-06）。
- 端末セッションの認証は、開始・個人モード昇格の応答で一度だけ返す64文字のランダムtokenと端末idの組を使う。D1にはSHA-256 hashだけを置き、片方だけ・形式違反・別端末・別組織・失効済みの組はJWTのstaffへ戻さず拒否する。
- 個人モードの権限は `expires_at` で終える。自動ロック後も同じ端末として日常業務を続ける最小fallbackは、同じ有効tokenを持つ行を `started_at + 24時間` 未満だけ共有端末として扱う（ちょうど24時間では失効）。明示終了と別セッションによる引継ぎは、このfallbackも失効させる。tokenの無い過去行は認証に使わない。
- 暗証番号の3回失敗・30秒待機は引き続き `SHORT_LIVED` KVに置く。単一キーへの同時更新を直列化する部品は追加せず、同時試行時の厳密な直列性は保証しない。通常の順次操作について3回目で待機になる意味を正本とする。

**データモデル差分**: `terminals`（店舗に置く iPad。`kind` が `shared` か `personal`、共有のときだけ端末側に
暗証番号のハッシュを持ち、`auto_lock_seconds` の既定は 120）と `terminal_sessions`（`mode` が `shared` か
`personal`、`personal` のときだけ `staff_id` を持ち、`expires_at` と `revoked_at` で寿命を表す）を新設する。
`audit_events` は `006-booking-flow` が P3 で作った表をそのまま使い（`008-reception-and-walkin` も同じ表を読み書きする）、
`actor_type` の値域と `terminal_id` の埋め方をこの feature で確定する。`alerts` は `010-recording` で作った表を読み、`resolved_at` / `resolved_by` を書くだけで足さない。
暗証番号の連続失敗回数は D1 に置かず KV（`SHORT_LIVED`）に 30 秒の寿命で置く。平文の暗証番号は
保存も応答もログ出力もしない。

**却下した代替案**:

- 共有端末でも操作のたびに個人ログインを求める: レジ横で毎回打つ手間が接客を止めるため却下。端末を主体にし、責任の残る操作だけ昇格させる。
- 暗証番号の連続失敗回数を D1 に持つ: 掃除の経路が要りテナントごとに行が増えるため却下。KV の寿命に任せる。
- 自動ロックで業務のセッションごと終わらせる: 打ちかけの入力が消えるため却下。画面を覆って名前と電話番号だけを伏せる。
- 監査の追記を best-effort（失敗しても通す）にする: 追記が落ちると経緯を追えなくなるため却下。本処理と同じ `db.batch()` に入れる。ただし、版や枠の条件が付いたバッチ（`009-change-and-cancel` の変更・取消、設定の保存）へ入れるときは、監査の追記にも本処理と**同じ `WHERE EXISTS` のガード**を付ける。D1 のバッチは 0 行しか当たらない `UPDATE` では中断せず後続を commit するので、ガードを付けないと「409 を返したのに、起きなかった操作の監査だけが残る」。
- 権限が足りないときに入力を捨てて設定の先頭へ戻す: 打ち直しが起きるため却下。下書きを保ったまま依頼と店長の暗証番号を同じ面に出す。

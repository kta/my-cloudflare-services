# UX レビュー — レポートに足りない観点

- **対象**: [`REPORT.md`](./REPORT.md)（2026-09-03 訂正版・38 点・122 所見）と [`findings/`](./findings/) 全 12 本
- **レビュー日**: 2026-09-03
- **突き合わせた資料**: 承認済みモック 68 枚、`design/01-requirements.md`、`design/06-use-cases.md`、`services/glasses_management/src/**`
- **立場**: このレビューはレポートを否定しない。所見の質は高い。**測っていない軸が 1 本ある**ことだけを言う。

---

## 総評

このレポートの強みは、意見を事実に還元しきったことにある。「ぬるぬるしない」を
`transitionDuration ≠ 0s` が 7 画面で 0 件という数字に落とし、「クリックしても何も起きない」を
`LedgerScreen.tsx:449` の prop 3 つに落とした。良い点を 8 つ残したことも、
自分の配点を「筆者の配点であり外部の指標ではない」と断ったことも、
Web 予約の誤判定を撤回して原因（固定した時計とサーバ実時間の食い違い）まで書いたことも、
監査文書としては上位の作法である。

決定的に抜けているのは、**100 点の定義がタスクで書かれているのに、測定が画面でしか行われていない**ことだ。
「3日目のアルバイトが誰にも聞かずに最後まで操作しきれる」は、電話を取ってから切るまで・
お客様が入ってから出るまでという時間の長さを持つ単位である。ところが `PROGRESS.md` の進め方は
12 領域を 11 ポートに分けて並走させる構成で、1 領域 = 1 画面群 = 1 ブラウザに閉じている。
この形は画面内の欠陥を漏らさない代わりに、画面をまたぐ欠陥を**構造的に観測できない**。
撤回された WEB-01 が象徴的で、あれは「Web 予約という画面群だけを切り出して固定時計で測った」から起きた誤りだった。
同じ切り出しが、逆向きの誤り——存在しない断絶を見落とす——も生んでいる。

結果として、レポートが「業務が完結しない経路は 2 本」と言うところは、通しで検証すると**少なくとも 7 本**ある。
そのうち 4 本は所見が 1 件も立っていない。以下、順に示す。

## 1. タスク単位で見た経路の断絶

4 つのシナリオを、コードの上で端から端まで辿った。所見が拾えていない断絶だけを書く。

### シナリオ A — 電話が鳴る。常連の田中様が来週の予約を変えたい

レポートは、台帳詳細の「変更する」が無反応であることを最優先の S1 に置き、直し方を
「3 つの prop を渡す（S）」としている。ここが誤っている。**prop を渡しても、この経路は通らない。**

渡す先の `ChangeScreen` は、予約を 1 件受け取る口を持っていない。props は
`storeId` / `storeName` / `now` / `onOpenCustomers` / `onStartBooking` / `onOpenLedger` /
`onGoHome` / `onSubline` / `onChangeSlot` / `onSessionExpired` / `isOffline` の 11 個で
（`change/ChangeScreen.tsx:210-233`）、`initialReservationId` に相当するものが無い。
内部の `step` も `useState('search')` 固定で始まる（`:243`）。
つまり配線を足しても、アルバイトは受話器を持ったまま**まっさらな検索画面**に降ろされ、
いま画面に開いていた田中様の名前をもう一度打つ。ニールセンの「記憶より認識」の教科書的な違反であり、
しかも直前に認識していた情報をシステムが自分で捨てている。

さらに悪いことに、その先で「担当を佐藤さんから別の人に替えたい」は**製品のどこにもできない**。
`onChangeSlot` は任意 prop で、`App.tsx:744-756` は渡していない。ソース中の注記
（`ChangeScreen.tsx:41-43`「渡されないときは 1 行で断る」）どおり、担当・場所の変更は断り書きで終わる。
要件 `01-requirements.md` §8 は業務を「予約の日時・**担当・場所**を変える」と定義しているので、
これは仕様未達の業務が 1 本まるごと存在するということである。レポートの「変更取消 60 点」は、
この 1 本を数えていない点数だ。

代わりに良い点を 1 つ。電話番号の下 4 桁で引ける検索は実装され、e2e も通っている
（`change/ReservationSearch.tsx:195-197`）。電話から始まる業務の入口として正しい。
惜しいのは、それが `search` 画面の中にしか無いことで、次項に繋がる。

### シナリオ B — 予約のお客様が来店。受け付けて、録音しながら相談し、次回予約を取る

このシナリオは 3 か所で切れる。3 つとも既存所見に無い。

**受付の前で切れる。** アルバイトがカウンターで開くのは「来店受付」だが、そこには
これから来る人が 1 人も出ない。レポートはこれを RECEP-02（S1・見積り M）とし、
「これから来る人・いま居る人・待ち時間・進行状況」をフェーズ 2 に置いた。
しかしコードを読むと、これは配線漏れでも作り忘れでもない。`domain/visit-board.ts:414-421` は
こう書いてある——「**まだお着きでない行は盤面に出さない**。絞らないと 16:00 のご予約が
11:08 の『ご来店中 N名』に混ざる（AC-RECEP-11 の人数が来店の数でなくなり、
AC-RECEP-27 の『まだどなたもお着きになっていません』は当日にご予約が 1 件でもあれば二度と出ない）」。
承認済みモック `RECEPTION-JOURNEY.png` も、来ている 4 名だけを描いている。
**この製品は、承認済みの仕様の段階で「これから来る人」を持っていない。**
だから RECEP-02 の「あるべき姿」を実装すると受入基準 2 本に反する。これは UI 改善ではなく spec 変更であり、
`SPEC_WORKFLOW.md` を通す案件としてフェーズを付け直さなければならない。見積り M も外れている。

ついでに RECEP-03（「本日すべて」タブが機能していない）は診断が誤り。タブは `scope` を
サーバへ送っており（`reception/ReceptionScreen.tsx:68,90`）、API も当日の予約を全件行に積んでいる
（`worker/index.ts:8289-8338`）。何も変わらなかったのは、seed の 8/27 に来店記録が 1 行も無く、
`all` でも `isPresent` で落ちるからである。タブは正しい。盤面の定義がそうなっている。

そして皮肉なことに、アルバイトが欲しい「これから 7件」は**すでに動く形で存在する**。
`ledger/ReservationList.tsx:190-213` の絞り込みチップ（すべて／これから／確認待ち、件数つき、
`aria-pressed` つき、0 件時の「すべてを見る」つき）がそれで、押せば `filterLedgerRows` が
クライアント側で絞る。置き場所が「予約台帳の 3 つ目の表示モードの中」というだけだ。
レポートは逆に、これを LEDGER-07「state はあるが UI が無く、常に `'all'` 固定」（S2）と書いている。
**事実と異なる。** 根本原因 D の表にも同じ誤りが載っているので、両方直したい。

**録音で切れる。** 承認済みモック `RECEPTION-CHECKIN.png` の右下には
「● 録音しています 00:42　止める」がある。実装にはこれが無い。`useRecorder` を
import しているファイルは製品全体で `booking/BookingScreen.tsx:20` の 1 つだけで、
録音は電話予約の 5 工程の間だけ回り、`receptionSessionId`（＝予約の下書き）に紐づく。
`reception/CheckinPanel.tsx:25` は「右下の録音の帯はこのフェーズでは出さない（P7）」と明記している。
つまり**受付から始まる接客は録音できない**。要件 §3.1 が「受付中は常に録音し」と書き、
モックが受付画面に録音バッジを描いているのに、である。
レポートの録音領域 9 所見はすべて「予約を取る画面の中の録音」を見ており、
録音がどの業務に紐づいているかという問いを持っていない。REC-05（止める操作が無い）も、
実は「モックにある止めるボタンが受付側ごと存在しない」が正体だ。

**次回予約で切れる。** 「お渡し」まで進めて「ご来店を終える」を押すと 1 日が終わる
（`06-use-cases.md:1990`）。眼鏡店で最も予約が取れる瞬間——できあがりの受け取り日を決める——が
ここなのに、盤面には次の予約へ行く出口が無い。`次回予約` `rebook` の類は src/web に 0 件で、
`VisitBoard` に `onStartBooking` は渡っていない。近いのは予約完了画面の「続けて予約を取る」
（`booking/DoneStep.tsx:176-182`）だけで、これは白紙の新規予約に飛ぶ。

### シナリオ C — Web 予約が入ったので確認して、当日受け付ける

訂正版は Web 予約を 70 点・製品内で最高としたが、**通しで見ると、この訂正はむしろ危険を大きくしている**。
お客様側の 6 工程が通るようになった結果、店舗側で確定できない予約が実際に積み上がるからだ。

公開側は `status: 'pending'` で予約を作り、完了画面で
「お店で確認のうえ、本日中にご連絡いたします。確定までお席の確保はできておりません。」と伝える
（`public/DoneStep.tsx:130-133`）。仕様は受信日の 24:00 JST を越えたら日次 Cron が自動で取り消し、
しかも**お客様へメールは送らない**（`06-use-cases.md:3106-3107`。`NotificationJob` に取消の型が無いため）。

では店舗側の確定 UI はどこか。無い。
お知らせの `web_booking.pending` は「台帳で確認する」を出すが、その実体は
`AlertScreen.tsx:87-88` → `App.tsx:779` の `navigate('ledger')` で、
`item.targetId` を持っているのに**捨てて**日付も指定せず今日の台帳を開くだけである
（同じ `targetId` は録音の行では使われている。`AlertScreen.tsx:79-81`）。
台帳の予約リストには「確認待ち」チップも「内容を確認」ボタンも描かれているが、後者に onClick は無い
（`ledger/ReservationList.tsx:275-277` は `kind === 'checkin'` にしかハンドラを付けない）。

結果として起きることを 1 行で言うと、**お客様が取った席が、誰にも触られないまま深夜に黙って消え、
お客様にはその通知も届かない**。売上と信頼が同時に落ちる経路で、しかも「Web 予約 70 点」という
評価の裏側にある。SHELL-08（お知らせの行き先）はフェーズ 1 に入っているが、
S1 1 件の配線ではなく、確定 UI の不在という業務の穴として扱う必要がある。

なお `ReservationList` の「ご案内」（ウォークイン）も同じ理由でハンドラを持たない。
レポートの「押しても何も起きないボタンは 5 個」は 8 画面 169 個の走査に基づくが、
リスト表示は行の種別が出て初めてボタンが現れるので、走査から漏れている。実数はもっと多い。

### シナリオ D — 途中で別の電話が鳴る（中断と再開）

これは依頼主が挙げていないが、店頭では最も頻繁に起きる。そして最も静かに壊れている。

予約の 5 工程には「あとで続ける」があり、コメントも「受付は進行中のまま残し、続きから戻れるようにする」と書く
（`booking/BookingScreen.tsx:485`）。実際、下書きはサーバの `reception_sessions` に残る。
ところが**続きから戻る画面が製品に存在しない**。`reception-sessions` を読むのは
`ReceptionHistory.tsx:310,347` だけで、そこは記録を読む面であり再開の口を持たない。
トップにも台帳にも進行中の受付は出ない。BOOK-15 は「行き先が分からない」S2 だが、
正しくは「行き先が無い」S1 である。

もっと広く、`App.tsx:324-330` の `navigate()` は画面を切り替えるたびに
`openReservation` を null に戻し、`customerQuery` を消し、各画面のコンポーネントを丸ごと unmount する。
台帳で見ていた日付も、顧客詳細で開いていた人も、分析のタブも、離れれば消える。
録音もここで死ぬ——`useRecorder` の unmount クリーンアップがマイクを離すので
（`recording/useRecorder.ts:498-501`）、予約中に台帳を確認しに行った瞬間に録音が終わる。
予約完了画面の「台帳で見る」（`App.tsx:581`）に至っては、いま採番したばかりの予約 ID を渡さずに
今日の台帳を開く。取ったばかりの予約を、自分で探し直す。

## 2. レポートが観点として持っていないもの

### 元に戻せないこと（回復可能性）

これが最大の欠落である。`元に戻す` `undo` の類は src/web 全体で **0 件**、
トースト／スナックバーの部品も 0 件。一方で不可逆な操作は次々に走る。
受付の確定も、工程を進めることも、「ご来店がなかった」も、確認を挟まず 1 タップで記録に積まれる
（`reception/ReceptionScreen.tsx:108-119`）。`ledger/ReservationList.tsx:78` には
「受け付けが済んだご予約に押し直す導線はモックに無い。押し間違いは取り消して受け直す」とあるが、
その取り消しの導線こそ RECEP-01 で死んでいる 3 ボタンである。

なぜこれが「アルバイトが迷わず使える」に直結するのか。新人が操作を止める理由は
「やり方が分からない」より「間違えたら戻せない」ことのほうが多いからだ。
戻せる製品では、新人は押して覚える。戻せない製品では、押す前に先輩を呼ぶ。
トレタが強いのはここで、台帳の操作はほぼ全部その場で戻せる。
レポートは取り消し画面を「壊してはいけないもの」として褒めているが、あれは
**不可逆であることを丁寧に説明する画面**であって、回復可能性そのものではない。
説明の丁寧さは、取り返しのつかなさを埋め合わせない。

### 誤りの予防（エラーの人間工学）

レポートが良い点として挙げた 8 つは、数えてみると全部「起きた後の説明」である——
満席の理由、閉店が開店より前、マイクが使えない、検索が 0 件、取り消しの結果予告。
文言の質は本当に高い。しかし予防の観点、すなわち **危険な操作と安全な操作の距離**、
既定値を安全側に置くこと、指での誤タップを構造で防ぐことは、1 件も測られていない。
44pt という寸法は測ったが、「取り消す」が「受け付ける」の何 px 隣にあるかは測っていない。
iPad を立って操作する現場では、これが実害の主因になる。

### モードレス性と直接操作（HIG の本体）

レポートは HIG をモーションの話に還元している。HIG が実際に要求している中心は、
モードに閉じ込めないことと、対象を直接触れることだ。この製品は両方で外している。
予約の 5 工程は `AppShell` の外に描かれ（`App.tsx:568-611`）、サイドバーも上部バーも消える。
電話中に台帳を横目で見るという、電話予約で最も自然な動作ができない。
`MicDeniedPanel` / `UploadFailedPanel` は Esc を持たず、選ぶまで抜けられない。
そして台帳の予約は掴めない（ドラッグのポインタハンドラ 0 件）。
「ぬるぬるしない」の正体はトランジションの不在だけではなく、
**画面が状態で切り替わり、対象が触れないこと**である。モーションを足しても、この 2 つは動かない。

### グローバルな入口が無いこと

電話は名前ではなく番号で始まる。ところが電話番号を引ける場所は
`change/ReservationSearch.tsx`（既存予約）と `customers/CustomerList.tsx`（顧客）に
分かれており、どちらに行くかを**受話器を上げた 2 秒で判断させられる**。
上部バーに検索は無く（`shell/AppShell.tsx:61-97` はホーム・店名・小見出し・お知らせだけ）、
ショートカットも無い。そして間違えたほうへ行くと、そこまでの状態が消える。
新人にとって「どちらの検索か」を毎回選ばされることの負荷は、機能不足より重い。

### 学習曲線と製品内ヘルプ

合格基準が「3日目のアルバイト」なのに、その人物像がレポートに 1 行も定義されていない。
何を知らないか（「担当が未定」「確認待ち」「お待たせ中」が何を指すか）、
何を怖がるか（戻せない操作）、誰に聞けないか（土曜の午後は店長が接客中）。
製品側にも、用語の説明・初回のガイド・空状態からの学習が無い。
空状態は「まだどなたもお着きになっていません」で終わり、次に何をすべきかを教えない。
新人が最初に開く画面が最も何も言わない、という構造になっている。

### プログレッシブ・ディスクロージャーの基準

レポートは時刻の札の 8 件切りを「隠している」と否定し、設定 15 項目・分析 5 面の
情報過多には触れない。隠すことは常に悪ではない。基準を 1 本置くべきで、
たとえば「その業務のその瞬間に決めるべきことだけを出す」なら、
夕方の枠は電話中に出すべき（隠すのは誤り）、分析の 5 面は日常業務から離すべき、と両方説明できる。

### 認知的負荷を数える軸

トレタと比べるための唯一の定量軸になり得たのに、一度も測られていない。
冷起動から受付完了までのタップ数、電話が鳴ってから確定までの工程数と画面遷移数、
同時に覚えておかねばならない項目数。これらは harness でそのまま測れる。

### 通信断と権限の穴

`isOffline` は Booking / Ledger / Reception / Change には渡るが、
`CustomerScreen` `SettingsScreen` `AnalyticsPane` `AlertScreen` には渡っていない
（`App.tsx:763-792`）。顧客と設定は書き込む画面である。
`onSessionExpired` も設定とお知らせには渡っておらず、401 が黙って行き止まりになる。
オフラインの帯も 2 種類が併存している（`shell/OfflineBand.tsx` と `ledger/OfflineBanner.tsx`）。

### お客様の面だけが作法を守れている理由

訂正で Web 予約が 70 点になり、業務 SPA より作法が良いことが分かった。
同じチーム・同じトークン・同じ規約で書かれた 2 つの面で、なぜ逆転したのか。
レポートはこれを「上位 3 つと下位 3 つの差＝作り込んだ画面と繋いでいない画面の差」と説明しているが、
それでは説明になっていない。差の正体は**タスクの長さ**である。

Web 予約は 6 工程 12 タップの直線で、始点と終点が 1 つずつしかない。
仕様（`06-use-cases.md` §9 WEB）も、その 1 本に沿って書かれている。
1 本しかないから、設計者も実装者も受入基準も、同じ 1 本を最後まで見ている。
だからスクロール 0 も、`autocomplete` と `inputmode` も、「満席」と偽らないことも自然に守られた。
守らなければお客様が離脱し、失敗がその場で可視になるからでもある。

業務 SPA の仕様は、`LEDGER` `BOOK` `RECEP` `CHANGE` `CUST` という群に分かれ、
それぞれの群の中で完結する形で受入基準が書かれている。群をまたぐ経路を定義した UC は 1 本も無い。
そして e2e も traceability も、その群の単位で 1 対 1 に対応している。
つまり**「画面ごとに正しい」は全員が確認しているが、「経路として正しい」は誰も確認していない**。
§1 の断絶が 4 本も所見に上がっていないのは、監査だけの見落としではなく、
仕様・実装・テスト・監査の 4 段すべてが同じ単位で切られているからである。
さらに業務側には「スタッフが慣れればいい」という逃げ道が設計に組み込まれていて、
説明のない固有語も、何も言わない空状態も、それで通ってしまう。

移植すべきものは 3 つある。押せない理由を `aria-disabled` ＋ `aria-describedby` で言う作法
（HIG-03 が「Web 予約は既にこの作法」と書いている）、
出せない枠を「満席」と偽らずに理由を言うか出さないこと、
そして 1 画面で 1 つだけ問うこと。いずれも部品と規約の移植で済む。

ただし正直に言えば、これを全部移しても §1 の断絶は 1 本も直らない。
公開側の手本が教えるのは作法であって、経路の設計ではないからだ。
業務 SPA の本当の難しさは、タスクが長く、分岐し、中断されることのほうにある。

## 3. トレタとの本質的な差

トレタが支持される理由は機能の数ではない、というのは正しい。差は 3 つの構造にある。

第一に、**トレタには基底面が 1 枚しかない**。台帳が常に下に敷いてあり、電話も来店も変更も、
その上にシートやポップオーバーとして重なって完結する。台帳から離れない。
EYE は業務ごとに画面を分け、`navigate()` が前の画面を破棄する。
この 1 行（`App.tsx:324-330`）が、レポートに載っている断絶のかなりの部分を生んでいる。
「顧客を選んだのに ID が落ちる」（`App.tsx:333-336` は `id` を受け取らず、
予約フローは電話番号で照合し直す）も、「取ったばかりの予約に戻れない」も、
「録音が画面遷移で止まる」も、すべて同じ構造の別の顔である。

第二に、**トレタの台帳は読み物ではなく物体**である。掴む、伸ばす、空きを叩いて作る。
EYE の台帳は見るためのもので、書くのは別画面の 5 工程だ。
空き枠 69 セルが意図的な no-op（`Timetable.tsx:164`）であることは、この思想の帰結であって不具合ではない。
だから LEDGER-03 を「タップで作れるようにする」と直すのは、思想の変更である。安く済む話ではない。

第三に、**トレタは「今」を中心に置く**。開いた瞬間、現在時刻が真ん中にある。
EYE は日付のグリッドを左から描き、17:00 以降が画面外に出る。
今どうなっているかではなく、その日の全体が主語になっている。

そして機能ではなく操作の帰属で言うと、この製品が構造として持っていないものは 3 つに集約できる。
操作が画面ではなく対象に属していること（どこから予約に触れても同じことができる）、
中断して再開できること、元に戻せること。
これが揃って初めて、新人は「怖くないから触る」に入る。トレタとの差はここであって、
週表示の有無でも月移動の有無でもない。

## 4. 優先順位への異議

フェーズ 0 の思想——「数行で直り体感が変わるものを先に」——には賛成する。異議は 3 点。

**フェーズ 0 の 1 番目が S ではない。** 3 ボタンの配線は、変更画面が予約を受け取れないので
経路が通らない（§1-A）。`initialReservationId` と `onChangeSlot` まで含めて初めて 1 本になる。
見積りは M、それでも 2 日以内で、優先は正しい。しかし「S だから今日直る」という前提で
計画されると、フェーズ 0 が終わったのに経路が通らないまま再監査を回すことになる。

**取り返しのつかなさを、フェーズ 0 に上げる。** 現状どのフェーズにも無い。
不可逆操作に確認と取り消しを 1 か所で入れる作業は、部品を 1 つ作れば全画面に効き、
新人の「押すのが怖い」を最短で外す。目標が「迷わず使える」なら、
モーションより先に、これが来る。

**誤情報を無情報より先に止める。** ANA-01（同じ日の予約数が 72 / 19 / 12 と 3 通り）は
フェーズ 3 に置かれている。数字が 3 通りある画面は、直るまで**表示を止める**のが正しい。
分析全体を落とす必要はなく、不整合の出る面だけでよい。0 日で終わり、信頼の毀損が止まる。

そのうえで、目標に対する最短経路として次の並びを提案する。

1. **不可逆操作の安全網**（確認 ＋ 取り消し ＋ トースト部品を 1 か所）。1〜2 日。全画面に効く。
2. **1 本のタスクを通す**——予約詳細 → 受付 → 工程 → 終える。3 ボタン配線、
   `ChangeScreen` への予約受け渡し、`onChangeSlot`、`onMarkNoShow`（`ReceptionScreen` が渡していない）。2〜3 日。
3. **来店受付に「これから来る人」を出す。** 承認済みの受入基準に触るので spec 先行。
   ただし当座は、予約リストの「これから」チップ（実装済み・動作する）を来店受付から開けるようにするだけで、
   その日から現場が使える。1 日 ＋ spec 作業。
4. **押下 100ms のフィードバックだけ先に入れる。** レポート自身が「3 ボタンの発見が遅れた原因」と
   書いているのだから、原因は最初に消す。トークン 2 つと `Button` 1 か所で、252 ボタンに効く。
   残りのモーションはフェーズ 2 のままでよい。
5. **Web 予約の確定 UI。** 公開側が通るようになった以上、これは売上の穴である。
6. 以降、既存のフェーズ 1（顧客編集・台帳の見え方・録音再生・設定）。
7. 録音を受付に付ける、次回予約の出口、台帳の直接操作。

トップを状況板にする（SHELL-05/06）は、フェーズ 2 から下げてよい。
アルバイトはトップに留まらない。留まるのは台帳と受付である。

## 5. 点数の妥当性

38 点という数字は、意思決定に使えない。定義と測定が別物だからである。
100 点は「タスクを最後まで操作しきれる」で定義されているのに、配点は領域ごとの所見数と
画面内の完結性で作られている。定義に忠実に、上の 4 シナリオで測れば完走は 0 本、すなわち 0 点になる。
土台の質（44pt・フォーカスリング 377・文言）で測れば 60 点を超える。
38 はその中間の値で、どちらの問いにも答えていない。

配点の作り方にも 3 つの偏りがある。

第一に、**使用頻度で重みが付いていない**。来店受付は 1 日に数十回開き、分析は月に 1 回開く。
それが 20 点と 35 点として並列に平均されている。頻度 × 失敗コストで重みを付け直せば、
台帳・来店受付・予約を取るの 3 領域で 8 割を占めるべきだ。

第二に、**未実装と作りの悪さが同じ物差しに載っている**。訂正がそれを証明していて、
Web 予約は API のバグ 1 本の見立てが変わっただけで 15 点から 70 点に動いた。
点数がこれだけ動く尺度は、改善の大きさを表していない。

第三に、**通しの経路が採点に入らないので、断絶が構造的に見えなくなる**。
変更・取消 60 点は、担当・場所が変えられないこと（§1-A）を数えていない。
Web 予約 70 点は、店舗側に確定 UI が無いこと（§1-C）を数えていない。
どちらも「その画面だけを見れば良くできている」という理由で高得点になっており、
点数が高い領域ほど断絶を隠すという逆転が起きている。

置き換えを提案する。総合点をやめ、再監査で動く 3 つの数字にする。

| 指標 | いまの値 | 測り方 |
|---|---|---|
| タスク完走率 | 0 / 4（§1 で通した 4 シナリオ） | シナリオ台本を 1 本ずつ通し、人が詰まらず終われるか |
| 取り消せる不可逆操作の割合 | 0 / 6（受付確定・工程・来店なし・変更・取消・おまとめ） | 操作後 10 秒以内に元へ戻せるか |
| 初回完了までのタップ数 | 未測定 | 冷起動から受付完了まで、電話開始から確定まで |

領域別スコアは残してよい。ただし「未実装」「未配線」「設計の不在」を欄で分け、
点数の隣に置く。直し方の見積りが桁で違うからである。

## So What

このレポートは、直すべきものの目録としてはよくできている。足りないのは目録の並べ方ではなく、
**測る単位**である。画面で測る限り、画面と画面のあいだにあるものは何度測っても出てこない。
撤回された WEB-01 は、その限界が偶然表に出た 1 件だった。

だから次の一手として提案したいのは、フェーズ 0 を片付けて同じ 12 領域を測り直すことではない。
`harness/` を組み替えて、**シナリオを単位にすること**である。
lib.mjs には `start()` と `go()` が既にあるので、台本を 12 本の領域スクリプトから
7 本のシナリオスクリプト（電話で変更する／来店を受け付けて次回予約まで／Web 予約を確定して当日受ける／
中断して再開する／ウォークインを受けて終える／設定を変えて影響を確かめる／新人が初日に開いて 1 件受ける）
に書き直すだけでよい。1 日で書ける。

そして報告する数字を、点数から**通ったかどうか**に変える。
いま §1 の 4 本は 0 本しか通らない。フェーズ 0 の後で 1 本通れば、それは 38 点が 45 点になるより、
はるかに多くのことを依頼主に伝える。「アルバイトが迷わず使える」という目標は、
点数では検算できないが、通ったか詰まったかでなら毎週検算できる。

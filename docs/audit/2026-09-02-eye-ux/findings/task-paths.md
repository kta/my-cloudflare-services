# task-paths（タスク単位の経路断絶）— 追加所見

画面単位の監査（`findings/` の 11 本）では見えなかった欠陥を、
**電話が鳴ってから確定するまで**のように画面をまたぐタスクで辿り直して洗い出したもの。
UX レビュー（[`../review-ux.md`](../review-ux.md)）が発見し、親エージェントが実装で裏取りした。

## この所見群が生まれた理由

12 領域を 11 ポートで並走させて監査したこと自体が、画面をまたぐ欠陥を構造的に見落とす形だった。
撤回した旧 WEB-01 は、その限界が偶然表に出た一例である。

### NEW-01 予約の担当・場所を変える手段が製品に存在しない
- **重大度**: **S1**
- **画面**: 予約を探す・変更（`search`）
- **再現**: 予約を 1 件選び、日時ではなく担当を替えようとする。
- **いま起きること**: `ChangeScreen` は `onChangeSlot?` を任意 prop で受け、渡されないときは
  1 行で断る設計になっている（`change/ChangeScreen.tsx:41-43`）。`App.tsx:744-756` は渡していない。
  よって担当・場所の変更は製品のどこからも実行できない。
  要件 `01-requirements.md` §8 は業務を「予約の日時・担当・場所を変える」と定義しており、未達である。
- **あるべき姿**: 予約 1 件から工程 3（BOOK-03-SLOT-STAFF）の盤を再利用して担当・場所を替え、
  差分確認（CHANGE-DIFF）を通して確定する。承認済みモックはこの経路を描いている。
- **根拠**: `change/ChangeScreen.tsx:41-43,207,228`、`App.tsx:744-756`
- **直し方の案**: `App` に `onChangeSlot` を実装し、`BookingScreen` の工程 3 を
  変更モードで開けるようにする。任意 prop を必須化し、断り書きの分岐を消す。
- **見積り**: M〜L

### NEW-02 「変更する」を配線しても、予約が変更画面に渡らない
- **重大度**: **S1**（RECEP-01 の見積りを訂正するもの）
- **画面**: 予約台帳 › 予約詳細 → 予約を探す・変更

- **あるべき姿**: 押した予約がそのまま変更画面の対象として開き、日時の面から始まる。

- **根拠**: `change/ChangeScreen.tsx:210-233,243`、`ledger/ReservationDetail.tsx:70-72,274-290`

  `App` の `navigate` に予約 ID を運ばせる（`openReservation` は既に台帳・受付で使われている経路がある）。
- **見積り**: M。**レポート §3 の「S（3 つの prop）」は、この分だけ過小である。**

## So What

このレポートは、直すべきものの目録としてはよくできている。足りないのは目録の並べ方ではなく、
**測る単位**である。画面で測る限り、画面と画面のあいだにあるものは何度測っても出てこない。
撤回された WEB-01 は、その限界が偶然表に出た 1 件だった。

だから次の一手として提案したいのは、フェーズ 0 を片付けて同じ 12 領域を測り直すことではない。
`harness/` を組み替えて、**シナリオを単位にすること**である。
lib.mjs には `start()` と `go()` が既にあるので、台本を 12 本の領域スクリプトから
7 本のシナリオスクリプト（電話で変更する／来店を受け付けて次回予約まで／Web 予約を確定して当日受ける／
中断して再開する／ウォークインを受けて終える／設定を変えて影響を確かめる／新人が初日に開いて 1 件受ける）
に書き直すだけでよい。1 日で書ける。

そして報告する数字を、点数から**通ったかどうか**に変える。
いま §1 の 4 本は 0 本しか通らない。フェーズ 0 の後で 1 本通れば、それは 38 点が 45 点になるより、
はるかに多くのことを依頼主に伝える。「アルバイトが迷わず使える」という目標は、
点数では検算できないが、通ったか詰まったかでなら毎週検算できる。

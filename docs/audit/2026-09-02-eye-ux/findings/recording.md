# recording（受付の録音）— 実機監査所見

環境: `vite preview` :4313（使い捨て D1 + seed）／Playwright Chromium 1194×834／
`getUserMedia` を e2e と同じ手法で差し替え（許可／拒否の両方）。**時計は固定せず実時間で計測**。
実装は `src/web/recording/`。

## 監査した画面・経路
- 「新しい予約を取る」を押した瞬間のマイク要求 → 録音開始 → 録音バッジの表示を
  **実時間 75 秒にわたり 3 秒おきにサンプリング**（表示文字列とレベルメーターのバー高さを毎回実測）
- マイクを拒否した場合の全面差し替え（EX-MIC-DENIED）
- 録音バッジが出る場所（帯／右下）、`RecordingPlayer` の到達可能性をコードで確認
- `useRecorder.ts` のタイマー実装

## 総評 — **30 / 100**

**オーナーの「録音画面が全然数字が動いていない」は完全に事実**で、原因も特定できた。
経過時間は `mm:ss` の形で出ているのに、**30 秒に 1 回しか計算し直していない**
（`RECOMPUTE_MS = 30_000`）。つまり 30 秒のうち 29 秒は数字が凍っている。
レベルメーターは 6 本の棒の高さが**固定値**で、音に一切反応しない（実測で 75 秒間ずっと同じ）。
さらに致命的なのは、**録音した音声を聞く導線が製品のどこにも存在しない**こと。
`RecordingPlayer` は実装されているが、契約が `recording: z.null()` 固定で、
呼び出し側も `recording=` を一度も渡していない。30 日保管している録音を誰も再生できない。

一方、マイクを拒否されたときの案内画面は**この製品でいちばん良く出来ている**（後述 REC-07）。

## 所見一覧

### REC-01 経過時間が 30 秒に 1 回しか動かない（秒の桁が凍る）
- **重大度**: **S1**
- **画面**: 予約を取る 全工程の下バー ／ 受付中の右下バッジ
- **再現**: マイクを許可して「新しい予約を取る」を押し、下バーの時間表示を 1 分間眺める。
- **いま起きること**: 実時間 75 秒の計測結果（3 秒おきにサンプリング、26 サンプル）:

  | 経過 | 表示 |
  |---|---|
  | +0〜+27秒 | `録音中 00:00`（10 サンプル連続で同じ） |
  | +30〜+57秒 | `録音中 00:30`（10 サンプル連続で同じ） |
  | +60〜+75秒 | `録音中 01:00`（6 サンプル連続で同じ） |

  **75 秒間で表示が変わったのは 2 回だけ**。`mm:ss` と秒まで出しているのに、
  秒の桁は `00` `30` `00` の 3 通りしか取らない。
  人間の目には「壊れて止まっている」ようにしか見えない。
  ```ts
  // useRecorder.ts:31-32
  /** 経過時間を数え直す間隔。1 秒ごとに描き直す必要は無い（読むための数ではない）。 */
  const RECOMPUTE_MS = 30_000
  ```
  コメントは「読むための数ではない」と言うが、**画面には秒まで書いてある**ので、
  利用者は読む数だと受け取る。設計意図と表示形式が食い違っている。
- **あるべき姿**: 秒を出すなら 1 秒ごとに更新する。更新頻度を落としたいなら
  表示のほうを `約1分` `約2分` のような粒度に変える。**表示の粒度と更新の粒度を一致させる。**
- **根拠**: 実測（上表）、`src/web/recording/useRecorder.ts:31-32,477-484`、
  `src/web/recording/RecordingBadge.tsx:56-60`（`elapsedLabel` が `mm:ss` を作る）
- **直し方の案**: `RECOMPUTE_MS` を 1000 にする。
  負荷が気になるなら `requestAnimationFrame` ではなく 1 秒 `setInterval` で十分
  （1 秒に 1 回の `setState` は iPad でも問題にならない）。
- **見積り**: **S（1 行）**

### REC-02 レベルメーターが音に反応しない（飾りの棒が一斉に点滅するだけ）
- **重大度**: **S1**
- **画面**: 録音バッジ（帯・右下とも）
- **再現**: 録音中にメーターの 6 本の棒の高さを測り続ける。
- **いま起きること**: 75 秒のあいだ、6 本の高さは**一度も変わらない**
  （実測で毎回 `[6, 12, 18, 9, 14, 5]` px）。
  コード上も高さは定数配列で、`animate-pulse` で 6 本が**同時に**薄くなるだけ:
  ```ts
  // RecordingBadge.tsx:62-63
  const METER_BAR = ['h-1.5', 'h-3', 'h-4.5', 'h-2.25', 'h-3.5', 'h-1.25'] as const
  ```
  つまり**マイクが実際に音を拾っているかどうかを、画面から確かめる方法が無い**。
  マイクがミュートでも、遠すぎても、故障していても、同じ見た目で「録音中」と言い続ける。
  受付が終わってから「何も録れていなかった」と気付くことになる。
- **あるべき姿**: `AnalyserNode` で実際の入力レベルを読み、棒の高さに反映する。
  無音が一定時間続いたら「音が拾えていません。マイクの位置をご確認ください」と出す。
- **根拠**: 実測（バー高さが 26 サンプル全て同一）、`src/web/recording/RecordingBadge.tsx:62-63,78-88`
- **直し方の案**: `useRecorder` が既に `MediaStream` を持っているので、
  `AudioContext.createAnalyser()` を繋いで RMS を 100ms ごとに取り、6 本へ配る。
  `prefers-reduced-motion` では数値だけ（「音を拾っています」）に落とす。
- **見積り**: M

### REC-03 録音を聞く導線が製品のどこにも存在しない
- **重大度**: **S1**
- **画面**: 予約台帳の詳細 ／ 受付履歴 ／ 予約検索 — そのどれからも聞けない
- **いま起きること**: `RecordingPlayer.tsx`（335 行）は実装済みで、
  **3 か所から実際に描画されている**（`ledger/ReservationDetail.tsx:222` /
  `change/ReservationSearch.tsx:564` / `reception/ReceptionHistory.tsx:745`）。
  塞いでいるのは 1 段上の器で、**理由が経路ごとに違う**:

  | 経路 | 塞いでいるもの |
  |---|---|
  | 受付履歴 | 契約が `ReceptionHistoryDetail.recording: z.null().default(null)`（常に null） |
  | 予約を探す | `ChangeScreen` が `recording` を渡さない |
  | 予約台帳 | `LedgerScreen.tsx:449` が渡さない ＋ 契約も未対応 |

  > **訂正（2026-09-03）**: 初版に「`App.tsx` は `recording=` を一度も渡していない」とだけ書き、
  > 単一の配線漏れとして扱ったのは不正確だった。塞ぎ方は 3 通りあり、直す量も経路ごとに違う。

  結果、**「録音を聞く」ボタンは製品のどこにも出ない**。
  録音は R2 に保存され 30 日保持されているのに、店側が聞き返す手段が無い。
  「言った・言わない」を録音で解決するという機能の目的そのものが達成できていない。
  （この事実は `e2e/recording.spec.ts` のヘッダコメント自身が「器に載っていない導線」として認めている）
- **あるべき姿**: 予約詳細と受付履歴の両方から 1 タップで再生できる。
  トレタでいう「通話録音を聞く」に相当する、この機能の存在意義そのもの。
- **根拠**: `packages/contracts/src/glasses_management.ts:2217`、
  `src/web/App.tsx`（`recording=` 0 件）、`src/web/ledger/ReservationDetail.tsx:65-69,222`、
  `services/glasses_management/e2e/recording.spec.ts:26-31`
- **直し方の案**: 契約の `recording` を `RecordingSummary.nullable()` に変え、
  Worker の詳細クエリで録音 1 本を join し、`App.tsx` から渡す。器は既にあるので配線だけ。
- **見積り**: M

### REC-04 録音していないときの `--:--` が「壊れている」ように見える
- **重大度**: S2
- **画面**: 予約を取る／変更 の下バー（録音していない全ての場面）
- **いま起きること**: 「**録音していません　--:--**」と、時計の枠だけが常に置かれている。
  録音していないのだから時間は無いはずで、`--:--` は
  「数字が出るはずなのに出ていない＝壊れている」と読まれる。
  実際オーナーはここも「数字が動いていない」と受け取っている。
- **根拠**: `src/web/recording/RecordingBadge.tsx:56-58`、
  `shots/booking/02b-slots.png` / `04-slotboard.png` / `08-customer.png` / `recording/03-mic-denied.png`
- **直し方の案**: 録音していないときは時間の枠ごと出さない（文言だけにする）。
- **見積り**: **S**

### REC-05 録音を止める・一時停止する・破棄する操作が画面に無い
- **重大度**: **S1**
- **画面**: 予約を取る 全工程
- **いま起きること**: 録音バッジは `<p role="status">` で、**押せない**。
  録音中に「今のは録らないでください」と言われても、止める手段が画面に無い。
  一時停止も、破棄も、いま何を録っているかの確認も出来ない。
  録音は工程を抜けるまで走り続ける。
- **あるべき姿**: バッジをタップで「録音を止める／このぶんを破棄する」を出す。
  お客様に「録音してよいか」を尋ねる導線も要る（同意の記録）。
- **根拠**: `src/web/recording/RecordingBadge.tsx:90`（`<p role="status">`）、
  実測（この面のボタン一覧に録音関連が 0 件）
- **直し方の案**: バッジを `<button>` にし、押すとシートで 停止／破棄／保存 を出す。
- **見積り**: M

### REC-06 お客様に録音中であることが伝わらない
- **重大度**: **S1**（法務・信頼の問題を含む）
- **画面**: 予約を取る 全工程
- **いま起きること**: 録音の印は**店員が見ている iPad の下バーの中の小さなピル 1 つ**だけ。
  対面の受付で、お客様の側から録音中だと分かる表示が無い。
  同意を取った記録も、保持期間の説明も画面に出ない。
  （マイク拒否の面には「あとから聞き直すことはできません」と書いてあるのに、
  録音できている通常時には保持や取り扱いの説明が一切無い）
- **あるべき姿**: 受付を始めるときに「録音してもよろしいですか」を明示し、
  同意の有無を記録する。録音中はお客様からも見える大きさ・位置で示す。
  保持期間（成立予約 30 日）と「音声はダウンロードできない」ことを画面で伝える。
- **根拠**: 実測（`shots/recording/01-booking-recording.png`）、
  `src/web/recording/MicDeniedPanel.tsx`（拒否時にだけ説明がある）
- **見積り**: M

### REC-07 【良い点】マイクが使えないときの案内は極めて良い
- **重大度**: —（維持すべき基準）
- **画面**: EX-MIC-DENIED
- **観測**: マイクを拒否すると全面が差し替わり、
  - 何ができなくなるか（「できないのは録音だけです」）
  - **何は続けられるか**（予約を取る・変える・取り消す／ここまで伺った内容／手書きメモ）
  - iPad の設定での直し方が **3 ステップの番号付き**で
  - 「録音せずに続ける」「直したので、もう一度確かめる」「受付をやめる」の 3 択

  が過不足なく出る。**この画面の水準が全画面の基準であるべき**。
  他の画面（PIN ロックアウト、空き枠の「満席」、台帳の空き枠）は、
  この画面と同じ設計者が書いたとは思えないほど説明が足りていない。
- **根拠**: `shots/recording/03-mic-denied.png`、`src/web/recording/MicDeniedPanel.tsx`

### REC-08 アップロード失敗が「お知らせ」に流れるだけで、受付中には分からない
- **重大度**: S2
- **画面**: 受付中 ／ お知らせ
- **いま起きること**: お知らせ画面に「録音の保存に3回失敗しました（対応が必要）」が出る
  （`shots/shell/23-alerts.png`）が、**受付をしている最中には何も知らされない**。
  自動再送は 5 分間隔（`RETRY_MS = 300_000`）で、その進捗も画面に出ない。
  端末に控えがある状態（`buffered` = 「録音は端末に保管中」）を利用者が読んでも、
  どうすればよいのか分からない。
- **根拠**: `src/web/recording/useRecorder.ts:29-30,487-494`、`src/web/recording/RecordingBadge.tsx:52`
- **直し方の案**: バッジに「保存待ち 2 件」を出し、押すと再送の状況と手動再送を出す。
- **見積り**: M

### REC-09 30 分を超える受付・画面遷移・端末ロック時の挙動が画面から読めない
- **重大度**: S2（未検証を含む）
- **いま起きること**: 「面を離れたら要らなくなる。マイクの明かりを点けたままにしない」として
  アンマウント時に全トラックを停止する（`useRecorder.ts:496-501`）。
  つまり**受付の途中で予約台帳を見に行くと録音が切れる**可能性が高い。
  そうなることも、そうなったことも画面に出ない。
- **根拠**: `src/web/recording/useRecorder.ts:496-501`
- **直し方の案**: 録音は画面から独立した器（App レベル）で持ち、
  面を移っても続ける。切れるなら切れることを事前に警告する。
- **見積り**: L

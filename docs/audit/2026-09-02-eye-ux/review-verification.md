### ANA-01 「日別の系列に週の合計が混ざっている」は実装の不具合ではなく **seed のデータ**

これは撤回済みの WEB-01 と**まったく同じ種類の誤り**である。

- **レポートの主張**:
  「トップの API 応答も `{"key":"2026-08-27","value":72}` を返しており……
  つまり**日別の系列に週の合計が混ざっている**」
  直し方: 「`overview` の**日別集計を修正**し」

- **実際に観測されたこと**:
  API 応答は再現した（8/27=72、8/31=42、8/24・8/26・8/28〜8/30 が 0）。**現象は事実**。
  だが原因が違う。**分析 API は予約表を集計していない。**
  `analytics_daily` に**あらかじめ入っている行をそのまま返すだけ**である
  （`src/worker/index.ts:10605`、`domain/analytics-report.ts:214`
  「表示側は入力された analytics_daily 行だけを読む」）。

  そしてその行を書いているのは `seed.mjs:971-991` であり、
  **seed 自身が 8/27 に 72、8/31 に 42 を直接書き込んでいる**:

  ```js
  // seed.mjs:973  ← コメントが自白している
  // 週の予約は 8/17–23=68、8/24–30=72、8/31–9/6=42、月合計は320件。
  const reservations =
    index < 16 ? (index === 0 ? 18 : 8)
    : index <= 22 ? (index < 21 ? 10 : 9)
    : index === 26 ? 72          // ← 8/27
    : index === 30 ? 42          // ← 8/31
    : 0
  analyticsRow(GINZA, date, 'reservations', 'total', '', 'ご予約', reservations)
  ```

  seed の作者が「週合計の 3 つの数字」を作りたくて、その値を**代表日 1 日に押し込んだ**。
  8/24・8/26・8/28〜8/30 が 0 なのも同じ理由（週合計を 1 日に寄せた残り）である。
  製品側の集計処理（`index.ts:3799-3807` の `analytics_daily` への書き込み＝日次ロールアップ）は
  **seed に上書きされて一度も動いていない**。

  「台帳の 12 件と合わない」も同根である。台帳は `reservations` 表を読み、
  分析は `analytics_daily` を読む。この監査環境では後者が**手で書かれた嘘の値**なので、
  一致しないのは当然で、**実装の不整合ではない**。
  台帳側の 12 件は正しい —— `seed.mjs:459` のコメント「予約 12 件」と、
  `reservationSeeds` の要素数 12 が一致する（実測）。

- **どう直すべきか**:
  ANA-01 を「**分析の値が台帳と一致しない（ただし監査環境では seed が
  `analytics_daily` を直接書いているため、実装の集計不整合であるとは言えない）**」に
  書き換え、重大度を **S1 → S2** に落とす。
  本当に指摘すべきは別のことで、**「日次ロールアップが seed に潰されていて、
  この監査では一度も検証されていない」**である。
  検証したいなら seed の `analyticsRow` を止めてロールアップを走らせるしかない。
  §6 フェーズ3 の「分析の集計不整合を直し」も同様に書き換えが要る。

## ⚠️ 根拠が弱い・未検証のまま断定している主張

### HIG-07【良い点】「タップ標的 44pt 未満が 0 件」は、母集団が狭い

- `probe.mjs` の `smallTargets` は
  `native || roleI`（`button`/`a`/`input`… または `role=button|link|tab|…`）**だけ**を数える。
  つまり `role="gridcell"` や `div[onClick]` は**最初から母集団に入っていない**。
- 実測で 8 画面すべて 0 件だったのは自分でも確認した（レポートと一致）。
  ただし「**実測した全画面**で満たされる」であって「**全要素**で満たされる」ではない。
  ここは書き分けたい。
- また `smallTargets` は `r.width < 4 || r.height < 4` を除外するので、
  **1〜3px の当たり判定は測定対象外**である。

### BOOK-01「掴める面積は帯全体の 30.6%」— 帯 144px という前提が示されていない

  **予約の長さと盤の横幅で変わる**（60 分の帯と 20 分の帯で比率が違う）。
  「30.6%」「69.4%」と小数第 1 位まで書くと、固定値であるかのように読める。
  「**予約が長いほど掴める割合は下がる（60 分の帯で約 3 割）**」と書くほうが正確で、かつ強い。

## 見落とされている欠陥

### 1. 台帳の空きセルは「空いています」と**読み上げてから何もしない**（LEDGER-03 より重い）

LEDGER-03 は「空き枠 69 セルが死んでいる」と書くが、
**その 69 セルが支援技術に何と名乗っているか**に触れていない。実測すると:

```json
{"role":"gridcell","tabindex":"0","aria-label":"10:00　佐藤 美咲　空いています"}
{"role":"gridcell","tabindex":"-1","aria-label":"10:30　佐藤 美咲　空いています"}
```

盤は `role="grid"` / `role="gridcell"`（91 要素）とローピング tabindex で
**正しく作られている**。だからこそ、VoiceOver は
「10:00　佐藤 美咲　**空いています**」と読み上げ、利用者は当然そこを選ぶ。
**そして何も起きない。** 見える人より、読み上げに頼る人のほうが強く裏切られる。
LEDGER-03 の重大度（S1）は妥当だが、**この一点を書き足すと指摘が格段に強くなる**。

（なお自分は最初「セルが `div` で非セマンティックなのでは」と疑ったが、
**それは誤りだった**。盤の ARIA 設計はむしろ良い。レポートが §7 で
褒めていないのは見落としである。）

### 2. 「お客様 様」は **すでに 1 か所で直っている** —— CHG-01 は「揃っていない」と書くべき

CHG-01 は「同じ誤りを複数画面で繰り返している」（§4 原因C）と括るが、
`ReceptionHistory.tsx:137-140` は**すでに正しい**:

```ts
/* （`お客様 様` は読み上げでも耳障りで、名前が分からない事実も伝わらない） */
return name == null ? 'お客様' : `${name} 様`
```

一方 `ReservationSearch.tsx:392` と `ChangeDateTime.tsx:258` は
`${row.customerName ?? 'お客様'} 様` のままである。
つまり**誰かが一度この問題に気づいて片方だけ直した**。
「全画面が同じ誤りをしている」ではなく「**正解が 1 か所にあるのに横展開されていない**」が正しく、
直し方も「新しく共通関数を作る」ではなく「**`ReceptionHistory` の書き方を移す**」になる。
§4 原因C の実例としてはこちらのほうが具体的で説得力がある。

## 1. 結論

100 点を「入って3日目のアルバイトが、誰にも聞かずに、迷わず、最後まで操作しきれる」と置くと、
**その定義で完走できる業務は 1 本も無い**。店頭で毎日起きる 4 つのタスクを端から端まで辿ると、
4 本とも途中で切れる。

1. **電話で予約を変える** — 台帳の「変更する」が無反応。配線しても、
   変更画面が予約を受け取る口を持たないので白紙の検索画面に降りる。
   そして担当・場所の変更は製品のどこにも存在しない
2. **来店を受け付けて接客する** — 受付画面に「これから来る人」が出ず、
   受付から始まる接客は録音できず（`useRecorder` の import は予約画面の 1 つだけ）、
   接客の終わりから次回予約へ行く出口が無い
3. **Web 予約を確定する** — お客様側は 12 タップで通るのに、
   **店舗側に確定する画面が無い**。お知らせの「台帳で確認する」は予約 ID を捨てて今日の台帳を開くだけで、
   確定されなかった予約は 24:00 JST に Cron が黙って取り消す。お客様への通知は無い
4. **一度登録したお客様の情報を直す** — 編集画面が「これから作ります」

そして 4 本すべてに共通して、**元に戻す手段が製品全体で 0 件**である
（`undo` 0・`元に戻す` 0・トースト部品 0）。

一方、土台の品質は高い。タップ標的 44pt は実測した全画面で満たされ、
フォーカスリングは 377 か所、`role="status"` は 100 か所ある。
アクセシブル名は「この予約を取り消す（取り消しの理由を選ぶと押せます）」の水準にあり、
取り消し画面とマイク拒否画面はそのまま製品の基準にできる。

お客様向け Web 予約に至っては、業務 SPA より作法が良い。
6 画面すべてがスクロール 0 で収まり、入力欄には `autocomplete` と `inputmode` が正しく付き、
休憩の時間帯を「満席」と偽らずに枠ごと出さない。業務 SPA 側はそのどれもできていない。

問題は「作れていない」ことではなく、作ったものが繋がっていないことに集中している。
S1 55 件のうち約 4 割は、数行の配線か、1 つの定数の値で直る。

### 点数の代わりに見る 3 つの数字

初版は総合点を出したが、廃止した。100 点をタスクで定義しながら領域ごとの所見数で測っており、
Web 予約は見立ての訂正だけで 15 点から 70 点に動いた。それだけ動く尺度は、改善の大きさを測れない。
領域別スコア（§5）は残すが、意思決定にはこちらを使ってほしい。

| 指標 | いまの値 | 測り方 |
|---|---|---|
| タスク完走率 | **0 / 4** | 上の 4 タスクを台本にし、人が詰まらず終われるか |
| 取り消せる不可逆操作の割合 | **0 / 6**（受付確定・工程・来店なし・変更・取消・おまとめ） | 操作後 10 秒以内に元へ戻せるか |
| 初回完了までのタップ数 | 未測定（Web 予約のみ 12 タップ） | 冷起動から受付完了まで、電話開始から確定まで |

重大度 S1 / S2 / S3 の判定は筆者による。

母集団と観測条件は次のとおり。

| 項目 | 値 |
|---|---|
| データ | `seed.mjs` が入れる EYEX 銀座店（本日 8/27 に予約 12 件、お客様 46 名、スタッフ 7 名、設備 6 件） |
| 時刻 | JST 2026-08-27 11:08 に固定（`page.clock.install`） |
| 端末 | Playwright Chromium。業務 SPA は 1194×834、Web 予約は 390×844 |
| 実行環境 | `vite preview`（実 workerd ＋ 使い捨て D1）を 11 ポートで並走 |
| 観測手段 | 画面テキスト・DOM・実行時の React props・API の生応答・スクリーンショット |

### データの限界

- **本番データではない。** 予約 12 件・お客様 46 名という小さな盤面での観測である。
  1 日 100 件を超える店舗での描画・スクロール性能は未検証。
- **実機の iPad Safari ではない。** Chromium のマウス操作で検証している。
  指でのドラッグ、慣性スクロール、Safari 固有のスクロール挙動、
  実際のマイクを使った録音は測れていない。
- **時計の固定が観測を歪めた例が 1 件あった。** 上の訂正のとおり、
  ブラウザの時計を固定したままサーバの実時間に依存する API を叩き、
  Web 予約を「壊れている」と誤判定した。
  同じ疑いのある分析の集計不整合（ANA-01）は時計を外して再測し、再現を確認済み。
  取り消しページ（`/w/ginza/manage`）は **【未確認】**。
- **grep の範囲を誤って所見を 1 件落とした。** モーションの計測を
  `services/glasses_management/src/web` に限り、`packages/ui` を見ていなかった（訂正 3）。
  同種の見落としが他にもある可能性がある。範囲は毎回 `packages/` まで広げること。
- 各領域の末尾に「未確認・要追加調査」を置いてある。そこは評価していない。

## 4. 根本原因

個別に直しても同じ指摘が再発する。原因の側を直したい。
4 つ挙げるが、重さは同じではない。最初の 1 つが今回の S1 の大半を生んでいる。

### 原因A: 「任意ハンドラ」が配線漏れを型で見逃している（最重要）

`onXxx?: () => void` の任意ハンドラが 48 個ある。
そしてコードベースには、ボタンにハンドラを渡すときの流儀が 2 つ混在している。

`ReservationList` と `VisitBoard` は安全な側で、ハンドラが渡されなければボタンごと出さない。

```tsx
{...(onCheckin !== undefined ? { onClick: () => onCheckin(id) } : {})}
{rows.length > 0 && onReceiveVisit !== undefined && (<button …>)}
```

`ReservationDetail` は危険な側で、`undefined` をそのまま `onClick` に渡す。

```tsx
<button type="button" disabled={isOffline} onClick={onCheckIn}>ご来店を受け付ける</button>
```

`onCheckIn` は親が 1 か所も渡していない（静的解析で確認）。
任意プロパティなので TypeScript は何も言わない。
実行時に 8 画面 169 個のボタンを走査したところ、`onClick` も `onPointerDown` も持たないものが 5 個あり、
うち 3 個がこの `ReservationDetail` の主要操作だった。

対処は 3 段。ボタンを描くコンポーネントのハンドラを必須にする。
残り 48 個の任意ハンドラを安全な流儀に揃える。
そのうえで「押しても何も起きないボタンがゼロ」を検証する e2e を足す
（本監査で使った `__reactProps$` の走査がそのまま使える）。

### 原因B: 良い部品の「配り方」が 2 通りあり、片方しか広まっていない

共有 UI パッケージには手応えの定義がある。`packages/ui/src/components.tsx:50-55` の
`Button` は `transition-colors`（0.15s）と 3 つの `hover:` を持つ。
ところが製品でそれを使っているのは **3 か所**で、残り **252 個のボタンは
素の `<button className="...">` を手書き**している。

同じパッケージのフォーカスリングは **377 か所**に広まっている。差は配り方にある。
`focusRing` は**文字列**としてエクスポートされているので、
手書きの `<button>` にも `${focusRing}` と 1 語足すだけで乗った。
押下の手応えは `Button` コンポーネントの中に閉じているので、手書きには乗らない。

だから直し方も決まる。押下フィードバックを `focusRing` と同じ**文字列**にすれば、
`focusRing` が既に書いてある 377 か所の隣に 1 語足すだけで広がる。
`theme.css` に duration / easing のトークンが 1 つも無いので、そこから始める。

### 原因C: 同じ部品を各画面が別々に作り直している

時刻の札の 8 件切り、「満席」の誤表示、2 週間の暦、押せない要素を `<span>` で描くこと、
盤のはみ出し、電話番号を出すか出さないか、名前が無いときの表示——
すべて 2〜3 画面で独立に同じ誤りをしている。
「時刻の枠を並べる」「空き枠の盤」「予約 1 件の表示名」「押せない状態の見せ方」を
共有部品に切り出さないと、同じ指摘が何度も出続ける。

### 原因D: 作ったものを画面に繋いでいない

| 実装 | 状態 |
|---|---|
| `RecordingPlayer`（335 行） | 3 か所から描画されているのに、どこからも聞けない（契約が `z.null()` ／ 親が渡さない ／ 両方） |
| `CustomerMerge` / `CustomerMatch` | 一覧・詳細に導線が無い |
| `MyReservations` | 描画されるが何も出力しない |
| 顧客の編集画面 | 「これから作ります」 |

## 7. 壊してはいけないもの

この水準を他の画面へ広げるのが、いちばん安い改善になる。

取り消し画面は、現在地（「まだ取り消していません」）、予約の全内容（電話番号込み）、
結果の予告（「取り消すと、この枠はすぐほかのお客様にご案内できる状態になります」）、
理由 4 択、記録先の明示、そして押せない理由をアクセシブル名に入れることまで揃っている。
マイクが使えない画面も同様に、何ができなくなるかだけでなく
「何は続けられるか」と iPad 設定での直し方 3 ステップまで書いてある。

このほか、検索の空振りで「ほかの探し方」4 つを出すこと、
営業時間の検証が「閉店が開店より前のため保存できません」と理由を言い
「木曜日に最後にお受けできるのは 18:20 です」と導出結果まで予告すること、
起動導線が端末モードを 3 項目で比較させること、
2 分でお客様情報を `●●●● 様` に伏せるロックベール、
実測した全画面でタップ標的 44pt 未満が 0 件であること、
分析の各グラフに「火曜（4・11・18・25日）の4日を除く営業日27日　ご来店日でかぞえます」と
集計条件が必ず添えてあること——いずれも維持したい。

寸法とコントラストの設計は既に良い。足りないのは「時間」と「状態」だけである。

## 8. 監査の再現手順

```sh
# 1) ビルド（dist を全ポートで共有）
cd services/glasses_management && pnpm run build

# 2) 監査用サーバ（ポートごとに使い捨て D1 + seed）
docs/audit/2026-09-02-eyex-ux/harness/serve.sh 4310

# 3) Playwright 台本
node <台本>.mjs     # harness/lib.mjs の start() が端末開始導線を通す
```

`harness/lib.mjs` は `launch(port, {viewport})` / `start(page, 'shared'|'personal')` /
`syncMembership(ctx, port)` / `go(page, 画面名)` / `shot(page, 名前)` を提供する。
`harness/probe.mjs` は `probeClickables` / `smallTargets` / `motionAudit` /
`overflowAudit` / `landmarkAudit` を提供する。

> **開発環境の落とし穴**: `services/glasses_management/.dev.vars` の `AUTH_PEPPER` が
> `.dev.vars.example`（`dev-auth-pepper-change-me`）と食い違っていると、
> seed が作る共有 PIN `2580` が永久に通らない。
> 画面には「暗証番号が違います」としか出ないので原因に辿り着けない。
> 本監査でも実際にここで詰まった。`.dev.vars.example` に揃えてから build し直すこと。

## 10. So What — 次にやること

この製品に要るのは繋ぎ直しである。
最優先の 10 件のうち 4 件は 1 行から数行で直り、
残りも大半は「作ってあるものを画面へ届ける」作業である。

次の一手は、機能を足すことでも設計をやり直すことでもない。
**最優先の 4 件を 1〜2 日で片付け、同じ `harness/` でもう一度測ること**である。
そのとき見たいのは §1 の 3 つの数字である。
タスク完走率 0/4 が動くか、取り消せる不可逆操作 0/6 が動くか、
そして初回完了までのタップ数を初めて測ること。

そのうえで 2 つの再発防止を仕込みたい。

ひとつは「押しても何も起きないボタンがゼロ」を検証する e2e である。
今回の 3 つのボタンは、e2e が 16 本あり web 側カバレッジの下限が 60% ある状態で、
それでも誰にも気づかれずに死んでいた。
問題はテストの量ではなく、**「押せるものが本当に押せるか」という観点そのものが無かった**ことだ。
本監査で使った `__reactProps$` の走査がそのまま使える。

もうひとつは、この監査自身が 2 度踏んだ落とし穴の共有である。
撤回した旧 WEB-01 と旧 ANA-01 は、どちらも
**サーバ側の集計・判定を読む所見で、seed の作りや観測条件を実装の挙動と取り違えた**ものだった。
`seed.mjs` が代表日に週合計を書き込むこと、公開 API が `new Date()` を読むこと ——
どちらもコード中にコメントで書いてある。次に誰かが測るときのために、
`PROGRESS.md` の「訂正の記録」に残してある。

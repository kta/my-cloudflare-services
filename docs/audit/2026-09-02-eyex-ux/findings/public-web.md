# public-web（お客様向け Web 予約）— 実機監査所見

環境: `vite preview` :4318（使い捨て D1 + seed）／Playwright Chromium **390×844（iPhone）**／
入口は `/w/ginza`。実装は `src/web/public/`。

> ## 訂正（2026-09-03）
>
> **初回の監査で「お客様は Web から 1 件も予約できない」と書いたのは誤りだった。撤回する。**
>
> 原因は監査手法の側にあった。業務 SPA と条件を揃えるため
> ブラウザの時計を JST 2026-08-27 に固定していたが、
> 公開側の空き枠 API は**サーバの実時間**を見る（`worker/index.ts:9903` の `const now = new Date()`）。
> サーバの実日付は 2026-09-03 だったので、画面は**サーバから見て過去の週**を問い合わせており、
> 全日が `isFull: true` で返っていた。実装の欠陥ではなく、こちらの観測条件の誤りである。
>
> 時計を固定せずに測り直したところ、
> API は 9/3 に 13 枠・9/4 に 11 枠・9/5 に 13 枠…と空きを返し、
> **予約は 12 タップで最後まで通った**（予約番号 `EY-W-2609-0001` を採番して完了画面に到達）。
>
> これに伴い、旧 WEB-01（予約が成立しない）・WEB-02（日セルが押せない）・
> WEB-03（翌週が白画面）の 3 件を取り下げ、領域スコアを **15 点 → 70 点**に改める。

## 監査した画面・経路
- 入口 `/w/ginza` からステップ 1（店舗）→ 2（ご用件）→ 3（日時）→ 4（お客様情報）→
  5（確認）→ 6（完了）を **最後まで実機で通した**
- 所要 **12 タップ**（店舗確定 1・用件 1・日時を選ぶ 1・日 1・時刻 1・進む 1・入力 4・確認 1・確定 1）
- 各画面のスクロール量・44pt 未満のタップ標的・入力属性を実測
- `/api/public/stores/ginza/availability` の生応答を取得

## 総評 — **70 / 100（製品内で最高）**

**この領域は業務 SPA より作法が良い。** 6 画面すべてが 390×844 に収まり
（`scrollHeight === clientHeight === 844`、スクロール 0）、
44pt 未満のタップ標的は 1 つも無く、主要ボタンは常に画面下端の親指が届く位置にある。
入力欄は `autocomplete="name" / "tel" / "email"`、`inputmode="numeric" / "email"` が正しく付き、
確認画面は項目ごとに「変更」で該当ステップへ戻れる。
完了画面は予約番号と確認番号を出し、「確定までお席の確保はできておりません」と
仮押さえであることまで断っている。

残る問題は 4 件で、いちばん重いのは**確認メールが送れなかったときの後始末**である。

## 所見一覧

### WEB-04 確認メールが送れなくても、番号を控える手段が画面に無い
- **重大度**: **S1**
- **画面**: ステップ 6 完了
- **再現**: 予約を最後まで通す。
- **いま起きること**: 完了画面に「**メールはお送りできませんでした。**」と出て、
  「この画面のご予約番号と確認番号をお控えください」と続く。
  出ている番号は `ご予約番号 EY-W-2609-0001` と `確認番号 3XGXZ8SP` の 2 つ。
  ところが画面には**コピーする手段も、再送する手段も、スクリーンショットを促す案内も無い**。
  お客様がブラウザを閉じた瞬間に、変更も取り消しもできなくなる。
  （なお `notifier` が dev で未設定なため送信に失敗しているが、
  本番でも配信失敗・迷惑メール振り分けは普通に起きる）
- **あるべき姿**: 番号をタップでコピーできるようにし、「メールを再送する」を置く。
  SMS での送信、カレンダーへの追加（.ics）、
  「この画面を保存してください」の明示のいずれかは要る。
- **根拠**: 実測、`shots/public/f7-done.png`
- **見積り**: S

### WEB-05 店舗が 1 つしか無いのに店舗選択のステップがある
- **重大度**: S2
- **画面**: ステップ 1 / 6
- **いま起きること**: 「1店舗を表示しています。」と表示され、その 1 店舗が既に「選択中」。
  それでも「銀座店（銀座4丁目）で予約を進める」を押させる 1 ステップを使う。
  6 ステップのうち 1 つが実質的に無意味で、進捗表示も「1 / 6」から始まる。
- **あるべき姿**: `/w/<店舗>` で入ったなら店舗選択を飛ばし、ステップを 5 つにする。
  複数店舗のリンクから入ったときだけ出す。
- **見積り**: S

### WEB-06 電話という逃げ道が用意されていない
- **重大度**: S2
- **画面**: 全ステップ
- **いま起きること**: どのステップにも**店舗の電話番号が出ない**。
  設定には `03-3571-0001` が入っているのに、お客様向けの画面では使われていない。
  空きが無い週に当たったとき、入力でつまずいたとき、
  メール送信に失敗したとき（WEB-04）のいずれでも、お客様は次の手を持たない。
- **直し方の案**: 全ステップの下部に「お電話でのご予約 03-3571-0001」を `tel:` リンクで置く。
- **見積り**: S

### WEB-07 `<h1>` が無く、`document.title` が業務アプリと同じ
- **重大度**: S2
- **いま起きること**: `main` は 1 つあるが `h1` は **0 個**。
  `document.title` は「**EYEX予約**」で、店舗スタッフ用アプリと同じ文字列。
  お客様がブックマーク・タブ・共有したときに何のページか分からない。
  URL も `/w/ginza` からステップが進んでも変わらないので、
  途中で離脱して戻ってくると最初からやり直しになる。
- **直し方の案**: `<title>` を「EYEX 銀座店 ご予約」にし、ステップごとに更新する。
  ステップを URL に持たせて途中復帰できるようにする。
- **見積り**: S

### WEB-08 モーションが 0 件
- **重大度**: S2
- **いま起きること**: 入口の全 30 要素で `transition` 0 件・`animation` 0 件。
  ステップが進んでも画面が瞬間的に差し替わる。
  スマートフォンの予約フォームとしては古く感じられる。
- **見積り**: M（横断課題。`findings/cross-hig.md` HIG-01）

### WEB-09 【良い点】この 6 画面は業務 SPA の手本になる
- **重大度**: —（維持すべき基準）
- **観測**:
  - 6 画面すべてで **スクロール 0**（`scrollHeight === clientHeight === 844`）
  - **44pt 未満のタップ標的が 0 件**
  - 主要ボタンが常に画面下端 y≈724（親指の届く位置）に固定
  - 「ステップ 3 / 6　日にちと時間」と進捗が常に見える
  - 押せない理由が必ず添えてある（「日にちとお時間をお選びになると進めます。」
    「4つの欄が埋まると進めます」）
  - `aria-disabled` と `aria-describedby` で押せない理由が支援技術にも渡る
  - 入力欄に `autocomplete="name" / "tel" / "email"`、`inputmode="numeric" / "email"`
    が正しく付いている（**業務 SPA 側は `inputmode="none"` / `autocomplete="off"` で、
    ここだけ作法が逆転している**。`findings/booking.md` BOOK-11 / `findings/customers.md` CUST-07）
  - 確認画面が項目ごとに「変更」で該当ステップへ戻れる
  - 「まだ確定していません。」「確定までお席の確保はできておりません。」と、
    いまどの段階かを毎回断っている
  - 休憩の 12:00 / 12:30 は「満席」と嘘をつかず、枠ごと出さない
    （**業務 SPA 側は休憩を「満席」と表示する**。`findings/booking.md` BOOK-06）
  - 完了画面に予約番号・確認番号・地図・変更取消の導線が揃っている

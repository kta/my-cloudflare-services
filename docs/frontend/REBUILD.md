# フロントエンドの作り直し — 承認済みモックへ寸分違わず合わせる

`docs/frontend/mockups/eyex-reservation/` の承認済みモックを正として、フロントエンドの
見た目を 0 から作り直す。バックエンドとの接続は当面持たない。

## 進め方

1. **設計** — モックの CSS を実測して、共通の語彙（`src/web/design/`）へ翻訳する。
2. **実装** — 1 画面 1 ファイルで `src/web/gallery/screens/<画面ID>.screen.tsx` を書く。
   固定値だけで描き、通信も権限判定も持たない。
3. **突き合わせ** — Playwright でモックと 1 枚ずつ重ね、違う画素を数える。
4. **差分が消えるまで 1 に戻る。**

## 道具

| コマンド | 何をするか |
|---|---|
| `node e2e/mock-reference.capture.ts` | モックから基準画像 `docs/frontend/reference/ref--<ID>.png` を作る |
| `node e2e/gallery.diff.ts [ID...]` | 突き合わせ台を撮って基準と重ね、不一致の割合を出す |
| `node e2e/crop.mjs <png> <out> <x> <y> <w> <h> [倍率]` | 差分画像の一部を拡大して切り出す |
| `node e2e/bands.mjs <ID>` | 不一致が多い横帯を上位から出す（どこを見るかの当たりを付ける） |

事前に 2 つのサーバーを上げておく。

```sh
# リポジトリの root をそのまま配る（モックと webfont を読むため）
python3 -m http.server 4176
# 突き合わせ台
pnpm --filter @app/glasses_management exec vite --port 5199 --strictPort
```

`GALLERY_BASE` を渡せば別ポートの dev サーバーを見に行く（並行作業のとき）。

出力は `docs/frontend/diff/impl--<ID>.png`（実装）と `diff--<ID>.png`（違う画素を赤で塗る）。

## 基準画像について

基準は承認済みモックの見た目そのものである。余白も文字寸法もモックのまま撮り、
アプリ側がそれに合わせる（`src/web/app.css` がブラウザ既定の余白・見出し寸法を
明示的に持ち直している）。

ただし次の 2 点だけは「モックの書き漏れ」として正規化してから撮る。理由も含めて
`e2e/mock-reference.capture.ts` に書いてある。

- **ボタンの `font:inherit` / `color:inherit` の抜け**。同じ画面の中でもボタンごとに
  有無がばらついており、抜けているボタンだけシステム書体・黒文字・13px に落ちる。
  設計ではなく書き漏れなので、宣言どおり本文の書体と文字色を継がせる。
- **台紙と端末の外枠**。モックは端末の絵を見出し付きの台紙に載せている。台紙の余白で
  端末が小数の位置に置かれ、字が半画素ずれる。対象の 1 面だけを原点へ寄せ、
  ビューポートをその実寸にしてから撮る。

## 合格の目安

**基準画像と実装の撮影が、バイト単位で一致すること。** 2026-08-28 時点で 44 画面
すべてが一致している。ここまで来ると割合も差分画像も見る必要がない。

崩れたときは `node e2e/overlay.ts [ID...]` を使う。1 枚の画像に 5 面（基準・実装・
重ね合わせ・差分・ずらし探索の結果）を並べ、次を数字で出す。

- **ずれ** — 上下左右に ±8 画素ずらして最も合う位置を探す。`0,0` 以外なら面ごと
  ずれている。字の輪郭の揺れと配置のずれを取り違えずに済む。
- **平坦な色の取り違え** — 対の両方が「その画像で広い面積を占める色」であるときだけ
  拾う。`#fff0ed` と `#fff1ed` のような塗りの取り違えが、割合に出なくてもここに出る。

重ね合わせの面は、基準を赤・実装を青の版にして 1 枚に刷ったもの。合っていれば灰色に、
ずれていれば赤と青が分かれて見えるので、ずれの向きが目で読める。

`node e2e/gallery.diff.ts` は割合と差分画像だけを出す軽い方。日常はこちらでよい。

## 一致させるまでに詰まったところ

同じ轍を踏まないように残す。

1. **書体が別物だった。** `packages/ui` が Fraunces と Public Sans を読み込んでいた。
   モックは IBM Plex Sans JP。これに気づくまで、何を直しても全画面がうっすら違った。
2. **モックが書体を宣言だけして読み込んでいない。** ボタンによって `font:inherit` /
   `color:inherit` の有無がばらついており、抜けているボタンだけシステム書体・黒・
   13px に落ちる。書き漏れとして正規化してから撮る。
3. **台紙で端末が小数の位置に置かれる。** 字が半画素ずれるので、対象の 1 面だけを
   原点へ寄せ、ビューポートをその実寸にしてから撮る。
4. **基準側のサブセットを絞ると記号だけ字形が変わる。** 日本語と欧文だけ読ませていた
   ときは、`●` や `✓` が基準の側でシステム書体へ落ちていた。アプリと同じ一式
   （`400.css` など全サブセット）を読ませる。**これで 43 画面が一気に一致した。**
5. **半透明の枠を不透明な近似色に置き換えない。** `#ffffff70` は 43.92% で、
   Tailwind の 1% 刻みでは表せない。緑に重ねた結果の色に置き換えると直線は合うが、
   角の丸みで下地との混ざり方が変わる。半透明のままトークンに持つ。

## 規約

- 色・角丸・文字寸法は `packages/ui/src/theme.css` のセマンティックトークンだけを使う。
  Tailwind 既定パレット（`bg-blue-500`）と任意値（`p-[13px]` / `text-[#hex]`）は禁止。
  モックに無い段が必要になったら、まずモックを見直す。それでも要るならトークンを足す。
- 4 の倍数でない実測値（列幅 390px / 250px、`1.4fr 1fr 1fr auto` など）は、
  純粋な配置としてインライン `style` で持つ。
- 日本語を `font-mono` で描かない。IBM Plex Mono は和文グリフを持たない。
  等幅は時刻・ID・数値だけ。
- コメントは日本語で、「何を」ではなく「なぜ」を書く。

## どの方言が正典か

承認済みモックは 2 つの寸法体系で描かれている。**76px の緑バーだけを持つ側が正典**である。

| | 正典（76px） | もう一方（67px + ステータスバー） |
|---|---|---|
| ファイル | `approved.html` / `staff-approved.html` / `operations-approved.html` / `settings-complete-approved.html` / `exception-states-approved.html` / `web-booking-complete-approved.html` | `settings-approved.html` / `analytics-approved.html` / `reception-history-approved.html` / `store-switch-approved.html` / `settings-responsive-approved.html` |
| 面の数 | 40 | 7 |
| バー | 76px・ワードマーク 19〜20px | 25px の偽 iOS ステータスバー + 67px |
| 緑 | `#1f604b` | `#286b55` |
| 本文 | 16px | 10〜11px |

正典とする理由は 3 つ。

1. `docs/frontend/mockups/README.md` の「採用」表に載っているのは `approved.html` と
   `staff-approved.html` の 2 つだけで、どちらも 76px 側である。
2. 面の数が 40 対 7 で、製品の大半が 76px 側で描かれている。
3. もう一方は**偽の iOS ステータスバー**（`9:41` / `5G` / `100%`）を描いている。アプリが
   システムのステータスバーを偽装するのは HIG が明確に禁じており、端末の額縁を
   そのまま製品仕様へ持ち込んだ書き損じと判断できる。本文 10〜11px も HIG の
   最小 11pt を割っている。

**実アプリのクロムは 76px 側だけを使う。** もう一方の 7 面は、承認済みモックの記録
として突き合わせ台に残す（`ANALYTICS` / `RECEPTION-HISTORY` / `STORE-SWITCH` /
`SETTINGS-GUIDE` / `SETTINGS-SP` / `WEB-*-COMPACT`）。実アプリの同じ画面は、正典の
寸法で組み直したうえで、モックの情報構造（何をどう並べるか）だけを継ぐ。

## モックからの意図的な逸脱

承認済みモックに従わないと決めた点は、ここに理由とともに残す。ここに無い違いは
「合わせ損ね」であって「判断」ではない。

### 1. 全画面共通の左サイドバー（モックには無い）

モックは面の行き来を、緑バーのタブと各面の左サイドに分けて持たせている。
その形には次の問題があり、実際に事故が起きた。

- タブの並びが面ごとに違う（実測で 5 通り）。同じ製品の中で主ナビの項目が
  出たり消えたりする。
- 同じ面が 2 つの名で呼ばれる（`変更履歴` と `監査ログ`）。
- 深いものは 3 階層辿らないと出てこない（分析・お知らせ）。
- 2 本目の緑帯を外した際、**5 つの面が実際に到達不能になった**。

そこで行き先はすべて 1 本の左サイドバーに集めた（`design/sidebar.tsx`）。
緑バーは店舗・副題・主操作だけを持つ。

見た目の語彙は増やしていない。250px の柱・地色 `side`・白い選択面・48px の行は、
元から設定と運用の面が持っていた形（`operations-approved.html` の `.side`）を
そのまま全画面へ広げたものである。

各面の中の節（`共有iPad` / `保存期間` など）は柱を 2 本立てず、開いている
行き先の下へ一段下げて入れる（面が `AdminLayout` の `sections` へ渡し、
`app-chrome.ts` の `screenSections` を経由して柱が読む）。

予約フローとホームは柱を出さない。前者は電話を受けている最中の面で、途中で
別の面へ移す動線を置くと入力が消える。後者は主操作 2 枚を大きく見せる面で、
モックどおり柱を持たない。

### 2. 録音の全画面の許諾・拒否（モックにはある）

`BOOK-MIC-PERMISSION` / `EX-MIC-DENIED` は、利用者の指示により実アプリから
外した。電話を受けた直後に開く面なので、録音の可否を先に問う全画面が挟まると
受付そのものが止まる。録音の状態は下部バーの表示だけで足りる。
突き合わせ台にはモックの記録として残してある。

### 3. 個人再認証の「個人ログインID」欄（モックには無い）

`REAUTH` のモックは 個人PIN の 1 欄だけを持つ。実アプリはその前に
個人ログインIDの欄を置いている。落とせない理由は 3 つある。

- PIN の伸長塩が `app:pin:<組織>:<個人>` で、誰の PIN かが決まらないと
  ブラウザ側で伸長値を作れない。生の PIN は送らない設計なので、ここは
  避けて通れない。
- 完全共有の iPad には個人セッションが無い。サーバ側にも「いま誰が触って
  いるか」を知る手がかりが無く、個人 ID を解決できない。
- 契約 `SharedTerminalReauthenticationInput` が `userId` を必須にしている。

欄を落とすには認証の設計そのものを変えることになるので、モックとの差は
ここに残す。バー・幕・板の形はモックどおり（幕もモーダルも重ねない）。

### 4. モックのバーのタブは左サイドバーの節になる

`SETTINGS-RESULT` のモックは緑バーに `設定一覧 / 公開結果 / 版履歴` の 3 本を
持つ。逸脱 1 のとおり行き先はすべて左の柱に集めているので、これらは
`設定ガイド` の下の節として出る（6 工程が `設定一覧`、その下に `公開結果`）。
公開結果は工程 6 の一節ではなく、全幅の独立した面として描く。

## 突き合わせ台と実アプリの関係

`/__gallery` に並ぶのは、承認済みモックと 1 枚ずつ突き合わせるための**表示だけの
複製**である。ここが一致していることは、**実アプリの画面がモックどおりであることの
証明にはならない**。実アプリの画面（`StaffWorkspace` から辿る各画面と `PublicBooking`）
が `src/web/design/` の語彙で組まれて初めて、モックどおりになる。

実アプリの画面を直したら、対応する突き合わせ台の画面も同じ語彙で組まれているかを
確かめること。台の方だけが一致していて実アプリが古いまま、という状態を作らない。

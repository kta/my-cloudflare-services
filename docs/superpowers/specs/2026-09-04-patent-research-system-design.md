# 典拠（Tenkyo）— 特許調査・出願支援システム 設計書

- 日付: 2026-09-04
- ステータス: Draft（人間の承認待ち）
- サービスディレクトリ: `services/patent_research`
- 製品名: **典拠（Tenkyo）**

## 0. なぜこの製品が存在するのか

特許の先行技術調査は「類似文献を並べる」作業ではない。**請求項を構成要件に分解し、構成要件ごとに、
どの公報のどの段落がそれを開示しているかを一つずつ突き合わせる**作業である。判断の単位は文献ではなく
**「構成要件 × 公報 × 段落番号」の交点**であり、その交点に置かれた引用の原文が、判断のすべての根拠になる。

汎用の LLM に「この発明は特許になりますか」と聞くと、それらしい文章が返る。だがその文章が引いている
公報番号と段落番号は、しばしば存在しない。存在しても、そこにその文は書かれていない。**特許の世界で
これは致命的である**。出願の可否、拒絶理由への応答、無効審判の帰趨が、その一文の実在にかかっている。

だから典拠は「AI が賢く答える製品」ではない。**機械検証できない主張を、構造的に画面に出せない製品**である。

### 製品テーゼ（すべての設計判断の上位規範）

> AI が生成した主張は、`(公報番号, 段落番号)` に紐づき、その段落の原文の中に引用文が実在することを
> **機械が照合できたときにだけ**、支持された主張として表示される。照合できなかった主張は、
> 削除されるのではなく **「照合できなかった」という事実とともに残り、支持の根拠には決してならない**。

この一文がデータモデル（§4 の `evidence` テーブル）とバリデータ（§5）とUI（§7 の典拠の余白）に
そのまま実装されている。ここを緩めたら製品ではなくなる。

## 1. スコープ

### やること
- 特許庁／INPIT のバルクデータ（媒体で受領する生データ）を、ローカルの正規化コーパスに取り込む
- 構成要件単位の先行技術検索（全文検索 + 分類コード + ベクトル）と、検索式の完全な記録
- クレームチャート（構成要件 × 公報 × 段落 × 引用原文 × 関係 × 照合状態）の作成・検証
- 新規性／進歩性の論証の下書き（主引用・副引用・組合せの動機付け・阻害要因の型に沿って）
- 明細書ドラフト（施行規則の見出し構造に 1:1 対応した節）の生成と編集
- 引用ネットワークのグラフ表示
- 上記すべてを、追加の課金なしにローカルで完結させる

### やらないこと（明示的なスコープ外）
- 特許庁への電子出願の**送信**（インターネット出願ソフトの代替は作らない）。出力は「様式に沿った書類」まで
- 他人のために業として出願書類を作成・代理すること（**弁理士法72条**。§2 参照）
- クラウドへのデプロイ（`admin` との連携も行わない。単発のローカルアプリとして完結させる）
- 外国特許（第1版は日本のみ。データモデルは `country` 列を持たせて将来に備えるが、実装しない）
- 法的助言。本システムの出力は**すべて下書き**であり、判断は人間（弁理士または出願人本人）が行う

## 2. 法的な立ち位置（設計に直接影響する制約）

**弁理士法72条**により、他人のために業として特許出願手続の書類を作成・代理することは弁理士の独占業務
である。一方、**自己の発明について自ら出願すること（自己出願）は誰でも自由**である。したがって本製品の
正当な使い方は次の2つに限られる。

| 使い方 | 適法性 | 本システムの位置 |
|---|---|---|
| ① 弁理士が自分の業務を効率化するために使う | 適法 | 弁理士の**業務支援ツール**。最終判断は弁理士 |
| ② 出願人が自分の発明を自分で出願するために使う | 適法（自己出願） | 出願人本人の**作業机** |
| ③ 弁理士でない者が、他人の発明の出願書類を業として作る | **違法** | **この用途を想定した機能を作らない** |

これは単なる注意書きではなく、**設計上の制約**として次の形で実装する。

- 生成物のすべてに `法的助言ではない / 判断は人間が行う` の帰属を機械的に付す（Markdown ドラフトの
  フッタ、画面のドキュメントヘッダ、エクスポートファイルの先頭）
- 「出願する」ボタンを作らない。最終操作は常に「書き出す」であり、提出は人間が別の手段で行う
- 案件に「出願人＝自分か他人か」を持たせず、**マルチクライアント管理機能を作らない**（②の用途に
  必要なく、③を助ける形になるため）

### 3.1 なぜコーパスを D1 に入れないのか（却下した代替案）

| 代替案 | 却下理由 |
|---|---|
| コーパスも D1（Drizzle + migrations）に入れる | D1 バインディング経由では SQLite 拡張を読み込めず **sqlite-vec が使えない**。また FTS5 の仮想テーブルを Drizzle のマイグレーションで管理するのは表現力が足りない。何より**コーパスは派生物**であり、マイグレーション履歴で管理すべき資産ではない（作り直せる） |
| SPA から直接サイドカーを叩く | クロスオリジンになり CORS が必要。ルート規約4（同一オリジン・CORS を書かない）に反する |
| アプリ全体を Node/Express で書く | このリポジトリの Zod 単一ソース・Hono RPC・デザイントークン・テスト規約という資産を全部捨てることになる。利用者の明示的な要求（example_service をベースに）にも反する |
| コーパスも Worker 内で読む（D1 以外の SQLite を直接開く） | workerd に生のファイルシステム・SQLite アクセスは無い |
| ベクトルを `vectors.db` に分ける | 段落とベクトルの整合を 1 つの取引で守れない。同一ファイルに置く |
| 1bit 量子化でベクトル検索を粗く絞る | 実測 recall@10 が 27〜40%。先行技術調査で真の上位の 6〜7 割を落とす |

**採用**: コーパスは独立プロセス。Worker からは `x-internal-key` 付きの HTTP で呼ぶ。これは
リポジトリが既に持つ **notifier の内部API（service binding + `x-internal-key`）と同じ形**であり、
新しい概念を増やしていない。キー未設定時は fail close（502）。

**確認済み（実測）**: `vite preview` の workerd から `127.0.0.1` のサイドカーへ outbound fetch が
届く。実際に `GET /api/corpus/status` が `reachable: true / publications: 12` を返し、
E2E（`e2e/claim-chart.spec.ts`）も実サイドカーに対して 6 本すべて緑になった。

なお、サイドカーを落とした状態で検索すると workerd が
`The Workers runtime crashed unexpectedly and is being restarted` を出して再起動することがある。
接続拒否の扱いによるものと見られ、**アプリの応答は正しく 503 になり画面も正しく出る**
（E2E がそれを確認している）。ローカル開発の癖として記録しておく。

### 3.2 二層検索（実測に基づく改訂）

当初「16TB は全件扱えないので絞る」と設計したが、**実測でそれは誤りだった**（`docs/patent/BUDGET.md`）。
取り込みは 1,714 公報/秒、DB は 27.2 KB/公報、検索は 62,084 件ヒットでも 1 ms である。
したがって層の切り方はこう変わる。

| 層 | 対象 | 中身 | 全件やるか |
|---|---|---|---|
| **層1: 書誌** | 受領データの**全件** | 公報番号・出願番号・各日付・発明の名称・出願人・IPC/FI/Fターム・要約 | **全件**（数分） |
| **層2: 全文 + 全文検索** | 受領データの**全件** | 段落単位の本文 + FTS5 bigram 索引 | **全件**（500万公報で約2.7時間・441GB） |
| **層3: 意味ベクトル** | 明示的に**昇格した部分集合** | int8 量子化ベクトル + 1bit 量子化 | **段階的**（全件だと数ヶ月） |

つまり **「分類コード + 全文検索」による調査は最初から受領データの全範囲に対して可能**であり、
絞り込みが必要なのは意味ベクトルだけである。これは調査の質にとって好都合な形である
（実務の第一級の道具が全範囲で使え、上積みだけが段階的になる）。

層3 への昇格は明示的な操作（`corpus embed --ipc G06F3/01 --from 2010`）であり、
どの部分集合が層3に入っているかは `promotion_sets` テーブルに記録される。
**検索結果には常に「この検索が層3のどの範囲を見たか」が付随する**
（見ていない範囲を「無かった」と誤読させないため。これも製品テーゼの一部）。

利用者の希望は「本当は全部やりたい」である。設計は**全件昇格を禁止しない**。
`corpus embed --all` は動く。所要時間は BUDGET.md に正直に書き、夜間の連続実行で
段階的に広げる運用を推奨する。

## 4. データモデル

### 4.1 corpus.db（コーパスエンジン所有、better-sqlite3）

派生物。壊れたら再構築できる。マイグレーション履歴を持たず、スキーマはコード内の DDL が単一ソース。

| テーブル | 主なカラム | 役割 |
|---|---|---|
| `meta` | key, value | `tokenizer_version` を刻む。索引の互換性の判定に使う |
| `import_batches` | id, media_label, source_path, product_name, format, started_at, finished_at, publication_count, notes | 受領媒体1本 = 1行。**どのデータから作られたコーパスか**の出自 |
| `publications` | **pub_number (PK)**, country, kind, app_number, filing_date, pub_date, reg_date, title, applicants(JSON), inventors(JSON), ipc(JSON), fi(JSON), fterm(JSON), abstract, claim_count, has_fulltext, **sections_ingested(JSON)**, pdf_path, batch_id, imported_at | 層1。公報1件。`sections_ingested` は実際に取り込めた部分（claim/desc/abstract）で、「請求項しか取れていない公報への明細書引用」を却下ではなく保留と言うために要る |
| `paragraphs` | **id (AUTOINCREMENT)**, pub_number, para_no, section, seq, text, **text_hash**, char_len | 層2。**引用の最小単位**。`id` は FTS5 の rowid と 1:1 で、**再利用しない**。`text_hash` は本文の変化を検知してベクトルを無効化するため |
| `paragraphs_ngram` | pub_number, para_no, ng | FTS5 / `tokenize='unicode61'`。`ng` は原文を**空白区切りの bigram 列**にしたもの。§12.2 の実測に基づく |
| `citations` | pub_number, cited_pub_number, source | 公報間の引用（元データに含まれる場合のみ） |
| `promotion_sets` | id, predicate(JSON), **model, dim, semantic**, publication_count, chunk_count, created_at | どの部分集合を層3へ昇格したか。モデルと次元を持つのは、次元違いを別の空間として扱うため |
| `extract_failures` | pdf_path, pub_number, reason, detected_at | テキストレイヤ無し・破損など。**握りつぶさず必ず残す** |

`section` は `claim` / `desc` / `abstract`。請求項は `para_no` の代わりに `claim_no` を `section='claim'`
の `para_no` に格納する（`0001` 形式ではなく `C001`）ことで、同一テーブルで扱う。

### 4.2 チャンクベクトル（corpus.db に同居）

| テーブル | 主なカラム |
|---|---|
| `chunks` | id, pub_number, para_no, chunk_seq, text_hash, model, dim, scale, vec (BLOB int8), vec_bin (BLOB 1bit/dim), promotion_id, created_at |

当初は `vectors.db` を別ファイルにする設計だったが、**同一ファイルに置いた**。
理由は、段落とチャンクの整合（本文が変わったらそのベクトルを消す）を 1 つの取引で守りたいから
である。ファイルを分けると、その不変条件を跨いだ取引が張れず、
「存在しない本文のスコアで順位が決まる」という壊れ方が起きる（実測で確認した欠陥）。

ベクトル検索は **sqlite-vec を使わず純 JS で実装する**（§12.3）。二段検索なので ANN 索引が要らない。
**1bit 量子化による粗い絞り込みは実装しない** — 実測で recall@10 が 27〜40% だったため
（`docs/patent/BUDGET.md` §4.1）。

チャンクは**段落境界を跨がない**。跨いだ瞬間に「どの段落からの引用か」が言えなくなり、製品テーゼが崩れる。
長い段落は段落内で分割し、`chunk_seq` を持つ。

### 4.3 D1 `patent_research`（Worker 所有、Drizzle + migrations）

全テーブルに `organization_id`。単独運用では固定値を使うが、**クエリのスコープは必ず JWT の `org` から**
取る（規約6。将来の外販でそのまま使えるようにするため）。

| テーブル | 主なカラム | 役割 |
|---|---|---|
| `organizations` | id, name, plan, is_disabled, created_at | 規約の `requireActiveOrg` を成立させるためのローカル行。admin とは同期しない |
| `matters` | id, organization_id, title, status, tech_field, created_at, updated_at | 案件（1発明 = 1案件） |
| `disclosures` | id, organization_id, matter_id, revision, problem, solution, effects, embodiments, keywords(JSON), external_llm_allowed, created_at | 発明開示。**未出願の秘密**。`external_llm_allowed` が false の案件は外部 API に本文を送らない（§6） |
| `disclosure_messages` | id, organization_id, matter_id, role, content, provider, created_at | 「こんなのが欲しい」→「こういう形で？」→ OK の対話ログ |
| `claim_elements` | id, organization_id, matter_id, claim_no, element_key, text, is_essential, sort_order, created_at | **構成要件**。クレームチャートの行の見出し。`element_key` は A, B, C… |
| `searches` | id, organization_id, matter_id, element_id, query(JSON), compiled_sql, mode, corpus_batch_high, promotion_set_id, hit_count, executed_at, engine_version | **検索式の完全な記録**。調査報告書に必要で、かつ再現可能性の担保 |
| `search_hits` | id, organization_id, search_id, pub_number, rank, score, snippet | 検索結果 |
| `evidence` | id, organization_id, matter_id, element_id, pub_number, para_no, quoted_text, relation, quote_check, quote_check_detail, review, reviewed_at, reviewer_note, produced_by, created_at | **典拠**。製品の心臓。§5 で詳述 |
| `assessments` | id, organization_id, matter_id, kind, primary_ref, secondary_refs(JSON), motivation_type, reasoning, conclusion, created_at | 新規性／進歩性の論証 |
| `drafts` | id, organization_id, matter_id, revision, section, markdown, created_at | 明細書ドラフト。`section` は施行規則の見出しに 1:1 対応 |
| `analysis_jobs` | id, organization_id, matter_id, kind, status, skill, params(JSON), requested_at, started_at, finished_at, error, result_ref | Claude Code スキルが拾うキュー |
| `graph_edges` | id, organization_id, matter_id, from_kind, from_id, to_kind, to_id, kind, weight | グラフ表示用の辺（`cites` / `evidence` / `similar` / `same_applicant`） |

`drafts.section` の値（施行規則の明細書構成に対応）:
`title` / `technical_field` / `background_art` / `prior_art_documents` / `problem` / `solution` /
`advantageous_effects` / `brief_description_of_drawings` / `description_of_embodiments` /
`reference_signs` / `claims` / `abstract`

**確認済み（一次情報の検索結果）**: 施行規則 様式第29 の見出しとして
【発明の名称】【技術分野】【背景技術】【先行技術文献】【特許文献】【発明の概要】
【発明が解決しようとする課題】【課題を解決するための手段】【発明の効果】
【図面の簡単な説明】【発明を実施するための形態】【実施例】【産業上の利用可能性】
【符号の説明】が存在することを確認した。`DraftSection` と `DRAFT_SECTION_HEADINGS`
（`packages/contracts/src/patent_research.ts`）はこの一覧に合わせてある。
`[要確認: 並び順の厳密な規定と、段落番号【0001】の付与開始位置の条文根拠は、
特許庁のサイトが機械的な取得を拒むため未確認。**様式変換フェーズに入る前に**
人間が公式 PDF を開いて確定させる。本体（調査とクレームチャート）の実装は
Markdown で持っているので、この未確認に妨げられない。]`

## 5. 典拠の照合（製品テーゼの実装）

`evidence` 行は **2つの独立した軸**で状態を持つ。混ぜないことが重要である。

### 軸1: `quote_check` — 機械照合（引用の実在）

コーパスに対して機械的に判定する。人間は介在しない。

| 値 | 意味 | 判定 |
|---|---|---|
| `pending` | 未照合 | 挿入直後の初期値 |
| `verified` | **引用文が、その公報のその段落の原文の中に実在する** | 正規化後の `paragraphs.text` に `quoted_text` が部分文字列として含まれる |
| `quote_mismatch` | 段落は実在するが、引用文がその中に無い | 段落あり・部分一致なし → **却下** |
| `paragraph_missing` | 公報は実在するが、その段落番号が無い | → **却下** |
| `publication_missing` | 公報自体がコーパスに無い | → **却下** |
| `not_in_corpus_tier2` | 公報は層1にあるが、**その部分（請求項/明細書）の全文**が層2に無いため照合不能 | → **保留**（「無い」とは言わない） |
| `quote_too_short` | 引用が短すぎて典拠にならない | → **却下**（ただし「前後を含めて引用し直す」で回復できる） |

正規化が吸収してよいのは「**同じ文字の書き方の揺れ**」だけである: 全角/半角（NFKC）、大文字小文字、
ダッシュ類（`-` `‐` `–` `—` `−` `－`）と波ダッシュ（`〜` `～`）、異体字セレクタ、`【】`、
そして**和文のあいだの空白**。

**吸収してはならないもの**:
- 同義語・語形（「瞳孔」と「ひとみ」）
- **踊り字**（「人々」と「人人」を同一にしたら、それだけで引用の同一性が緩む）
- **長音符**（`ー` をダッシュに畳むと語が変わる）
- **英数字どうしのあいだの空白**。ここを潰すと、表組みの「実施例1␣␣2.5」から `12.5` が
  「原文に実在する」と判定される（実測で確認）。特許では数値が新規性の分かれ目なので致命的である。
  英数字のあいだの空白だけは 1 個に畳んで残す。

加えて、**正規化後 10 文字未満の引用は照合を通さない**（`quote_too_short`）。下限が無いと、
AI は引用文を「る」「を」にするだけで照合を通せる（日本語の段落なら助詞はほぼ必ず含まれる）。
これは作話（`quote_mismatch`）とは直し方が違う（前後を含めて引用し直せばよい）ので、状態を分ける。

`verified` 以外の行は、**UI で支持の根拠として一切表示されない**。ただし削除もされない。
クレームチャートには「却下された引用」の欄が別に存在し、`quote_check_detail` に
「AIは【0032】に◯◯と書いてあると主張したが、実際の【0032】は△△である」が残る。
これは AI の信頼性を利用者が自分で評価するための材料である。

### 軸2: `review` — 人間の法的評価（関連性）

機械照合を通った典拠について、人間が法的な意味を判定する。

| 値 | 意味 |
|---|---|
| `unreviewed` | 未評価 |
| `confirmed` | この段落は確かにこの構成要件を開示している（または示唆する／阻害する） |
| `disputed` | 引用は実在するが、この構成要件の開示にはあたらない |

`relation` は `discloses` / `suggests` / `teaches_away` / `background` / `unrelated`。
`teaches_away`（阻害要因）を型として持つことが進歩性の論証に必須である。

### 5.1 バリデータの位置

照合は **Worker 側で行う**（`POST /api/matters/:id/evidence` のハンドラ内で、コーパスサイドカーに
段落原文を問い合わせて判定する）。理由: AI（Claude Code スキル）側の善意に依存させないため。
スキルがどんな JSON を送ってきても、Worker を通った時点で `quote_check` が確定する。
**スキルは `quote_check` を指定できない**（契約のスキーマに含めない）。

## 6. 秘密の扱いと外部送信

| データ | 送信先 | 条件 |
|---|---|---|
| 未出願の発明開示（`disclosures`, `disclosure_messages`） | Claude Code（Anthropic） | 利用者が Claude Code を使う前提そのものなので不可避。**画面に明示**する |
| 未出願の発明開示 | Gemini その他の外部 API | **禁止**。`external_llm_allowed` が既定 false。true にするには画面で明示的な操作が必要 |
| 既に公開されている公報テキスト | Gemini 無料枠 | **許可**。要約・分類・キーワード抽出に使う。公開情報なので秘密の問題は生じない |
| 公報コーパス全体 | どこにも送らない | ローカルのみ |

`external_llm_allowed=false` の案件について外部プロバイダを呼ぶ経路は、**コードレベルで存在しない**
ようにする（プロバイダ選択関数が案件フラグを引数に取り、false のとき外部プロバイダを返さない）。
テストでこれを固定する。

## 8. テスト方針

`docs/testing/TEST_RULE.md` に従い、以下を**境界値まで**必ず書く。

1. **典拠の照合（この製品固有の最重要領域）** — `evidence.quote-check.test.ts`
   - 完全一致 / 前後に空白 / 全角半角の違い / 改行を含む / `【】` の有無 → `verified`
   - 1文字違う / 語順が違う / 同義語に置換 → `quote_mismatch`（**通してはいけない**）
   - 段落が無い → `paragraph_missing` / 公報が無い → `publication_missing`
   - 層1にあるが層2に無い → `not_in_corpus_tier2`（`quote_mismatch` と**取り違えない**）
   - 契約に `quote_check` を含めても無視されること（クライアントが照合状態を偽装できない）
2. **検索の再現性** — `search.reproducibility.test.ts`
   - 同じ `query` と同じ `promotion_set_id` で 2 回実行 → 同一の `hit_count` と同一の順位
   - `corpus_batch_high` が変わったら「コーパスが変わった」と記録され、過去の検索と区別される
3. **秘密の境界** — `disclosure.confidentiality.test.ts`
   - `external_llm_allowed=false` の案件でプロバイダ選択が外部プロバイダを返さない
   - 公報テキストの要約経路では外部プロバイダが選ばれる
4. **時刻** — `*.time.test.ts`。時刻は必ず引数注入（`now: Date`）。`Date.now()` に依存しない
5. **権限** — `permissions.test.ts`。表駆動で全エンドポイント × アクター。未知パスも入れる
6. **テナント分離** — `tenant-isolation.test.ts`。3テナント。body に `organizationId` を混ぜる偽装
7. **失敗時フォールバック** — コーパスサイドカーが落ちているときに、
   検索は 503 を返し**握りつぶさない**。典拠の照合は `pending` のまま残り、`verified` にならない

## 11. 却下した設計案（記録）

| 案 | 却下理由 |
|---|---|
| スクレイピングで公報を集める | J-PlatPat 等は規約でプログラムによる自動アクセスを禁止。規約違反データを根拠にした調査報告書は弁理士に出せず、商品として成立しない。バルクデータ受領に置換した |
| ベクトル検索だけで先行技術調査を行う | ベクトル類似度は「同じ分野の文献」を返すだけで、「構成要件Aを開示する文献」を保証しない。構成要件分解 + 分類コード + 全文検索を第一級にし、ベクトルは第二段の補助にした |
| AI の出力を自由記述のレポートとして保存する | 引用の実在を機械照合できなくなる。構造化テーブル（`evidence`）に落とし、照合を必須にした |
| 全公報をベクトル化する | 時間とディスクが非現実的。層1（書誌・全件）と層2（全文・部分集合）に分けた。ただし全件昇格を禁止はしない |
| チャンクを固定長で切る | 段落を跨いだ瞬間に「どの段落からの引用か」が言えなくなる。段落境界を跨がない分割にした |
| admin サービスと連携して認証する | 利用者の要求により単発アプリ。固定 org_id でテナントスコープ規約だけ満たす |
| Queues / Workflows で分析を非同期化 | ローカル完結なので不要。`analysis_jobs` テーブルをキューにし、Claude Code が手動 or `/loop` で拾う |

### 12.2 日本語全文検索（実測により設計が覆った）

当初 FTS5 の `trigram` トークナイザを採用する計画だったが、**実測で使えないことが判明した**。

```
sqlite3 :memory: "CREATE VIRTUAL TABLE t USING fts5(x, tokenize='trigram');
  INSERT INTO t VALUES('瞳孔の中心座標を算出する');
  SELECT count(*) FROM t WHERE t MATCH '瞳孔';"
→ 0
```

trigram は**3文字未満のトークンを検索できない**。特許の技術用語は「瞳孔」「視線」「撮像」「電極」
「樹脂」のように**2文字が主力**であり、これらが1件も引けないのでは調査に使えない。

**採用する方式: 空白区切り bigram + `tokenize='unicode61'` + フレーズ検索**

原文を bigram 列に変換して格納し、検索語も bigram 列にしてフレーズ検索する。

| 原文 | 索引に入る文字列 |
|---|---|
| `瞳孔の中心座標を算出する` | `瞳孔 孔の の中 中心 心座 座標 標を を算 算出 出す する` |

| 検索語 | クエリ | 実測結果 |
|---|---|---|
| `瞳孔` | `"瞳孔"` | **ヒット** |
| `中心座標` | `"中心 心座 座標"` | ヒット（フレーズなので連続性が保証される） |
| `瞳中`（原文に連続して存在しない） | `"瞳中"` | **0件**（偽陽性なし） |
| `瞳孔 AND 中心` | `"瞳孔" AND "中心"` | 正しく AND が効く |
| `bm25()` | — | 機能する |

`detail=full`（既定）を維持する。`detail=none/column` にするとフレーズ検索が壊れ、bm25 の精度も落ちる。

**既知の限界（正直に記録する）**: 1文字の検索語は bigram に分解できないため、この索引では引けない。
1文字クエリは `LIKE` へのフォールバックとし、UI で「1文字の検索語は低速な走査になる」と明示する。
特許の調査で1文字語を単独で引く場面はほぼ無いため、実用上の制約は小さい。

### 12.3 SQLite ドライバとベクトル検索（実測により依存が消えた）

当初 `better-sqlite3` + `sqlite-vec` を追加する計画だったが、**どちらも不要になった**。

```
node -e "import('node:sqlite')" で確認した内容:
  sqlite_version: 3.53.4
  FTS5: OK          bm25(): OK          json1: OK
  loadExtension: あり（{ allowExtension: true } で有効化）
```

**Node 26 に内蔵の `node:sqlite`（SQLite 3.53.4）で必要なすべてが揃っている**。ネイティブモジュールの
ビルド（node-gyp）が不要になり、依存追加ゼロで済む。利用者の「完全に自作してください」という要求に
最も忠実な解でもある。

ベクトル検索も `sqlite-vec` を使わない。理由は**二段検索だから ANN 索引が要らない**こと。

- 通常の検索: FTS5（bigram）と IPC/日付で**数千件以下**に絞ってから、その候補集合の中だけで
  コサイン類似度を計算する。数千 × 768 次元の内積は純 JS の `Float32Array` で数ミリ秒。
- 「全件を横断してベクトルで引きたい」場合: 1 bit/次元に量子化した `vec_bin` を
  `BigUint64Array` の popcount でハミング距離走査し（1M件 × 768bit ≒ 96MB、純 JS で数百ミリ秒）、
  上位を `Float32Array` で再スコアする。

`sqlite-vec` は pre-v1 で破壊的変更が前提と公式に明記されており、ANN の有無も確認できなかった。
**確認できないものを製品の基盤に置かない**。

### 12.4 埋め込みモデル（アダプタ化して実装を止めない）

`ollama` は未インストール、`pdftotext` も未インストールだった。ここで実装を止めないために、
**埋め込みと PDF 抽出はアダプタにする**。

| プロバイダ | 実体 | 追加インストール | 用途 |
|---|---|---|---|
| `deterministic`（既定） | 文字 bigram をハッシュして L2 正規化した**語彙ベクトル**。純 JS | 不要 | 開発・テスト・決定的な回帰テスト。意味は捉えないが「同じ入力→同じ出力」が保証される |

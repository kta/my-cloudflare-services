# glasses_management 設計

## 目的と到達点

`glasses_management` は、複数店舗の眼鏡店向けに、スタッフの予約受付・来店対応・顧客参照と、顧客向け Web 予約を一つのドメインで提供する。既存の `glasses_reservation` は永続化のない旧モックとして廃止し、本サービスへ移行する。

今回の対象は `specs/glasses_management/features/002-eyex-reservation-product/` に定義された全 181 UC、125 AC、および `docs/frontend/mockups/eyex-reservation/` の承認済み画面・状態である。SKU、在庫、保証、AI 提案、店舗横断の空き枠比較・送客は対象外とする。

## 確定した判断

- サービス名は `glasses_management`、パッケージ名は `@app/glasses_management`、Worker 名は `glasses-management` とする。
- `services/glasses_reservation` は削除対象とし、CI・Makefile・root test/deploy matrix から外す。モックと仕様の履歴は新サービスの仕様・設計資料へ移管して保持する。
- `glasses_management` は Worker、React SPA、Hono RPC API、専用 D1、非公開 R2 録音バケットを所有する。Worker と SPA は同一オリジンで配信する。
- `admin` は認証と組織の正とする。`admin` の単独運用方針は、本サービス向けの組織同期と認証プロキシを追加する範囲で改訂する。
- `notifier` を再導入し、Web 予約の確定メールと管理コードの発行・再発行メールだけを同期 service binding で送信する。Queues は使用しない。
- Web 予約の変更・取消は、予約番号と会社発行の管理コードで本人確認する。コードはD1にハッシュだけを保存し、期限、試行上限、失効、発行履歴を管理する。メール、SMS、ブラウザからの自動再送は行わず、再発行は会社側の本人確認後にだけ実行する。
- 録音本体は非公開 R2 に置く。D1 には受付セッション、状態、保持期限、保全状態、R2 key などのメタデータだけを保存する。ダウンロード API は提供しない。

## サービス境界とデータ所有

```text
browser ── same origin ──> glasses-management
                              ├─ D1: 業務データ、版、冪等、監査
                              ├─ R2: 非公開録音本体
                              └─ notifier: 確定・管理コードのメール送信
admin ── service binding ───> glasses-management
```

`admin` は組織、利用者、認証情報を所有する。`glasses_management` は同期した組織行、店舗、店舗所属・権限、予約、顧客、設定、録音メタデータ、共有端末、監査、分析・通知状態を所有する。組織同期には admin が発行する単調増加 `revision` を含め、service binding の到着順が逆転しても古い状態で上書きしない。cross-D1 JOIN は行わない。

全テーブルは `organization_id` を持ち、店舗業務の行は原則 `store_id` も持つ。IDはアプリ生成UUID、FKとDB生成IDは使わない。更新可能な予約、顧客、ウォークイン、注意事項、設定には版番号を持たせる。予約登録・変更・取消・録音メタデータ・Web確定は、D1の冪等レコードで重複を防ぐ。

空き枠と資源競合は、来店目的が定める時間調整単位へ予約区間を分解し、担当者・設備の確保行を `db.batch()` と一意制約で同時確保する。確定前に再検証し、競合時は409として入力と同一店舗内の代替候補を返す。

## 認証、権限、共有端末

非公開 API は default-deny の `tenantAuth()` と組織有効性確認を通す。組織行が未同期なら503、無効なら403、認証不備・期限切れなら401とする。JWTの `org` だけをテナント根拠とし、body、query、pathの組織IDを認可根拠にしない。

既存JWTの粗い `admin` / `staff` は認証の入口に維持し、店舗ごとの操作可否は `glasses_management` の店舗所属と permission set で評価する。管理設定、注意事項の公開・改訂・非表示化、録音の保全・解除は個人再認証を必須とする。

完全共有 iPad は、高エントロピーの端末セッションを使う。D1にはトークンのハッシュ、店舗、端末、失効時刻、最終通信だけを記録する。非表示化・バックグラウンド・無操作期限・失効を検知したらPIIと未送信情報を破棄し、業務開始画面へ戻す。共有端末の管理操作は個人PIN再認証へ切り替え、共有端末と個人の双方を監査する。

## 公開Web予約とメール

公開 API は店舗slugから組織・店舗を解決し、入力値の組織・店舗IDを信頼しない。店舗検索、店舗詳細、目的、日時、顧客情報、確認、完了、本人確認、成立照会を提供する。顧客画面に技能・設備・内部メモを表示しない。

確定処理はD1上の確定キーで冪等にし、確定後に予約番号と管理コードを発行する。`notifier` はその確定メールを同期で送る。送信失敗は予約を取り消さず、予約詳細と完了画面に「予約は成立、メールは未送信」の回復導線を表示し、会社側だけが再発行できる。メール再送は顧客自身の操作には提供しない。

## 録音、監査、設定公開、運用

録音は、権限確認、録音中、停止、送信中、保存済み、保存失敗、保全中、削除予定、削除済みを予約状態と独立して扱う。成立予約は録音完了から最低30日、破棄受付は最低24時間保持する。最低期間前の通常削除と手動削除は拒否する。R2 Lifecycleだけに頼らず、Workerの定期処理で削除結果とD1を照合し監査する。

設定は下書き、確認待ち、公開予約、公開中、受付停止を正式状態とする。競合、失敗、再検証要求は状態ではなく警告である。公開前・実行直前に未来予約、営業時間、技能、設備、Web枠を再検証する。過去版は直接再公開せず、新しい下書きとして復元する。

管理操作と録音の再生・保全・削除、権限変更、顧客統合・誤関連解除は、追記専用の監査イベントを同一`db.batch()`で書く。監査書き込みが失敗した管理操作は成立させない。

## UI とアクセシビリティ

承認済みモックは情報階層と視覚方向の正とする。HTML内の値をコピーせず、EYEX固有の色・書体・形状を `packages/ui/src/theme.css` のセマンティックトークンに翻訳する。既存の旧モック用トークンは新サービスへの移管時にEYEX名称へ整理する。

スタッフ画面は横向きiPad、顧客Webと設定の狭幅画面は375pxを最小対象とする。全主要操作は44×44 CSS px以上、native要素優先、可視focus、論理Tab順、Enter/Space/Escape、200%文字拡大、Split View、reduced-motion、WCAG AAを満たす。モックにないloading、empty、validation、403、409、network failure、stale、共有端末ロック、録音失敗は必ず実装する。

## 実装フェーズ

1. サービス移行と仕様ゲート: 新サービス仕様、旧サービス廃止計画、全UC/AC・画面台帳の移管、未割当証跡の解消。
2. 基盤: contracts、D1、組織同期、認証プロキシ、権限、監査、版、冪等、JST時計、R2/KV/bindings。
3. 受付条件: 店舗、営業時間、来店目的、技能、勤務、設備、資源確保と空き枠エンジン。
4. 予約と顧客: 電話・店頭受付、顧客検索、復唱、競合、顧客台帳、録音と保持。
5. 現場運用: 台帳、ウォークイン、来店進捗、予約検索・変更・取消、店舗切替、共有iPad。
6. 顧客Web: ポータル、店舗専用URL、Web予約、確定メール、会社発行管理コード、成立照会。
7. 管理: 設定公開閉ループ、注意事項、端末・PIN、監査、録音運用。
8. 改善と完成: 分析、通知状態、顧客重複訂正、全状態の画面証跡、E2E traceability、アクセシビリティ、`pnpm check`。

各フェーズは、契約・テストを先に追加して期待する失敗を確認してから最小実装を行う。Worker/integrationは各coverage指標80%以上、web unitは各60%以上、Approved UC/ACは各1本のPlaywright E2Eへ一意に対応させる。

## 採用しない案

- 旧 `glasses_reservation` を実サービスへ拡張する案: モック専用境界を引きずり、名前とD1/API/認証の正が曖昧になるため不採用。
- `admin` の認証・組織を複製する案: 認証源泉が分裂し、無効化・監査・権限の即時性を失うため不採用。
- メール送信を予約確定の前提にする案: 送信失敗で成立予約を失うため不採用。
- 自動メール再送・SMS・Queues: ユーザーの運用方針と無料枠の設計判断に反するため不採用。

## 2026-08-26 レビュー是正: 確定競合と回復境界

予約の候補判定だけでは同時確定を防げないため、確定処理は予約・顧客・資源占有を同じD1書込み境界に置く。`availability_bookings` は候補計算専用の投影とし、確定の排他根拠には使わない。新しい `reservation_resource_allocations` は、予約ID、組織、店舗、resource kind (`staff` / `equipment` / `purpose`)、resource ID（capacity unitを含む）、開始時刻を持つ。担当者・設備の個別割当を必須化し、同じリソースの同一分への重複確保をD1の一意制約で拒否する。複数時間帯をまたぐ重複は、設定が任意の分単位を許すため1分単位で占有行を分割して確保する。

確定時は、可否エンジンが選んだ担当者・設備を明示的に返す。予約、顧客upsert、分割された資源占有、availability投影、監査、冪等完了結果を一つの`db.batch()`で書く。いずれかの一意制約に失敗した場合は全体をロールバックし、409 `slot_unavailable`を返す。顧客は`(organization_id, phone_normalized)`を一意にし、upsertで来店回数を更新する。予約側の氏名等は予約時点の連絡先スナップショットであり、将来の訂正・匿名化操作の対象として監査する。

冪等キーは組織、店舗、操作にスコープする。業務上の失敗（未確保・入力不備）はclaimを完了状態にしないため、同じキーで安全に再試行できる。D1書込み後に応答結果だけが不明になった場合は結果照会で回復し、無条件のclaim再取得は行わない。
